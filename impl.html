    ├── page-bridge.js         (loaded into page context; communicates via postMessage)
    ├── background.js          (service worker — Gemini calls only)
    └── popup.js

Why page-bridge.js is a separate file: Content scripts run in an isolated world and cannot access page-defined JS (dataViewerApp, getPostingOverview, action tokens). The bridge is injected as a real <script src="..."> element so it runs in page context with access to those globals. Using a separate file (vs. a string blob injected from content.js) gives real DevTools line numbers on errors. It must be listed under web_accessible_resources in manifest.json.

Key Technical Decisions

page-bridge.js vs inline string injection
Bridge is a real file loaded via <script src>, not a string blob eval'd from content.js. Reason: real DevTools line numbers when debugging. Declared in web_accessible_resources for waterlooworks.uwaterloo.ca.
Posting ID extraction
Use input[name="dataViewerSelection"].value — the most reliable selector. The visible span.overflow--ellipsis text also works as fallback. Do NOT use col-key="Id" or :is-id="true" (Vue template attrs, stripped from rendered DOM).
selectAll vs per-page scraping
One POST with the selectAll token returns all matching posting IDs across all pages. This is exactly what WW's own "select all" checkbox does internally. No need to paginate through the table.
getPostingOverview returns HTML, not JSON
No explicit dataType on the $.post call, so jQuery returns whatever the server sends (HTML string). Use DOMParser + .textContent to strip to plain text before Gemini. Cap at ~6000 chars to control token cost.
Folder trigger
dataViewerApp.sidebarPostingIds = Number(postingId) then dataViewerApp.jobFolderEditSidebar = true. Bare form (no .$data) — this is what the page uses at lines 7963-7964 of exampleWW-compact.html. Both forms work in Vue 3; bare is preferred.
MutationObserver target
Observe the <table> element (not tbody) because DataViewer may replace the entire tbody on re-render. Use childList + subtree. Re-inject score badges in the callback whenever new tr.table__row--body elements appear.
Scores live in memory only
scores is a module-level Map in content.js. It does not persist across page reloads or sessions. This is intentional per spec (out of scope: cross-session persistence).
Rate limiting
600ms delay between Gemini calls. 429 retries: 2s, 4s, 8s (max 3). Both enforced in background.js.

Out of Scope

Per plan.html: auto-apply, cover letters, cross-session score persistence, backend server, non-Gemini providers, PDF CV upload. New features bump major version to v02.xxx.
