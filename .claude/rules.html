Project Rules

All agents working on this project must follow these rules strictly.

1. HTML for all documents (with three narrow exceptions)

Use HTML for all plans, documents, and written artifacts — not markdown. HTML is chosen because it can carry semantic structure and metadata that markdown cannot: <meta> headers, lang, datetime on <time>, id anchors, data-* attributes when they earn their place, and tags that name what content is (<article>, <section>, <figure>, <dl>, <dfn>, <code>) instead of just how it looks.

Allowed Markdown files (do not convert these to HTML):

  • CLAUDE.md — required by Claude Code's filename lookup.
  • README.md — required by GitHub's filename lookup.
  • docs/whiteboard.md — user's low-friction scratchpad. Edit friction outweighs semantic structure here. See docs/decisions/0006-whiteboard-as-markdown.html.

No other file may be Markdown without a new ADR.

Use that expressiveness with restraint. More metadata is not better. Every attribute or tag should earn its place by making the document easier for a future reader (human or agent) to navigate or query. Guidelines:

  • Pick the tag that names the content. A list of decisions is a <dl> or <ol>, not a wall of <p>s. A version history is a series of <section>s with <time>.
  • Add <meta> only for facts a reader would otherwise have to infer (project, doc type, author, status). Skip generic SEO boilerplate — these docs are not served on the web.
  • Reach for id on anything that might be linked to. Skip class entirely (no styling).
  • Use data-* only when an agent would actually query it (e.g. data-status="done" on a phase). Don't invent attributes nobody reads.
  • No CSS, no JavaScript, no design. Content and structural metadata only.

The test: if removing an attribute or wrapper would not change how a future reader finds or interprets the content, leave it out.

2. Read the right doc set

The project moved to a per-phase spec + ADR architecture at v4 opening (2026-05-27). Always start at docs/README.html — it maps task type to the docs you need.

  • Current (v05+): docs/README.html (index), docs/roadmap.html (vision), docs/architecture.html (living system doc), docs/specs/vX.Y.Z-slug.html (per-phase specs), docs/decisions/NNNN-slug.html (ADRs), docs/reference/ (stable lookup).
  • Archived (shipped majors): docs/archive/vNN/. v01–v03 use the older plan/impl/history three-doc shape; v04+ keep their per-phase specs as-is, relocated here when the major ships. Frozen, read-only history — don't edit archived docs, but the archive itself grows by one folder per shipped major. See docs/decisions/0005-doc-architecture-spec-adr.html (the spec+ADR architecture) and docs/decisions/0014-archive-shipped-major-version-specs.html (the archive-on-ship policy).

Treat existing specs and roadmap entries as user-confirmed. Build directly from them; if something is not covered, confirm with the user before extending.

3. Minimal code

Write the simplest, clearest, most direct code that solves the problem. No abstractions beyond what the task requires. No clever patterns, no premature generalization. Three similar lines is better than a premature abstraction.

4. Document phases as specs; decisions as ADRs

For each new phase, write docs/specs/vX.Y.Z-slug.html following the convention in docs/README.html (Goal / Files / Verify / Notes).

For significant decisions — choices that constrain future work or that a future agent would otherwise re-debate — write a new ADR in docs/decisions/NNNN-slug.html using the Michael Nygard template (Context / Decision / Consequences). ADRs are immutable once accepted; supersede with a new ADR rather than editing.

Per-phase notes that are observations rather than load-bearing decisions go in the spec's Notes section. If a note in there later turns out to constrain future work, promote it to an ADR.

Update docs/architecture.html whenever the system shape changes (new component, new boundary, new storage key). Update docs/roadmap.html when the vision shifts.

5. Versioning — vX.Y.Z (manifest.json style)

Every commit must include a version number in the message using the format vX.Y.Z, identical to the manifest.json version field. The three parts decompose as:

  • X — major version. Increment when adding a new feature set or restructuring the project.
  • Y — planned phase within the major version. Each phase's first commit ends in .0 (e.g. v4.1.0, v4.2.0, v4.3.0).
  • Z — sub-commit within a phase. If a phase needs more than one commit, increment the last digit (v4.2.0 → v4.2.1 → v4.2.2). The next planned phase resets to .0 (e.g. v4.3.0).

The commit-message version and manifest.json's version are the same string (with or without the leading v). Bump manifest.json in the same commit that introduces the new version.

Some versions may be non-functional; that is expected and acceptable.

Historical note. Versions v01.xxx, v02.xxx, and v03.xxx used an earlier three-digit-suffix scheme (vXX.YZW). The vX.Y.Z rule above applies from v4 onward.
