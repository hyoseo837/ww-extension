ADR 0055 — Sign in from the sidebar credits field, via one OAuth flow centralized in the background worker

Context

A whiteboard feature: in the credit field, add login with UWaterloo if not logged in (owner, 2026-06-16). Today the sidebar header's credits chip (#ww-ext-credits) is simply hidden when signed out, and the only way to sign in is the options page — the empty-list guide points the user there ("Sign in … in Settings"). A signed-out user looking at the sidebar has no direct way to authenticate.

The sign-in itself is an Azure (Microsoft / UWaterloo, ADR 0036) OAuth flow through Supabase, run with chrome.identity.launchWebAuthFlow. That API is not available in content scripts — only in extension pages and the background service worker. So the flow currently lives inline in options.js; the sidebar (a content script) cannot call it directly.

Decision

  • Centralize the OAuth flow in the background worker as a { type: 'signIn' } message handler. It runs launchWebAuthFlow, parses the access/refresh tokens and the JWT email/sub, writes auth to chrome.storage.local, and returns { ok, email } | { ok:false, error }. Background.js already names "any future caller" as a design goal and reuses its existing decodeJwtPayload.
  • Both surfaces call the one handler. options.js is refactored to send the message instead of running its own copy of the flow — removing the duplicated OAuth code (and its now-unused SUPABASE_URL / decodeJwtPayload). The sidebar sends the same message.
  • Sidebar credits field shows a "Sign in" button when signed out. renderCreditsChip stops hiding the node; signed out it renders a compact "Sign in" chip-button that sends signIn. On success the background writes auth, and the existing storage.onChanged reactions take over: background refreshes the balance, the content script re-renders the chip (now the ⚡ balance) and the guide's step-1 checkmark. No new state plumbing.
  • Storage stays the single source of truth. No new auth state, no token handling in the content script — it only triggers the flow and reacts to the resulting auth write, exactly as the options page does.

Consequences

  • + A signed-out user can authenticate in one click from where they already are (the sidebar), not only via Settings.
  • + One OAuth implementation instead of two; the options page and sidebar can't drift, and a future caller (popup, welcome page) reuses it.
  • + No manifest change — identity is already granted and launchWebAuthFlow runs in the SW.
  • − The sign-in popup is launched from the background after a content-script message rather than directly in the click handler. launchWebAuthFlow(interactive:true) does not require a propagated user gesture, so this is fine; the options-page path keeps the same behaviour through the shared handler.
  • The empty-list guide's "in Settings" wording stays valid (Settings still signs in) — left unchanged to keep the diff tight.

Alternatives considered

  • Sidebar button just opens the options page (like the guide link) — rejected: that is a redirect, not "add login"; the feature asks for sign-in from the credits field itself.
  • Duplicate the OAuth flow into a content-script-reachable place — impossible (no chrome.identity in content scripts) and, even via a second copy, would duplicate the flow the project's minimal-code rule discourages.
  • Leave sign-in to Settings only — rejected: that is the status quo the feature is removing.
