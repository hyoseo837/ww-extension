ADR 0011 — uv as Python dependency manager for server/

Context

The backend in server/ needs a dependency manager that handles: a lockfile for reproducible builds, a virtual environment, fast resolution, and clean Docker integration. Candidates considered: uv (Astral), poetry, and pip-tools (requirements.in + pip-compile).

uv is Astral's Rust-based tool, ~10–100× faster than pip/poetry for resolution and install. Single binary handles project, lockfile, venv, and tool execution. De facto choice for new Python projects in 2026. Poetry is mature, popular, slower; familiar if you've packaged Python before. pip-tools is minimal but splits responsibilities across multiple tools (pip + pip-compile + venv).

For a Docker deploy on DigitalOcean App Platform, build speed matters (faster CI builds, faster local iteration). For a solo dev, fewer tools to learn matters.

Decision

Use uv for server/. Lockfile is server/uv.lock, committed. Dockerfile uses the official ghcr.io/astral-sh/uv:python3.12-bookworm-slim image for the build stage and copies the resulting .venv into a slim runtime stage.

Consequences

  • + Fast: uv sync typically finishes in seconds even for ~50 deps.
  • + Single tool covers lockfile, venv, tool execution (uv run), and Python version management.
  • + First-class Docker support via the published uv images and cache-mount patterns.
  • + Lockfile is committed; reproducible builds across local dev, CI, and production.
  • − Dependency on Astral's continued stewardship. Astral is well-funded and uv is broadly adopted, but it's a younger project than pip or poetry. Mitigation: pyproject.toml is standard PEP 621; if uv is ever abandoned, the project metadata moves to another tool with minimal change.
  • − Less familiar to Python developers who haven't kept up with the 2024–2026 tooling shift. Acceptable for a solo project.
