ADR 0033 — Pin the extension key for dev/prod ID parity

Context

Google sign-in runs through chrome.identity.launchWebAuthFlow with a Supabase redirect_to of chrome.identity.getRedirectURL(), which is https://<extension-id>.chromiumapp.org/. Supabase only redirects back to a redirect_to that is in its allowlist, so the extension ID — and therefore the redirect URL — must be stable and known.

v7.1.3 (0db088a) removed the dev key from manifest.json, reasoning that the Web Store assigns the published ID so the key was "dev-only." That was a mistake for auth: without a pinned key, the unpacked ID is derived from the load path and changes between machines/loads, breaking the allowlisted redirect URL. After approval, sign-in failed — Supabase refused the (now-changed) chromiumapp.org redirect.

Two facts settled the fix:

  • The git dev key (from the v7.1.1 manifest) hashes to ceobdeelponblelbcbbnojfjijheffpi — not the published ID. The Web Store generated its own key on publish, so the dev key never matched production.
  • The published public key, extracted from the live CRX, hashes to the store ID bichfckekdcnmkenflpmmehegggcfgdd. A public key shipped in every CRX is not a secret, so it can be committed.

Decision

Pin the published extension's public key in manifest.json as the key field. The unpacked dev build then loads under the same ID as the store build (bichfckekdcnmkenflpmmehegggcfgdd), so:

  • Dev and prod share one redirect URL — https://bichfckekdcnmkenflpmmehegggcfgdd.chromiumapp.org/ — the only entry that needs to be in Supabase's redirect allowlist.
  • The dev ID never drifts again across machines/reloads.

This reverses the v7.1.3 key removal. Re-uploading to the Web Store with this key present is safe: the store already uses this exact key for the item, so it is consistent rather than conflicting.

Operational dependency (not code): sign-in only works once https://bichfckekdcnmkenflpmmehegggcfgdd.chromiumapp.org/ is added to Supabase → Authentication → URL Configuration → Redirect URLs. Pinning the key removes the moving target; the allowlist entry is the gate.

Consequences

  • Easier: one stable redirect URL; dev and prod auth behave identically; no per-machine allowlist churn.
  • Constrains: the key must stay in the manifest; removing it again re-breaks the unpacked ID (see v7.1.3). Any future ID change (e.g. a republish under a new item) requires updating both the key and the Supabase allowlist.
  • Supersedes the v7.1.3 "drop dev key" change.
