ADR 0002 — Versioning vX.Y.Z mirrors manifest.json

Context

v01 through v03 used a three-digit suffix scheme: commit messages like v03.015, translated to manifest.json as XX.YZ.W = 3.0.15. The translation required a mental step every commit, and in practice the user's commits did not always match the documented decomposition.

Chrome's manifest.json version field uses dot-separated integers natively. There is no reason to maintain a separate commit-message format that requires translation.

Decision

From v4 onward, commit-message versions use the format vX.Y.Z — identical to manifest.json's version field (with or without the leading v).

  • X — major version. Bump on new feature set or restructure.
  • Y — planned phase within the major version. First commit of each phase ends in .0 (e.g. v4.1.0, v4.2.0).
  • Z — sub-commit within a phase. Follow-ups increment Z (v4.2.0 → v4.2.1). Next planned phase resets Z to 0.

manifest.json's version field must be bumped in the same commit that introduces the new version number.

Consequences

  • + No translation step. Commit version and manifest version are the same string.
  • + Git log is naturally Chrome-version-sortable.
  • + Phase boundaries visible in the version number (v4.2.0 vs v4.2.5).
  • − v01–v03 commits use the old scheme. Search across all-time history requires knowing both formats. Mitigated by the historical note in rules.html.
  • − Y is finite (Chrome accepts up to 65535 per component), so a single major version cannot have more than 65535 phases. Not a real constraint.
