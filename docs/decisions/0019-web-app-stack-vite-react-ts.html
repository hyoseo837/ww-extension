ADR 0019 — Web app stack: Vite + React + TypeScript SPA

Context

v6 moves account, profile/CV, match-criteria, and payment management off the extension's options page and onto a dedicated web app (see roadmap, v6 section). The driving reason is UI quality — the three-tab options page is cramped and the profile fields are barely usable. Everything that surface needs already lives server-side behind authenticated FastAPI endpoints (GET/PUT /profile, /credits/*), so the web app is a new client of an existing API, not a re-architecture.

The project's "minimal code" rule (ADR 0003) biases toward no framework. But the explicit goal here is a markedly better UI with real forms, validation, routing, and auth state — hand-rolling that in plain DOM would reinvent a framework badly. The relevant question is which stack reaches a good UI with the least incidental complexity for a solo maintainer, while integrating cleanly with Supabase auth and Stripe.

Decision

  • Build the web app as a Vite + React + TypeScript single-page application — static build artifacts, no app server, talking to the existing FastAPI backend over fetch with a Supabase session bearer token.
  • Auth via @supabase/supabase-js (Google OAuth, PKCE) in the browser; the backend already verifies Supabase JWTs against JWKS, so no backend auth change is required (only CORS — see ADR 0021 / ADR 0022).
  • TypeScript scope is the web app only. The existing extension stays JavaScript; a JS→TS extension migration is explicitly out of v6 and left as a separate future decision.
  • The app is built responsive from the start — account/profile management is a phone-friendly surface.

React over the considered alternatives (SvelteKit; plain TS + minimal templating): chosen for the largest ecosystem and first-class Supabase/Stripe support, and because it is the stack the maintainer is most familiar with — the deciding factor for a solo project. SvelteKit's smaller bundle and SSR were not worth the smaller ecosystem here; plain TS was rejected because the UI-quality goal would push it toward re-implementing framework primitives.

Consequences

  • + Reaches a good account/profile UI quickly, with mature libraries for forms, routing, and auth state.
  • + No backend rewrite — the SPA consumes the existing API; the only backend deltas are CORS, a Supabase redirect URL, and (later) small new read endpoints.
  • + A real web origin lets Stripe use a proper success_url, retiring the chrome-extension:// checkout-result shim for web-initiated purchases.
  • − Departs from ADR 0003's no-framework bias: a build step, a dependency tree, and a second frontend codebase to maintain alongside the JS extension. Judged worth it for the UI-quality goal; minimal-code still governs within the React code (no premature abstractions, no extra state libraries until a need is proven).
  • − Two frontend languages in the repo (JS extension, TS web app) until/unless the extension migrates.
  • − SPA (not SSR) means the public landing/intro page is client-rendered — acceptable, since SEO is a non-goal for a single-product extension companion.
