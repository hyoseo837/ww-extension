ADR 0004 — Backend lives in a separate repo

Context

v4 introduces monetization: user accounts, a credit ledger, and server-side Gemini calls. The choice is whether the backend code lives in this repo (monorepo, e.g. server/ alongside src/) or in a separate repository.

Monorepo pros: atomic client+server changes, single set of docs, easier for a solo developer to navigate.

Split pros: the extension is loaded unpacked or distributed via the Chrome Web Store — anything in this repo can be inspected by any installed user. The user wants to keep scoring prompts, tuning logic, and any pricing/business code out of the client bundle so they aren't visible to end users or competitors.

Decision

The backend lives in a separate repository (name TBD as of this ADR). The extension repo (this one) holds only the client. The client's view of the API contract is mirrored in docs/reference/api.html in this repo; the backend's repo holds the authoritative server-side schemas and endpoint implementations.

Consequences

  • + Proprietary scoring prompts and tuning logic never ship in the extension bundle.
  • + Each repo has a smaller agent context surface — faster orientation for agents working on either side.
  • + Independent deploy story for the server (no Chrome Web Store review cycle for backend changes).
  • − Client/server changes can no longer be atomic. API contract changes require a coordinated release. Mitigated by versioning the API and keeping the contract mirror in this repo current.
  • − Two repos to maintain. Slight overhead for a solo dev.
  • − Cross-repo cross-references in docs are weaker than intra-repo links. The contract mirror approach (this repo describes what the client expects; backend repo describes what it provides) keeps each repo self-contained for agents working within it.
