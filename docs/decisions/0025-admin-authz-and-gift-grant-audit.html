ADR 0025 — Admin authZ (env allowlist) + gift-grant audit columns

Context

v6.6 adds an operator console: inspect users and issue manual gift-credit grants. Two decisions need recording, because both constrain later work and a future agent would otherwise re-debate them.

(1) How to authorize admins. There is a single operator (the project owner) and no role system. Options ranged from a full roles/permissions table to a Supabase custom claim to a static env allowlist. A grant endpoint mutates balances, so the gate must be enforced server-side on the endpoint — hiding the UI is not enough.

(2) Where the gift-grant audit trail lives. The roadmap requires grants to ride the append-only ledger as a new entry kind with balance derivation unchanged, plus a who/what/when/why audit trail. kind='admin_grant' was already reserved in the ledger CHECK constraint (migration 0001) and already flows through history. The ledger row already carries what (delta) and when (created_at); it lacks who (the granting admin) and why (the reason). The ref column is unsuitable — it is single-purpose (Stripe event id / scan id) and overloading it with a who+why blob would be opaque.

Decision

  • AuthZ: static env allowlist. A new ADMIN_USER_IDS env var holds comma-separated Supabase user_ids. A FastAPI dependency require_admin runs the normal JWT verification (current_user) and then returns 403 unless the verified sub is in the allowlist. Every /admin/* endpoint — including the balance-mutating POST /admin/grant — depends on it. No roles table, no custom claims.
  • Gift grants reuse kind='admin_grant' (no schema change to the constraint, no new kind). Balance stays SUM(delta).
  • Audit trail: two nullable columns on the ledger (migration 0009): created_by uuid references auth.users(id) (the actor) and note text (the reason). Grant rows set both; all other rows leave them NULL. This keeps who/what/when/why on the one append-only row without a side table.

Consequences

  • + Minimal: a config string + one dependency + two nullable columns. No roles infrastructure for a one-operator product; fits ADR 0003.
  • + The mutating endpoint is locked server-side; the web route can be public because the data/actions are gated by the backend (403), not by hiding the UI.
  • + The audit columns are general-purpose — any future actor-attributed or annotated ledger entry (e.g. a future reversal or promo) can reuse created_by/note.
  • − Adding/removing an admin is a redeploy (env change), not a runtime action. Acceptable at this scale.
  • − created_by is not enforced to be an admin at the DB level (it is just an FK to a user). Integrity rests on only the admin-gated endpoint ever writing admin_grant rows. Accepted; the constraint would add little for a backend-only writer.
  • The web app learns "am I an admin?" only by calling an /admin/* endpoint and seeing 200 vs 403 — there is no separate admin claim in the session.
