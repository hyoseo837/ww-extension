ADR 0018 — Client-side deterministic hard-exclusion pre-filter

Context

v5.2 (ADR 0017) added the Excluded verdict, but the model produces it during a scan — so the user spends a credit to learn a posting was a hard no-go. v5 thread #4 (hard filters) wants to skip clearly excluded postings without spending a credit. Since the credit debit lives inside POST /scan, a credit-free skip must be decided before that call. Two questions follow: where the decision runs, and what is allowed to trigger it.

The candidate's structured match criteria (ADR 0013) include an excluded tier per criterion (locations, work modes, target term, term length, languages) — the candidate's own declared no-gos. WaterlooWorks exposes some posting facts as structured fields cheaply (e.g. the City column on the results table, and getPostingData JSON) without any Gemini call.

Decision

  • Runs client-side, before /scan. The extension checks each posting in the scan loop against the candidate's excluded-tier criteria; on a match it marks the posting Excluded locally and does not call /scan — no Gemini call, no credit. To know the criteria, the client fetches the profile once per scan batch via the existing GET /profile (no new endpoint).
  • Scope: the candidate's own excluded preferences only — matched against structured posting fields. Free-text work-authorization / citizenship / clearance detection is not pre-filtered here; it stays with the scan-time Excluded verdict (ADR 0017), which reads the full posting and is accurate.
  • Conservative matching — zero false-positive skips. Normalized (lower/trim), confident structured matches only (the posting's field equals or clearly contains an excluded token). Missing or ambiguous fields never trigger a skip — the posting falls through to a normal scan.
  • Reuses the Excluded verdict for display (ADR 0017). A pre-filtered Excluded carries no numeric score; the badge shows the verdict alone and the reason names the gate.
  • User-toggleable, default on. An options-page setting (hardFilterEnabled, default true) lets a user opt out — when off, no pre-filter runs and every posting scans normally (the candidate's excluded criteria are still weighed by the scan-time Excluded verdict).

Consequences

  • + Saves a credit on every posting the user already declared a no-go, with no model latency — the decision is instant and deterministic.
  • + Reuses the Excluded verdict and its existing badge / sort / save-filter handling (v5.2.4) — minimal new UI.
  • − Excluded now has two producers (server scan + client pre-filter); the verdict is no longer solely server-derived. The client must tolerate a null-score Excluded entry (badge without a number; validation/sort updated).
  • − The client now holds eligibility-filtering logic and fetches match_criteria — a small duplication of "what the user excluded" on the client. Acceptable: deterministic, non-proprietary eligibility is unlike the scoring logic kept server-side.
  • − Conservative matching under-filters: region/province/country-level location exclusions and any free-text gate won't pre-filter, so they still cost a scan (and are caught by the scan-time Excluded verdict). Accepted — zero false positives is worth more than maximal coverage.
  • Work-auth/citizenship pre-filtering (e.g. from getPostingPreScreening) remains possible future work if that data proves reliably parseable.
