ADR 0021 — Independent auth sessions for extension and web app (no handoff)

Context

With v6 the user has two surfaces that talk to the same backend as the same person: the extension (signs in via chrome.identity.launchWebAuthFlow, shipped v4.2, stores a Supabase session in chrome.storage) and the new web app (ADR 0019, signs in via @supabase/supabase-js in the browser). Both end up holding a Supabase session JWT for the same user_id and call the same authenticated FastAPI routes. The question is whether the two sessions should be shared/handed off, or kept independent.

A single-sign-on handoff (sign in once, propagate the session to the other surface across the chrome-extension:// boundary) is smoother UX but real plumbing: passing and refreshing tokens across that boundary, keeping two stores in sync, and more failure modes. The extension's launchWebAuthFlow sign-in already works and ships.

Decision

  • The extension and the web app keep independent sessions. Each signs in on its own and stores its own Supabase session; there is no token sharing or handoff between them.
  • Both are ordinary clients of the same backend: each sends Authorization: Bearer <jwt>, the backend resolves the same user_id from either, and per-user data (profile, credits, ledger) is identical regardless of which surface is used.
  • The surfaces connect by deep link, not by session: the extension gets a Manage account → link to ww-extension.hyoseo.dev, and links the user there for profile setup, credit purchase, and account management.
  • Profile editing lives only on the web app; the extension remains a profile reader (it fetches match_criteria via GET /profile for the client hard-filter pre-filter, ADR 0018) and a consumer of scan/credit endpoints.

Consequences

  • + No new cross-boundary session code; reuses the shipped extension sign-in and a stock Supabase browser session on the web. Fewer moving parts, fewer failure modes.
  • + The two surfaces can evolve independently — a change to web auth can't break extension scanning.
  • − The user signs in twice (once per surface). With Google OAuth this is one click each, but it is two distinct flows — the accepted cost of no handoff.
  • − Two sessions can drift (e.g. sign out on one, still signed in on the other). Acceptable: each surface independently handles 401 by prompting re-auth.
  • A future SSO handoff remains the upgrade path if the double sign-in proves annoying; it would supersede this ADR rather than be retrofitted silently.
