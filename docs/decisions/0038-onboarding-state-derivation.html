ADR 0038 — Derive onboarding progress without touching the extension

Context

v8.1 adds a new-user getting-started checklist on the web dashboard (v8.1.0 spec). The three steps are: (1) install the Chrome extension, (2) set up your profile, (3) run your first scan. For the checklist to be "smart" — checking steps off as they're done — the web app needs to know which steps a given user has completed.

Two of those are server state the web app already reads. The first — "is the extension installed?" — is not cheaply knowable from a web page. Reliable detection would mean either adding ww-extension.hyoseo.dev to the extension's content_scripts matches (so a content script can post an install marker into the page) or declaring externally_connectable and pinging the extension by ID. Both are manifest changes, and any manifest change ships only through a Chrome Web Store review cycle — heavyweight for v8, whose charter is maintenance & polish, not extension churn.

Decision

Derive all three step states on the web side only, from data the dashboard already fetches. No extension or backend change.

  • Step 2 — profile set up. true when GET /profile shows a non-empty profile — the same cvReady check the dashboard already computes (profile_json.summary or profile_json.experience or legacy cv_text).
  • Step 3 — first scan done. true when GET /credits/history contains any entry of kind scan_debit. A debit is written only by a real scan, so its presence is proof the user has scanned at least once.
  • Step 1 — extension installed. No direct signal, so infer it: hasScanned (step 3) implies the extension is installed, because a scan is impossible without it. Until the first scan, step 1 stays open and actionable (a Chrome Web Store button) and the user may also tick it off manually; that manual ack is persisted in localStorage (ww_onboarding_ext_installed), not the backend — it is a UI hint, not authoritative state.

The checklist card hides once the user is fully set up (profile ready and at least one scan), so it is a first-run aid that disappears on its own and never nags an established user.

Consequences

  • No Web Store review on the critical path. The whole feature is web-only (web/), shippable as a normal deploy.
  • No new endpoints. /profile and /credits/history are already fetched by the dashboard (Account.tsx); the checklist reuses them.
  • Step 1 is a soft signal. A user who installs the extension but never scans, and never ticks the box, sees step 1 as "not done" — acceptable, since the next action we want from them (scan) is exactly what would complete it. We accept a slightly loose step-1 signal in exchange for not touching the extension.
  • If precise install detection is wanted later, it can be layered on via a content-script marker on the web-app origin — a deliberate extension change with its own ADR, not a prerequisite here.
