ADR 0051 — Scan loop warms the cache before fanning out

Context

Scoring relies on Gemini's implicit context caching: every /scan sends an identical prefix — systemInstruction (SYSTEM_TEXT) plus <candidate_profile>{cv_text}</candidate_profile> — and only the job text varies (scoring/gemini.py). The backend bills the cheap cached rate on cachedContentTokenCount (billing/pricing.py); flash cached input is $0.075 vs $0.30/1M. Implicit caching is populated by the first request carrying a given prefix; later requests with the same prefix hit it.

The extension scans with a worker pool of SCAN_CONCURRENCY (v8.14 raises it 5 → 10 for throughput). A naive fan-out launches all N workers at once — so the first N scans of every batch race before any has written the cache, making them all cache misses. Raising concurrency makes this worse (10 cold scans, not 5), and a batch of ≤N jobs gets no cache benefit at all. The owner raised exactly this concern when asking to bump concurrency.

Decision

runScan primes the cache before fanning out: run the first scan alone to completion (populating the implicit cache for this user's prefix), then start the SCAN_CONCURRENCY-wide worker pool on the remaining ids. One cold scan per batch instead of SCAN_CONCURRENCY; the rest hit the warm cache. Mechanically the per-id handling (counters, halt/abort, progress) is factored out so both the warm-up scan and the pool share it.

Consequences

  • Every batch pays at most one full-price scan for the shared prefix instead of up to ten; small batches regain the cache discount they lost under a flat fan-out.
  • Slight upfront latency: the first scan's round-trip (~2–4s) runs at concurrency 1 before the pool spins up. Negligible against the 10× throughput on the bulk, and it is cheaper, not just faster.
  • Warm-up is best-effort. If the first scan is a non-halt failure (fetch/Gemini error) the cache may not be primed and the batch still fans out cold — acceptable and rare. A halt on the first scan (no credits / not signed in / profile unset) short-circuits the whole run before fan-out, unchanged from before.
  • This couples the client loop to an implementation detail of the provider (implicit prefix caching). If scoring ever moves to an explicit cached-content handle or a provider without prefix caching, the warm-up becomes a no-op worth removing — hence this ADR, so a future "simplify" doesn't delete it blind.
