ADR 0012 — Stripe Checkout + webhook-driven credit grants

Context

v4.4 made scoring spend credits server-side, but the only way to gain credits is the 100-credit signup bonus. v4.5 adds purchasing. The roadmap deferred the payments decision to v4.5 planning; this ADR records it.

Constraints from the existing system: the client is a Chrome extension (no server-rendered checkout page of our own, no place to safely hold card data); the credit ledger (v4.3) is append-only with a kind = 'purchase' value already reserved; the backend is stateless on auth (verifies Supabase JWTs) and owns all ledger writes via a service-role connection.

Two sub-decisions are in play, each with alternatives:

  1. How the user pays. Stripe Checkout (Stripe-hosted payment page; we create a session and redirect) handles PCI scope, card UI, 3DS, and receipts for us. Stripe Payment Intents + custom UI would mean building card entry inside the extension — more code, PCI exposure, no upside here. Stripe Payment Links (static dashboard-created URLs) can't carry the per-user metadata we need to attribute a payment to a Supabase user.
  2. How a paid purchase becomes credits. Stripe confirms payment out-of-band, so the grant must be driven by a webhook (checkout.session.completed), not the browser redirect (which the user can close or never reach). The webhook can fire more than once for the same payment, so the grant must be idempotent. Options for the idempotency key store: a dedicated stripe_event table (records every event), or a partial unique index on the existing ledger's ref column scoped to kind = 'purchase' (one grant row per Stripe event id). The latter reuses the exact pattern already used for the one-per-user signup bonus (v4.3, migration 0001).

Decision

Use Stripe Checkout in hosted mode. POST /credits/checkout (authenticated) creates a mode=payment session with dynamic price_data (no Stripe Dashboard Products — amounts live as in-code constants), stamps client_reference_id and metadata = {user_id, credits, package_id}, and returns the session URL for the extension to open in a new tab.

Credits are granted only by POST /webhooks/stripe, a Stripe-only endpoint that verifies the Stripe-Signature header against STRIPE_WEBHOOK_SECRET before any logic. On checkout.session.completed with payment_status = "paid", it inserts one kind = 'purchase' ledger row with ref = <Stripe event id>. Idempotency is a partial unique index on (ref) WHERE kind = 'purchase' plus ON CONFLICT DO NOTHING — no separate event table.

The granted credit amount is derived server-side from package_id against the backend's package table at session-creation time and carried only in the Stripe-held metadata. The client never sends a dollar or credit amount, and the webhook trusts only metadata it set itself.

Consequences

  • + Zero PCI scope and no card UI to build — Stripe hosts the payment page, 3DS, and receipts.
  • + The grant is decoupled from the browser redirect, so a user who closes the success tab still gets credited when the webhook lands.
  • + Idempotency reuses the ledger's existing append-only + partial-unique-index pattern; no new table, no new query surface. Replays and Stripe retries are safe.
  • + Amount-from-package_id means a tampered client request can't grant more credits than the package is worth.
  • − The ledger stores only the granting event (no row for sessions that are created but never paid). If full payment-funnel auditing is ever needed, add a stripe_event table later — this ADR does not preclude it.
  • − Stripe's hosted page needs an http(s) success_url; a chrome-extension:// URL is not allowed, so the backend must serve a small landing page (GET /credits/checkout/result).
  • − Balance updates lag the payment by the webhook round-trip (usually seconds). The extension refreshes the balance when the options tab regains focus rather than trusting the redirect.
  • − New vendor dependency (Stripe) and two new secrets to manage (STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET), in addition to Supabase and DigitalOcean.
