ADR 0020 — Web app in the monorepo at web/; excluded from the Web Store zip

Context

v6 adds a third codebase to the project: the React web app (ADR 0019). The repo already holds the extension at the root and the backend at server/ as a monorepo (ADR 0010). The question is where the web app lives and how it is kept out of the Chrome Web Store bundle, which ships only the allowlisted runtime files via package.sh.

The same forces that made the backend a monorepo subdirectory apply: a solo dev, cross-cutting phases (e.g. v6.2 adds a GET /credits/history endpoint and the web UI that renders it), and one authoritative API contract in docs/reference/api.html rather than mirrored copies.

Decision

  • The web app lives in a new top-level web/ directory in this monorepo, parallel to server/ (created at v6.1 bootstrap).
  • It is excluded from the Web Store zip by construction. package.sh is an allowlist that names only extension runtime files; anything not listed — including web/ — is excluded automatically. No package.sh change is required; the discipline is "never add web/ (or server/) to the allowlist," verified at any release touching packaging.
  • The web app deploys from web/ to its own host (ADR 0022), independent of the backend's DigitalOcean deploy. DO only rebuilds on server/ changes, so web/ commits don't trigger backend deploys, and vice versa.
  • The single monorepo version line (ADR 0002) continues to govern; web/package.json is not required to track manifest.json's version (it is not a released artifact in the vX.Y.Z sense), but the commit message and manifest.json still carry the phase version.

Consequences

  • + Cross-cutting v6 phases (new endpoint + its web UI) stay atomic single-repo commits.
  • + One doc tree and one API contract serve all three codebases; no contract drift.
  • + Backend and web deploys remain decoupled despite sharing a repo — different hosts, different change triggers.
  • − A third codebase grows the repo and the set of things a packaging mistake could leak. The allowlist model contains this: only explicitly named files ship, so the failure mode is "accidentally add to the allowlist," which the packaging-verify step at release catches.
  • − The root of the repo now mixes three concerns (extension files at root, server/, web/). Acceptable; the extension predates the others and moving it into its own subdirectory is a larger churn than its value.
