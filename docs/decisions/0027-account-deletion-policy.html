ADR 0027 — Account deletion: hard delete, Stripe as financial record

Status: accepted (2026-06-01). The owner confirmed hard delete: financial history lives in Stripe, so cascading away our derived mirror rows is acceptable. Implemented in the v6.9 phase. One coupled concern — a hard delete would otherwise let a user re-register for a fresh signup bonus — is handled by ADR 0029 (a retained one-way identity hash), so this ADR stays scoped to the data/financial-records question.

Context

v6.9 adds self-serve account deletion. All app tables FK auth.users(id) with ON DELETE CASCADE (user_profile, credit_ledger_entry, scan), so deleting the Supabase auth user removes every app row atomically. The one real decision: do we preserve the user's purchase/financial records in our own database? The credit ledger holds kind='purchase' rows; a hard delete cascades them away. Some businesses must retain transaction records for tax / accounting / chargeback windows.

Key fact: Stripe is the system-of-record for payments. Every checkout/charge/refund lives in Stripe, which retains it independently for its own compliance window. Our credit_ledger_entry is a derived balance (a sum of deltas), not the authoritative books — the purchase rows are a convenience mirror of what Stripe already holds.

Decision (proposed)

  • Hard delete. The backend deletes the Supabase auth user via the service-role admin API; FK cascade removes user_profile, credit_ledger_entry (including purchase rows), and scan. No in-DB financial record is preserved.
  • Stripe is the retained financial record. Because Stripe independently keeps all transactions, cascading away our mirror rows is acceptable — financial history remains reconstructable from Stripe. The Stripe customer object is left intact (or PII-minimized) so that history stays linkable; this is an implementation detail.
  • Self-serve + irreversible. The authenticated user deletes their own account behind a deliberate double-confirmation; admins may also delete via the admin surface. There is no soft-delete / undo.

Consequences

  • + Simple and complete: one admin call + the existing cascade fully satisfies erasure. No bespoke per-table teardown.
  • + Financial history is not lost — it persists in Stripe, the actual source of truth.
  • − Our DB can no longer answer "what did this (now-deleted) user buy?" — that query moves to the Stripe dashboard.
  • − Irreversible by design; a mistaken deletion can't be undone from our side. Mitigated by the confirm UX.
  • Alternative if rejected: if financials must stay in our DB, switch to anonymize-in-place — keep the auth.users row but scrub PII (email) and delete user_profile + CV, retaining de-identified ledger rows. More code and a fuzzier "deletion." Documented here so the trade-off is explicit; not chosen unless the owner requires in-DB retention.
