ADR 0010 — Monorepo: backend at server/, repo private

Supersedes ADR 0004.

Context

ADR 0004 split the backend into its own repo so that proprietary scoring prompts and pricing logic would not ship to end users via the publicly inspectable Chrome extension bundle. After scaffolding both repos (extension + WW-extension-backend) and trying the cross-repo workflow, two issues surfaced.

1. Workflow friction. Two Claude sessions, two doc trees, manual contract mirroring between two api.html files. For a solo dev, the overhead compounds on every cross-cutting phase — v4.4 (server-side scoring) and v4.5 (Stripe checkout ↔ purchase UI) each touch both halves and would require coordinated commits in two repos.

2. Visibility leak vector was misidentified. ADR 0004 framed the concern as "anything in this repo can be inspected by any installed user." That conflated two surfaces:

  • What end users see. Determined by what ships in dist/ via the Chrome Web Store, not by what's in the GitHub repo. A monorepo with backend in server/ and packaging that excludes server/ keeps backend code out of end-user installs just as effectively as a separate repo.
  • What GitHub visitors see. Determined by the GitHub repo's visibility setting. A private repo is invisible to anyone who's not a collaborator.

Making the ww-extension repo private closes the GitHub-visitor surface; the Chrome Web Store packaging discipline closes the end-user surface. Both surfaces can be closed in a monorepo, making the repo split unnecessary for visibility reasons.

The user's portfolio / public-code concern (a reason a hobbyist repo might stay public) is addressed by the Chrome Web Store listing serving as the public surface for the project.

Decision

  • Merge the backend into the ww-extension repo as a server/ subdirectory (created at v4.1 bootstrap).
  • ww-extension repo visibility changed to private on GitHub.
  • WW-extension-backend repo (and its sole commit v0.0.0) deleted.
  • Single version line for the monorepo: vX.Y.Z matches manifest.json per ADR 0002. server/pyproject.toml (created at v4.1) syncs to the same string on every release commit.
  • Packaging discipline: ./package.sh (or its replacement) MUST exclude server/ from the Web Store zip. This replaces the repo split as the mechanism keeping backend code out of end-user installs.

ADRs 0007, 0008, 0009 (DO App Platform, Supabase auth+DB, FastAPI) remain valid — they describe backend stack, not repo layout, and survive this supersede.

Consequences

  • + Single Claude session covers the entire v4 arc. One CLAUDE.md, one .claude/rules.html, one .claude/settings.json apply uniformly.
  • + API contract drift impossible by construction — one authoritative docs/reference/api.html, not two mirrors.
  • + Cross-cutting phases (v4.4 scoring, v4.5 Stripe + purchase UI) become atomic commits instead of coordinated two-repo releases.
  • + No more "extension vX.Y talks to backend vA.B" coordination — the whole project is at one version.
  • − Loss of public GitHub portfolio surface. Mitigated by Chrome Web Store listing as the public face of the project.
  • − Packaging discipline replaces repo split as the mechanism gating end-user visibility. If package.sh ever stops excluding server/ (or its env files), backend code or secrets could leak into the bundle. Web Store zip layout must be verified at every release that touches packaging.
  • − ADR 0004's "smaller agent context per repo" advantage is gone. In practice, agents load docs/specs selectively and rarely touch both halves' code in one read, so the cost is marginal.
  • − A future contributor who only wants to look at the backend cannot clone just the backend — they take the whole repo. Acceptable: no contributors yet.
