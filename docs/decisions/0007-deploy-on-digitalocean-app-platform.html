ADR 0007 — Deploy backend on DigitalOcean App Platform

Context

The backend (separate repo, see ADR 0004) needs a deployment target for v4. Candidates considered: Vercel (serverless functions), DigitalOcean App Platform, Fly.io, Render, Railway, a self-managed droplet.

Vercel forces Python into serverless functions: cold starts, per-request timeouts (10s Hobby / 60s Pro), no persistent connection pool, no background workers. The backend will handle Stripe webhooks, hold a Postgres connection pool, and may batch Gemini calls — all of which are friction on serverless.

Fly.io and Render fit the use case technically (Dockerfile deploy, persistent process, Postgres add-ons), but the user already has DO experience from a prior project. Reducing the number of new platforms to learn matters more than the marginal difference between providers for a solo dev shipping v4.

Decision

Deploy the backend on DigitalOcean App Platform as a Dockerized FastAPI service. Use App Platform's managed deploy from a Git push rather than a self-managed droplet. Database is hosted on Supabase (see ADR 0008), not DO Managed Postgres.

Consequences

  • + Persistent process matches FastAPI's shape — DB pool, Stripe webhook handlers, no cold-start tax on user-facing scans.
  • + Predictable monthly bill (~$5/mo for the smallest instance).
  • + Zero new platform to learn; faster path to a deployed v4 bootstrap.
  • + Dockerfile keeps the image portable — migrating to Fly.io or a droplet later is straightforward if the cost/perf shape changes.
  • − No scale-to-zero: pay for compute even at zero traffic. Acceptable at v4's hobby-tier scale.
  • − More expensive than Fly.io's free tier would be while v4 has no paying users.
  • − DB and app live on different vendors (Supabase + DO). Latency between API and DB depends on region selection — match regions deliberately.
