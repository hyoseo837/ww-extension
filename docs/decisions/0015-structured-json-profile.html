ADR 0015 — Structured JSON profile with cv_text fallback and a separate supplement column

Context

Through v4 and v5.0, the candidate profile is a single raw-text blob: user_profile.cv_text (text), produced by POST /profile/extract (Gemini multimodal → plain text) and sent to the scorer as the "Candidate Profile" context on every scan. Re-sending full resume prose each scan is token-heavy and hands the model an unstructured blob to reason over.

v5 thread #2 (spec v5.1.0) switches the profile to a structured JSON object (summary / education / experience / skills / projects / languages) and lets the user add supplementary experience/project entries that a one-page resume omits. This is foundational: the prompt rewrite (thread #3) needs structured profile fields to attribute score deltas to specific points ("AWS preferred, not in profile"). So the storage shape constrains future work, like the criteria shape did in ADR 0013.

Three sub-decisions are in play:

  1. How to store the extracted structured profile. Discrete typed columns/tables per field, or a single JSONB column validated in the app by Pydantic (as ADR 0013 chose for criteria).
  2. How existing cv_text users cut over. Replace cv_text (forcing a re-upload), backfill JSON by re-extracting every stored blob, or keep cv_text as a fallback and upgrade users on their next extract.
  3. Where user-authored supplementary entries live. Folded into the same JSON the extractor produces (risking being clobbered on re-extract), or kept separate.

Decision

Add profile_json jsonb not null default '{}' to user_profile — the extracted structured profile, owned and validated by a backend Pydantic model (the DB enforces only valid JSON, consistent with ADR 0013).

Keep cv_text as a fallback. The scan serializes profile_json when non-empty, else falls back to cv_text. No data migration: existing users keep working on their cv_text blob and upgrade to JSON naturally the next time they extract. The v5.1.0 migration only adds columns.

Store supplementary entries in a separate profile_supplement jsonb not null default '[]' column — an array of {kind, title, description} objects (kind = experience | project), written only by PUT /profile. POST /profile/extract overwrites profile_json but never touches profile_supplement, so re-uploading a PDF can't wipe hand-entered entries. At scan time both are serialized into the Candidate Profile block — "merged" for matching, separate at rest.

Consequences

  • + The scorer gets clean structured signal, and (expected) fewer input tokens per scan than full resume prose — measured at build time.
  • + Zero-migration cutover: cv_text stays a safety net for users who haven't re-extracted, and old rows read back as profile_json = {}.
  • + A separate supplement column makes "re-extraction preserves user-entered entries" a structural guarantee rather than careful read-merge-write code in the extract transaction.
  • + Consistent with ADR 0013 (JSONB owned by Pydantic) — same validation and evolution story; new profile fields need no migration.
  • − Three profile columns now (cv_text, profile_json, profile_supplement); cv_text becomes legacy once a user re-extracts. A later cleanup migration can drop it once adoption is complete — deferred, not now.
  • − The DB can't enforce the profile shape; the contract lives only in the app (same trade-off as ADR 0013).
  • − Structured extraction adds a responseSchema to the extract call; a malformed or empty extraction must fail without destroying the user's existing profile_json (handled in the extract flow).
