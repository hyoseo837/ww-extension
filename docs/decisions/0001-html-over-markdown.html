ADR 0001 — HTML over Markdown for project docs

Context

Most software projects use Markdown for internal docs. But Markdown cannot carry semantic metadata: no <meta> headers, no <time datetime>, no id anchors on arbitrary elements, no semantic tags that name what content is (versus how it looks).

This project is consumed primarily by AI coding agents (Claude Code) that benefit from structured metadata when deciding which docs to load and how to interpret them. Status tracking on specs and ADRs, version tags, dates, and explicit document types are all things a well-tagged HTML doc surfaces that a Markdown doc only implies.

The cost of HTML is ~30% more tokens than equivalent Markdown for the same prose content, due to closing tags and attributes.

Decision

Use HTML for all docs under docs/. Exception: CLAUDE.md and README.md at the project root, which must be Markdown because their consumers (Claude Code and GitHub) require it by filename.

Use HTML's expressiveness with restraint. Every tag and attribute must earn its place by helping a future reader (human or agent) navigate or query the doc. Skip generic SEO boilerplate. Use data-* only when something actually queries it. No CSS, no JavaScript, no design.

Consequences

  • + Specs and ADRs can carry status, dates, and version metadata in <meta> — greppable and machine-readable without parsing prose.
  • + Semantic tags (<section>, <dl>, <time>) name content types, giving agents structural cues beyond heading hierarchy.
  • + id anchors on any element enable precise cross-doc links.
  • − ~30% more tokens per doc than Markdown. Mitigated by writing concisely and keeping individual files small.
  • − Loses Markdown's ecosystem tooling (auto-rendering on GitHub, ADR templates, lint tools). Accepted tradeoff — these docs are not for GitHub browsing.
  • − Discipline required to avoid over-tagging. Easy to add metadata "just in case." Restraint rule in this ADR and the project rules file is the only guardrail.
