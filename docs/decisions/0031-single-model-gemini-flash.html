ADR 0031 — Single scoring model (Gemini Flash), no model switch

Context

The extension currently lets the user pick the Gemini model used for scoring. options.html has a Model tab with a <select id="model">; options.js persists the choice to chrome.storage.local; background.js (scoreJob) sends it on POST /scan, defaulting to gemini-2.5-flash. Server-side, ScanRequest.model is a required field validated against pricing.supported_models(), and it drives cost estimation and the actual Gemini call. Pro is offered as the higher-accuracy option at roughly 10× the per-scan cost of Flash (the options help text says as much).

In practice Flash is sufficient for the job-posting scoring task: the scan reads one posting against a structured profile and returns a 1–20 score with a per-aspect breakdown (ADR 0016/0017). Pro's extra capability is not worth ~10× the credit cost for this workload, and a user-facing model choice adds options-page surface, a pricing-explanation burden, and a support / "why did my scan cost more?" question — all friction on the path to a clean Web Store listing and a simple paid product.

The roadmap's v7.3 redesign already planned a minimal options page including a model switch, and carried a flag that multi-model isn't built server-side. The owner has now decided to drop the model-switch feature outright rather than carry it into the redesign.

Decision

Scoring standardizes on a single model, Gemini Flash (gemini-2.5-flash). There is no user-facing model selection. Concretely:

  • The options-page Model tab and its <select> / save logic are removed; the model storage key is no longer read or written by the client.
  • The client no longer sends a user-chosen model; scoring always uses Flash. (Whether the model field stays on the /scan request as a fixed server default, or is dropped entirely, is a v7.3 implementation detail — the key point is that no end user picks it.)
  • The default model remains an operator-side constant (the v4.7 tunable-constants pattern), so the single model can be changed in one place without shipping a client release — it is just not exposed in the UI.

This does not commit to removing Pro support from the backend immediately; it commits to Flash being the only model the product uses for scoring and to there being no UI to choose otherwise. Cleaning up Pro pricing / supported_models() can follow if it proves to be dead code.

Consequences

  • Easier: a smaller options page (closer to the v7.3 "auto-skip toggle + sign-in only" target); one predictable per-scan price; no "which model / why did it cost more" support load; one less thing to explain in the Web Store listing.
  • Harder / lost: users who would want maximum accuracy can't opt into Pro. Accepted — Flash is judged good enough for this task, and the cost ratio doesn't justify the option.
  • Constrains: v7.3 no longer builds a model-switch UI. The earlier "don't build the switch until multi-model ships server-side" flag is moot. Multi-model / non-Gemini providers stay an uncommitted "further out" idea, now explicitly not on the scoring path unless a future ADR reopens it.
  • Supersedes the v7.3 roadmap line that listed a model switch in the minimal options page.
