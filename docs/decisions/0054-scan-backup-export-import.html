ADR 0054 — Scan backup: export/import as plain JSON, merge-with-warning, all boards, schema-gated

Context

Scores live only in chrome.storage.local (ww_scores + ww_posting_ids), per browser profile — there is no cross-device sync and no backup. The owner wants to move a scored set between devices and keep a backup (whiteboard, 2026-06-16). The data is small structured text: a map of posting id → {score, verdict, reason, breakdown, title, org, board, feedback}.

Decision

  • Plain JSON file, not a zip. The extension has no build step and vendors no libraries (ADR 0026); a zip would mean a bundled archive lib for a payload that is a few KB of text. Export writes one .json; import reads one. File shape: 
    {
  "app": "ww-extension",
  "schema": 2,                 // SCORING_SCHEMA_VERSION at export time
  "exportedAt": "2026-06-16T...Z",
  "scores": { "<postingId>": { score, verdict, ... board }, ... },
  "postingIds": ["<id>", ...]
}
    Download is a Blob + <a download> click in the content script (no downloads permission); import is a hidden <input type="file"> read with file.text().
  • Export includes all boards. Entries are already board-tagged (entry.board, v8.7.1), and the scores map holds both Full-Cycle and Direct. A backup wants everything; the per-board filtering stays a view concern, not an export one.
  • Import merges, behind a warning. Imported entries are merged into the live scores map; on a posting-id collision the imported entry wins. Because that can overwrite scores already in the sidebar, import is gated by a confirm dialog that says so plainly ("Merge N jobs? Scores for postings in both will be replaced by the file's — you can lose current scores."). Owner's call: merge is the useful default for combining devices, and the warning covers the data-loss risk. (Replace-all was the alternative; rejected.)
  • Schema-gated. Import refuses a file whose schema ≠ the current SCORING_SCHEMA_VERSION — the same guard loadScores uses so score scales never mix (ADR 0016). A mismatch shows a message, not a silent merge. A malformed / non-ww file is rejected the same way.
  • Lives in the sidebar (content script), purely local. No server involvement — these are the user's local scores. Doing it in the content script (not the options page) means a merge live-updates the open tab: re-render the list, re-inject row badges (injectRowScores), saveScores.

Consequences

  • + Cross-device move and backup with one file and zero new dependencies or permissions.
  • + Board tags survive the round-trip, so a merged set still filters correctly per board.
  • − Merge can overwrite current scores on id collision — mitigated by the explicit warning, not prevented.
  • − The file is plaintext (no encryption). Accepted: it holds only the job scores/titles the user already sees, no credentials or account data.
  • A file exported under an older score scale is rejected by the schema gate rather than mixed in — correct by construction.

Alternatives considered

  • Zip archive — rejected: a vendored archive lib and build-step pressure (against ADR 0026) for a negligible size win on a few-KB text payload.
  • Replace-all on import — rejected by the owner in favour of merge; the warning makes the collision behaviour explicit.
  • Export/import on the options page — rejected: the sidebar sits with the scores and can live-update the open tab on merge; the options page could not without a reload.
  • Cloud sync via the backend — out of scope: scores are deliberately local (the server stores per-scan billing rows, not the user's curated board). A file keeps it simple and offline.
