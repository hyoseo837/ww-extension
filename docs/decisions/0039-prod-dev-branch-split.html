ADR 0039 — Split production (master) and development (dev) branches

Context

Until now the repository had a single branch, master, and every per-phase vX.Y.Z commit landed on it directly. That was fine pre-launch, but two of the three deliverables now auto-deploy from master:

  • web/ — Vercel builds and publishes its production branch on every push (ww-extension.hyoseo.dev).
  • server/ — DigitalOcean App Platform redeploys the FastAPI backend on every push to its tracked branch.
  • ext/ — unaffected by branching; the Web Store only receives what package.sh zips and the user uploads manually.

With the product live (extension approved 2026-06-04, web app and backend serving real accounts and credits), pushing an in-progress phase commit to master ships it to production users immediately. Development needs somewhere to accumulate commits that is not a deploy trigger.

Decision

  • master is production. It stays the branch Vercel and DO App Platform track. Pushing it is a deliberate deploy action, not a side effect of saving work.
  • dev is the long-lived development branch, created from master at v8.2.0. All per-phase vX.Y.Z commits land on dev; the per-phase commit discipline (ADR 0002) is unchanged, only the branch moves.
  • Release = merge dev into master and push, once a version (or batch of phases) is verified. Prefer a plain merge; no rebasing of pushed history (consistent with the user's no-force-push preference).
  • Short-lived topic branches off dev are allowed but not required — for a solo project, committing phases directly on dev is the default.

Consequences

  • Production deploys become intentional and batched; half-done phases can be committed and pushed (to dev) without touching users.
  • Vercel builds free preview deployments for pushes to dev, giving a staging URL for the web app at no cost.
  • The database does not branch. Both branches point at the same Supabase instance, so schema migrations applied while developing on dev affect production data immediately. Branch discipline protects code paths, not the schema — migrations must stay backward-compatible with whatever master is running.
  • The Vercel production-branch setting and the DO App Platform branch setting live in their dashboards, not in the repo; both must be confirmed pinned to master (and Vercel preview deploys of dev must not be treated as production).
  • Agents must check which branch they are on before committing; committing phase work straight to master is now a process error. CLAUDE.md records the rule.

Alternatives considered

  • Keep single-branch master — status quo; rejected because every push is a production deploy of web and server.
  • Full git-flow (develop/release/hotfix branches) — rejected as ceremony a solo project does not need; two branches give the entire benefit.
  • Decouple deploys instead (deploy by tag or manual promote in Vercel/DO) — viable, but moves the safety mechanism into two third-party dashboards instead of one visible repo convention; can be layered on later without superseding this ADR.
