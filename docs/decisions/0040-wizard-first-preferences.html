ADR 0040 — Wizard-first preference capture; jsonb completion flag; schema unchanged

Context

The Match preferences page (web/src/pages/Preferences.tsx, v6) exposes the raw scoring model: five identical criterion rows, an unlabeled weight select (must / strong / nice-to-have), and four value tiers (preferred / acceptable / avoid / excluded) hidden behind "More options". The owner reports it is hard to understand and dislikes the structure (whiteboard, 2026-06-06; scoped 2026-06-10). Nothing routes a new user through it, so many users likely scan with empty criteria and get generic scores — the product's quality depends on this data existing.

Decision

  • Two surfaces, one schema. A guided wizard (/preferences/setup) is the first-run capture path — plain-language, one question per step. The preferences page (/preferences) is rebuilt as the simplified durable editor. Both read/write the existing match_criteria jsonb.
  • The wizard is required. A signed-in user who has not completed setup is redirected from the app shell to /preferences/setup (web-side gate). Users with pre-existing criteria (work authorization or any preferred values) are grandfathered as set up. No server-side scan blocking — the extension keeps working regardless; the gate funnels, it does not brick.
  • Completion is an explicit flag in the jsonb: match_criteria.wizard_completed_at (ISO timestamp). Because PUT /profile validates with Pydantic (which drops unknown keys), the field is added to the server's MatchCriteria model — a one-line change, no migration (jsonb column absorbs it).
  • The scoring schema does not change. Weights and tiers keep their stored names; only the UI vocabulary is simplified — weight reads as Nice to have / Important / Must-have, tiers as Ideal (preferred), Would rather not (avoid), Never (excluded). The acceptable tier is dropped from the UI but preserved in data. Scorer prompt and extension are untouched.

Consequences

  • Every new user produces non-empty criteria before their first scan, which is the cheapest available scoring-quality win.
  • The gate lives web-side (consistent with ADR 0038's derive-don't-store approach to onboarding state, except for the one explicit completion flag). A user who never opens the web app after sign-up is not forced through it — accepted; sign-up itself happens on the web.
  • Wizard answers that don't fit the structured criteria (free-form dealbreakers, context) land in the existing preferences notes field, which the scorer already weighs.
  • Dropping acceptable from the UI means that tier can no longer be edited, only carried; if it proves dead weight, removing it from the schema is a future server-side cleanup.

Alternatives considered

  • Freeform description + LLM extraction — lowest friction, but adds an LLM call and a review/correct loop; owner chose the deterministic wizard + page pair instead.
  • Simplified page only (no wizard) — fixes comprehension but not the empty-criteria problem; nothing would still route new users through it.
  • Server-enforced gate (refuse POST /scan without criteria) — strongest guarantee, but breaks scanning for existing users and couples scoring availability to web onboarding. Rejected; can be revisited if web-side funnelling proves leaky.
  • localStorage completion flag — no server change, but per-browser: the wizard would re-trigger on every new device. Rejected in favour of the jsonb field.
