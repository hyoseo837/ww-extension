ADR 0029 — Suppress repeat signup bonuses after account deletion

Status: accepted (2026-06-01). Companion to ADR 0027 (hard delete) and part of the v6.9 phase.

Context

The 100-credit signup bonus is granted by a database trigger (grant_signup_bonus_trigger, migration 0001) that fires on every auth.users insert. The "one bonus per user, ever" unique index is keyed on user_id — the auth row's id, which is brand new on each signup. So the guarantee is really "once per auth row," not "once per person."

ADR 0027 chose hard delete: deletion removes the auth.users row and cascades the ledger (including the signup-bonus row). That reopens the farming path: delete → sign in again with the same Google account → new auth.users row → trigger grants another 100 credits. With the bonus worth ~200 Flash scans (pricing.py), this is a cheap, repeatable abuse. Erasure and anti-farming are therefore coupled and must be decided together.

Decision

  • Keep a minimal suppression record. On deletion, the backend writes one row to a new signup_bonus_block table containing only a one-way SHA-256 hash of the lowercased email (no plaintext email, no other PII) — written before the auth user is deleted, while the email is still available from the verified JWT.
  • The trigger checks it. grant_signup_bonus() is amended (migration 0010) to skip the grant when sha256(lower(new.email)) is present in signup_bonus_block. Both sides compute the hash with the same SQL expression (encode(digest(lower(...),'sha256'),'hex'), pgcrypto), so they always agree. Everyone else still gets the bonus exactly once.
  • This is a deliberate, disclosed retention. The hash is the one piece of data that survives a hard delete. It is disclosed in the privacy policy as a fraud-prevention measure (legitimate interest); it cannot be reversed to an email and is not used for any other purpose.

Consequences

  • + Signup bonus becomes once-per-person regardless of delete/re-register, closing the farming hole while preserving real erasure of all personal data.
  • + Tiny surface: one table, one trigger tweak, one insert in the delete path. No change to the normal signup flow.
  • − We retain a permanent fingerprint (hash) of every deleted account's email. It is one-way and disclosed, but it is a retention — a stricter "delete everything, no trace" reading would reject it. Accepted as a proportionate fraud-prevention trade-off for a credit-granting product.
  • − Hash keys on email, not the Google subject id. If a user deletes, then changes their Google account's email and re-registers, they'd get the bonus again. Acceptable: that's a high- effort edge, and the stable email covers the common case. Could later switch to the OAuth sub if needed.
  • Alternative considered: anonymize-in-place (keep a scrubbed auth.users row so a returning login maps to the same id and gets no new bonus). Rejected — it makes "deletion" fuzzier and is more code than a single hash row. See ADR 0027's alternative.
