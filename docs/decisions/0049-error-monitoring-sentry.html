ADR 0049 — Error monitoring via Sentry's free tier, env-gated and errors-only

Context

The 2026-06-11 audit (#9) found failures exist only in DigitalOcean's log stream and web-app errors vanish entirely — with marketing about to bring users (ADR 0042), breakage would be discovered by email, not by the owner. ADR 0046 scheduled error monitoring for v8.10 but gated the tool choice on an owner decision, because it adds the project's first external observability service and a new data flow (error payloads leave our infrastructure). Candidates: Sentry (hosted free tier), GlitchTip (open-source Sentry-compatible), or deferring.

Decision

Use Sentry's hosted free tier (owner decision, 2026-06-11): sentry-sdk[fastapi] on the server, @sentry/react on the web app. Both are errors-only (no performance tracing, no session replay) and env-gated — initialized only when SENTRY_DSN / VITE_SENTRY_DSN is set, with send_default_pii=False server-side, so local dev, CI, and any clone of the public repo run with Sentry fully inert.

Consequences

  • Server exceptions and web-app crashes become visible with stack traces, releases tagged by version, and email alerts — breakage is heard about before users write in.
  • New external account and data flow: error payloads (stack traces, request metadata — not request bodies, not PII fields) go to Sentry's cloud. The privacy policy's subprocessor story should mention this at the next legal-page touch.
  • Free-tier quota (~5k events/month) is far above expected volume; if an error storm ever burns it, events drop — monitoring degrades, the product does not.
  • Errors-only keeps the integration one init() per side; choosing tracing/replay later is a new decision, not creep into this one.
  • GlitchTip remains the escape hatch: it speaks the Sentry SDK protocol, so switching is a DSN swap, not a code change.
