ADR 0044 — Scan feedback loop: 👍/👎 per scored posting, keyed to the scan row

Context

ADR 0042 froze feature work and parked the feedback loop until the December 2026 checkpoint — but named it the first candidate to un-park. The owner has decided to un-park it now, ahead of the September 2026 recruiting wave: a feedback collector only pays off if it is already in place when marketing brings users, and the wave is the one shot at organic volume before the checkpoint. This amends ADR 0042's parking list, not its direction — v8 stays the final major; this ships as v8.6.

The value identified when the feature was shaped (whiteboard, 2026-06-10) is a growing gold set of (profile, criteria, posting, score, user verdict) tuples to calibrate prompt changes against — including validating v8.5's phrasing-inferred importance. The loop closes by hand: collect → review in admin → tune prompt → re-test.

Decision

  • One feedback per scan, keyed to the scan row. New table public.scan_feedback with scan_id uuid primary key references scan(id) on delete cascade, user_id, rating ('up'/'down'), optional one-line comment, optional description_text, timestamps. Re-submitting upserts — latest verdict wins. The scan row already holds the stored result, posting id, title/org, and model, so feedback adds nothing redundant.
  • Posting description is captured only on 👎, at feedback time. The scan row deliberately doesn't store descriptions (row bloat); instead the extension re-fetches the posting overview — the same free WW fetch a scan uses — and sends the trimmed text with a 👎. Thumbs-up needs no debugging context and stores none.
  • Backend is the sole writer (same posture as ADR 0011's user_profile hardening): RLS enables select-own only; writes go through POST /scan/feedback, which verifies the scan row belongs to the caller, is kind='scan', and status='success'.
  • No credit interaction. Feedback is free, earns nothing, and refunds nothing — it must stay a zero-stakes signal, not a refund channel users learn to farm.
  • Review surface is the existing admin page: a recent-feedback list via GET /admin/feedback. No automation — per the shaping, per-user score adjustment and implicit signals (save/apply tracking) are explicitly out of scope.

Consequences

  • The extension must learn its scan_ids: the background scoreJob returns the generated UUID and the content script caches it per posting. Cached entries from before v8.6 have no scan_id — those cards simply don't offer feedback buttons (acceptable: real collection starts with new scans).
  • Hard-deleting an account cascades through scan → scan_feedback, so ADR 0027's deletion guarantee holds without new code. The privacy policy's data inventory gains one row (feedback + optional posting text).
  • The gold set lives in Postgres and is reviewed by hand; if volume ever justifies tooling, that's a future decision.

Alternatives considered

  • Key by (user, posting) — rejected: a posting can be scanned again after profile changes; keying to the scan row pins feedback to the exact (profile, criteria, score) that produced it, which is the whole point of the gold set.
  • Store the description on every scan — rejected (row bloat for data needed only on the rare 👎).
  • Wait for December as ADR 0042 planned — rejected: the collector must precede the users it collects from.
