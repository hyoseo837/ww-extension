ADR 0053 — Single-job scan by posting ID: sidebar input now (reuses the batch path), detail-page button deferred pending a DOM capture

Context

A whiteboard feature: scan a job one by one by entering a posting ID. The owner's intent (confirmed 2026-06-16) is cost-conscious — score one specific posting without spending credits on the whole table — and the requested surfaces are both a posting-ID input in the extension sidebar and a "Scan this job" button on an individual posting's detail view.

Two facts from the code shape the decision. (1) The extension's whole content script — sidebar, the page-bridge, and the session-specific WaterlooWorks action tokens (selectAll, getPostingOverview) — only exists on the job-table page (jobs.htm, gated on the table by waitForTable). The posting fetch (fetchOverview) scrapes those tokens from the page's inline scripts and POSTs to location.pathname; it is table-page-bound. (2) Bulk scan already scores off-page postings: selectAll returns every posting id across all pages and runScan scores ids that have no visible table row, with the title falling back to the fetched heading or #id (v8.14). So scoring an arbitrary id is the exact path bulk scan already exercises.

The detail view is different. WaterlooWorks' posting-detail DOM and URL are not documented in docs/reference/ww-dom*.html and no capture of that view is checked into the repo. The project rule is to build WW integration against verified captures, never guesses (ww-dom reference; the v8.8.4 column-order bug is the cautionary tale).

Decision

  • Ship the sidebar posting-ID input first (v8.16.1). A small input + button under "Scan All Jobs": type a numeric id → confirm the 1-credit cost → runScan([id]). It reuses the batch machinery verbatim — a single id is just a one-element batch, and off-page fetch/score already works. This alone fully serves the "scan one specific posting cheaply" goal.
  • Already-scored id → reveal, don't re-charge. If the entered id is already in scores, show its score/verdict in the status line and scroll to its row (best-effort) rather than spending credits again. Cost-consciousness is the whole point of the feature, and a re-scan path already exists (delete the card, or the future refresh idea).
  • Defer the detail-page "Scan this job" button (v8.16.2) until a posting-detail capture exists. It needs the content script to run on the detail view and a verified way to read the open posting's id and reach the fetch tokens. Without a saved snapshot that is a guess, so it waits on the owner providing one — exactly how exampleWW.html / ww-dom-direct-full.html seeded the existing DOM reference.
  • No backend or server change. The single scan hits the same POST /scan with the same per-scan debit; the batch-grouping batchId is still sent (a batch of one).

Consequences

  • + The core value (scan one posting cheaply, even one not in the current list / on the other board) ships immediately with near-zero new surface area — it is the audited batch path with a one-element list.
  • + No new WW-DOM dependency for the shipped part, so nothing new can break when WaterlooWorks changes its markup.
  • − The detail-page button — the more discoverable of the two surfaces — does not ship in this phase. Accepted: typing an id covers the use case, and guessing the detail DOM would likely be wrong and churn.
  • An invalid / nonexistent id flows through the existing failure path (fetch error → counted as a failure, offered for retry); no special handling beyond digit sanitisation.

Alternatives considered

  • Build the detail-page button now against best-guess DOM — rejected: violates the verified-capture rule and risks the v8.8.4-class breakage; better to wait for a snapshot.
  • A separate single-scan code path (own fetch, own progress) — rejected: runScan([id]) already does it, including the warm-up, refund-on-failure, and badge injection. A second path would duplicate audited logic.
  • Re-scan an already-scored id by default — rejected for this cost-conscious feature; reveal the existing score instead. On-demand refresh stays a separate whiteboard idea.
