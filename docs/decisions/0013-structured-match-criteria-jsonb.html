ADR 0013 — Structured match criteria as a JSONB column

Context

Through v4, a user's match preferences are a single free-form prose field: user_profile.preferences (text), synced from the options page and prepended to the Gemini prompt by build_job_part() as "Candidate Preferences". v5.0.0 (spec) replaces that single textarea with structured fields — work authorization, preferred locations, target term + length, work mode, languages — and demotes the prose to an "additional notes" field. The biggest motivation is a reliable work-authorization signal for international students, which today is lost in prose.

This is foundational: hard filters (v5 thread #4) will auto-Skip postings that exclude the user (e.g. citizenship-required) by reading work authorization, and the exploratory external-site direction may also read and write criteria. So the storage shape is a decision that constrains future work, not a per-phase detail.

Two sub-decisions are in play:

  1. How to store the structured criteria. Discrete typed columns (one column per field) are directly queryable and Postgres-checkable, but every new or changed field is a migration, and multi-value fields (locations, languages, work modes) need arrays or join tables. A single JSONB column holds the whole evolving object, validated in the app by Pydantic, and is still queryable (match_criteria->>'work_authorization') and indexable if a hard filter ever needs it.
  2. What to do with the existing preferences text. Either rename/migrate it into a new notes column, or keep the column as-is and re-purpose it as the "additional notes" field. The data is identical in both cases — only the label and the prompt framing change.

Decision

Store the structured criteria as one match_criteria JSONB column on user_profile (not null default '{}'). The object shape is owned and validated by a Pydantic model on the backend — the database enforces only that it is valid JSON. work_authorization is a closed categorical enum (citizen | pr | international | other); the remaining fields are scalars or string arrays (see the spec for the full shape).

Keep the existing preferences text column and re-purpose it unchanged as the "additional notes" field. No data migration: every existing user's prose simply becomes their notes. The v5.0.0 migration only add column … match_criteria.

build_job_part() serializes the populated criteria into a short deterministic labelled block ahead of the notes. The richer prompt work (co-op framing, calibration anchors, few-shot) stays a separate v5 thread — this ADR covers storage and a faithful pass into the existing prompt, not the prompt rewrite.

Consequences

  • + The criteria object can grow (new fields, changed options) without a schema migration — only the Pydantic model and the UI change. Good fit for a set still being discovered.
  • + Multi-value fields (locations, languages, work modes) are natural JSON arrays — no array columns or join tables.
  • + Zero data migration for existing users; the re-purposed preferences column keeps their prose as notes, and old rows read back as match_criteria = {}.
  • + Hard filters (#4) can still key off work authorization via a JSONB expression, and a ->>'work_authorization' expression index can be added later if needed.
  • − The database can't enforce the criteria shape or the work-auth enum; that contract lives only in the app. A bad writer outside the API could store a malformed object. Acceptable — all writes go through the authenticated PUT /profile.
  • − Querying/aggregating individual criteria is less ergonomic than typed columns (JSON operators, casts). The product doesn't analytically query criteria today; if that changes, promote hot fields (likely work_authorization) to a generated column.
  • − Keeping the column name preferences while its meaning narrows to "notes" is a slight naming drift; the spec and data-model reference note the mapping so it isn't surprising.
