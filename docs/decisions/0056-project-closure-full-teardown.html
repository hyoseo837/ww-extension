ADR 0056 — Close the project: full infrastructure teardown; the repo becomes the artifact

Supersedes ADR 0042 (portfolio flagship; December 2026 checkpoint).

Context

ADR 0042 (2026-06-10) froze feature work and bet the remaining upside on distribution: get in front of UWaterloo co-op students during the September 2026 recruiting wave, then judge the product on real adoption data at a December 2026 checkpoint. Everything since (v8.6 → v8.18) has been maintenance and polish against that plan.

Two things changed by 2026-07-26. The owner's co-op term ended, which removes both the daily contact with the user base the marketing plan depended on and the owner's own use of the product. And the user count is still zero — the same number ADR 0042 was written to fix, with no organic signal in the seven weeks since.

Against that, the deployment bills continuously. ADR 0007 accepted "no scale-to-zero: pay for compute even at zero traffic" as fine at hobby scale; at zero users it is the entire cost of the project, ~$5/mo, and reaching the December checkpoint would spend roughly $25 more to run an experiment whose input — owner-driven marketing to a cohort the owner has left — is no longer available. Supabase, Vercel, Stripe, Gemini, and Sentry all sit at $0 on free or usage-based tiers and contribute nothing to the bill.

Decision

  • Close the project. Tear down all hosted infrastructure — not just the billed component. The owner chose a clean full stop over keeping the $0 tiers alive as a live portfolio link, on the grounds that a half-live service (browsable web app, dead API) misrepresents the product to anyone who clicks through.
  • Teardown covers: the DigitalOcean App Platform app (the only paid component), the Supabase project (auth + Postgres), the Vercel deployment of web/, the Stripe account's live product and webhook, the Sentry project, and the ww-extension.hyoseo.dev DNS records.
  • Unpublish the Chrome Web Store listing. The extension (approved as 7.1.1 on 2026-06-04) is non-functional without the backend — sign-in and scanning both fail. Leaving it installable would hand new installers a broken product. The developer account and the approval history are retained, so republishing later does not start from zero.
  • Delete user data with the Supabase project, rather than retaining it against a possible reopening. This is the behaviour ADR 0027 and the published privacy policy promise: data exists to serve the account, and the service is ending. A final database export is taken first and kept offline by the owner, for the ledger record only.
  • Settle money before Stripe goes away. Any unspent purchased credit balance is refunded per ADR 0028 ahead of deactivation. Stripe retains its own transaction records independently, so the financial trail survives the teardown.
  • The repository is the artifact. The portfolio value ADR 0042 identified — a complete, shipped, documented, revenue-capable system — now lives in the code, the 56 ADRs, the phase specs, the screenshots, and the walkthrough video, none of which depend on anything being deployed.
  • No further versions. v8.19.0 is the final release. The dev → master split (ADR 0039) is retained but inert once master has nothing to auto-deploy to.

Consequences

  • + Recurring cost goes to $0. The teardown is complete rather than partial, so no forgotten resource resumes billing later — the common failure mode of "just downgrade it for now".
  • + Nobody encounters a broken product. Unpublishing ahead of the backend teardown means there is no window in which the store offers an extension whose API is already gone.
  • + Deleting user data at shutdown honours the privacy policy instead of leaving personal data (UWaterloo emails, extracted CV text) sitting in an unmonitored project indefinitely.
  • − The live demo is gone. README and store links go dead, and the portfolio story becomes "here is the repo and the video" rather than "here is the running product". Accepted deliberately: the owner judged a dead-API web app worse than an honest archive.
  • − Reopening is a rebuild, not a restart. server/ stays portable — the Dockerfile redeploys and migrations/ recreates the schema (ADR 0007 anticipated exactly this) — but it needs a fresh Supabase project, a fresh key set, new Stripe products, and a new Web Store review. Days, not minutes.
  • The whiteboard's parked ideas (subscription / term pass, cover-letter generation, the detail-page scan button) and the roadmap's "Further out" section are closed unbuilt. They stay in the docs as a record of what was considered, not as a backlog.
  • The scraping-fragility risk becomes moot: WaterlooWorks DOM changes no longer break anything that runs.

Alternatives considered

  • Destroy the DO app only, keep the $0 tiers — the cheapest option that preserves a live URL, and it stops 100% of the bill, since DO is the only paid component. Rejected by the owner: the web app without its API still renders sign-in, credit, and scan surfaces that all fail on click, which reads worse to a visitor than no site at all.
  • Replace the web app with a static "discontinued" page — keeps a $0 live link that is honest about its state. Rejected as ongoing surface to maintain for a project being closed; the GitHub repo and the walkthrough video serve the same purpose without a deployment.
  • Hold to ADR 0042's December checkpoint — rejected: the checkpoint tests a marketing push the owner is no longer positioned to run, so it would spend five more months of hosting to measure nothing.
  • Retain user data and pause the project instead of deleting it — rejected: contradicts the published privacy policy and ADR 0027, and leaves personal data in an unwatched project.
