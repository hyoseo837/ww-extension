ADR 0045 — Secret-scanning alert on captured WW page is a false positive; keep pushed history

Context

v8.7.0 added docs/reference/ww-dom-direct-full.html — a full DOM capture of the Employer-Student Direct board, saved as reference while building the Direct-board support. Unlike the original capture (ww-dom-full.html, gitignored from the start), this one was committed and pushed (commits v8.7.0–v8.7.2, on both dev and master).

On 2026-06-10 GitHub secret scanning emailed that the repository might contain a secret API key. The owner, assuming the leaked key was the Gemini key, rotated it immediately, then gitignored the capture (v8.7.2) and deleted it from the tree (v8.7.3).

Investigation on 2026-06-11 (pattern search over every commit in history) found exactly one key ever committed: AIzaSyBStl… inside a <script src="https://maps.googleapis.com/maps/api/js?key=…"> tag at line 3868 of the capture. That is WaterlooWorks' own Google Maps embed key — a third-party, client-side key the WW site serves to every visitor's browser, public by design. Both Gemini and Maps keys share the AIza… prefix, which is why the scanner (and the owner) read it as a possible Gemini key. The project's actual Gemini key lives only in server/.env (gitignored) and was never committed; its rotation was harmless but unnecessary.

Decision

  • Do not rewrite pushed history. The key stays reachable in commits v8.7.0–v8.7.2. It is not our secret and was already public; the v8.7.3 deletion is sufficient.
  • Dismiss the GitHub secret-scanning alert as a false positive ("used in tests / not a secret").
  • Rule going forward: full DOM captures are gitignored before they are saved. Captured third-party pages carry whatever the site embeds (keys, session tokens, CSRF nonces) and must never be committed. .gitignore already lists both capture filenames; any future capture gets its entry first.

Consequences

  • dev and master keep their published history; no force-push against the auto-deploying master (Vercel + DO, ADR 0039).
  • Anyone re-encountering the alert (or the key in old commits) has this record: it is WaterlooWorks' public Maps key, not a project credential.
  • The current Gemini key has never appeared in git history.

Alternatives considered

  • Rewrite history to scrub the file (filter-repo + force-push) — rejected: the key is third-party and public, and the rewrite would have to hit both long-lived branches, including the production branch that auto-deploys. All risk, no benefit.
  • Treat as a real leak and rotate — moot: the rotation already happened as a precaution, and the key that leaked was never ours to rotate.
