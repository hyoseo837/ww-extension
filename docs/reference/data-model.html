Data Model

All persistent state. Updated whenever a storage key is added, removed, or its schema changes.

Client — chrome.storage.local

apiKey
Type: string. Gemini API key. Read only by the background service worker; never enters the content-script context. In v4 this becomes optional / removed once server-side scoring lands.
model
Type: string ('gemini-2.5-flash' | 'gemini-2.5-pro' — verify against current options page).
cvText
Type: string. Legacy raw extracted profile text, cached from the server. As of v5.1.0 it's a fallback only — the structured profileJson below supersedes it once the user re-extracts (ADR 0015). User-facing name: "application package."
profileJson (v5.1.0)
Type: structured profile object cached from GET /profile (summary / education / experience / skills / projects / languages). Rendered read-only by section on the options page. Mirrors the server user_profile.profile_json column below.
profileSupplement (v5.1.0)
Type: array of { kind, title, description } user-authored entries, cached from GET /profile. Mirrors the server user_profile.profile_supplement column below.
preferences
Type: string. As of v5.0.0 this is the "Additional Notes" field — free-form prose the scorer weighs alongside the structured criteria below. Column/key name unchanged so old prose carries over (ADR 0013); only the label and prompt framing narrowed.
matchCriteria (v5.0.4)
Type: structured match-criteria object, cached from GET /profile (server is authoritative). Shape mirrors the server user_profile.match_criteria column documented below.
theme
Type: 'dark' | 'light'. Default 'dark'. Live-synced via chrome.storage.onChanged across all extension contexts.
tokenUsage
Type: { input: number, cached: number, output: number }. Cumulative token counters across all scans. Writes are serialized through tokenWriteChain in the background service worker to prevent lost-update races.
ww_scores
Type: Record<postingId, { score: number, verdict: string, reason: string, title: string, org: string }>. Score map keyed by WW posting ID. Drives badge rendering and sidebar list.
ww_posting_ids
Type: string[]. Ordered array from the last selectAll. Used for cross-page row navigation when the user clicks a sidebar entry on a different results page than where it was scored.
welcomeShown
Type: boolean. Set after the first-install welcome tab opens. Prevents re-opening on dev reloads (which fire onInstalled with reason 'update').
droppedFile
Type: options-page transient state for the last-dropped PDF (filename + base64). Cleared by the "Clear application package" button.
auth (v4.2.1)
Type: { access_token: string, refresh_token: string, expires_at: number, email: string, user_id: string }. Supabase session captured by chrome.identity.launchWebAuthFlow. expires_at is a millisecond timestamp; email and user_id are extracted from the decoded JWT for display. Absent when signed out; cleared by the Sign out button. Refresh logic lands at v4.2.2.
creditBalance (v4.3.1)
Type: number | undefined. Last-known credit balance fetched from GET /credits/balance by the background service worker. Unit: 1 credit = $0.01 CAD. May be fractional once debit/refund land (v4.4+). Cleared on sign-out. Live-synced to UI via chrome.storage.onChanged.

Server — Supabase Postgres

User records are managed by Supabase Auth (table auth.users) — populated automatically on first Google sign-in. Application-owned tables (credit ledger, scan history) land at v4.3+ and will be documented here as they ship.

Live (v4.3.0):

  • auth.users (Supabase-managed) — identity records keyed by UUID. The extension receives this UUID as sub in the session JWT.
  • public.credit_ledger_entry — append-only credit ledger. See below.

public.credit_ledger_entry

Append-only log of credit movements per user. Balance is computed as SUM(delta) over a user's rows. Unit: 1 credit = $0.01 CAD.

id uuid primary key default gen_random_uuid()
Row identifier.
user_id uuid not null references auth.users(id) on delete cascade
Owner. If the auth row is deleted, the ledger rows go with it.
delta numeric(14, 6) not null
Positive for credits added (signup_bonus, admin_grant, purchase, scan_refund); negative for credits spent (scan_debit). Fractional values are expected once token-priced debits land at v4.4. NUMERIC keeps Postgres SUM exact.
kind text not null check (kind in (…))
One of 'signup_bonus', 'admin_grant', 'purchase', 'scan_debit', 'scan_refund'.
ref text null
Free-form correlation (scan UUID for debit/refund pairs at v4.4; Stripe event ID for purchases at v4.5).
created_at timestamptz not null default now()
Insertion time.

Indexes: (user_id, created_at desc) for balance/history reads; partial unique index on (user_id) where kind = 'signup_bonus' as defense-in-depth against double-grant; partial unique index on (ref) where kind = 'purchase' (migration 0004, v4.5) so a replayed Stripe webhook can't double-grant — one purchase row per Stripe event id.

RLS: enabled. SELECT policy auth.uid() = user_id; no INSERT/UPDATE/DELETE policies. Backend uses service-role credentials and bypasses RLS for its own queries — RLS is a safety net for any future code path that ever holds a user-role connection.

Signup bonus trigger. public.grant_signup_bonus() fires AFTER INSERT on auth.users and inserts one signup_bonus row of delta = 100 (= $1 CAD). Hardcoded; bump via a follow-up migration.

Live (v4.4): public.scan — per-call request/response + metering record backing the estimate-debit-refund flow and scan_id idempotency on /scan and /profile/extract. Full column set in server/migrations/0002_scan.sql.

Credit purchases (v4.5). Stripe purchases add no new table. A paid checkout.session.completed webhook inserts one kind='purchase' row into credit_ledger_entry with ref = the Stripe event id; idempotency is the purchase-ref partial unique index above. ADR 0012 chose this over a dedicated stripe_event table (minimal-code; add one later if full payment-funnel auditing is ever needed).

public.user_profile

Server-authoritative profile, one row per user (migration 0003, v4.4). All writes go through the authenticated PUT /profile; POST /profile/extract sets cv_text.

user_id uuid primary key references auth.users(id) on delete cascade
Owner. Profile row is removed if the auth user is deleted.
cv_text text not null default ''
Legacy raw extracted profile text. As of v5.1.0 it's a fallback (ADR 0015): the scan serializes profile_json when non-empty, else this. Existing users keep scoring on it until they re-extract; a cleanup migration to drop it is deferred.
preferences text not null default ''
Free-form prose. As of v5.0.0 its meaning narrows to the "Additional Notes" field; the column name is kept (ADR 0013) so existing users' prose carries over with no data migration.
match_criteria jsonb not null default '{}' (v5.0.0, migration 0006)
Structured match criteria. Shape is owned/validated by the backend MatchCriteria Pydantic model — the DB enforces only valid JSON (ADR 0013). Fields:
  • work_authorization — enum citizen | pr | international | other | unset. An eligibility fact, not weighted.
  • preferred_locations, work_modes, target_term, target_length, languages (spoken/working, not programming) — each a WeightedCriterion: a weight (must | strong | nice-to-have) plus four string-array tiers preferred / acceptable / avoid / excluded.
build_job_part() serializes populated criteria into a short labelled block ahead of the notes; empty criteria emit nothing, so an empty-criteria scan is byte-identical to the pre-v5 prompt. Credit-free hard-Skip on an excluded match or work-auth ineligibility is a later v5 thread (#4) — v5.0.0 only makes the model aware of the criteria.
profile_json jsonb not null default '{}' (v5.1.0, migration 0007)
Machine-extracted structured profile, owned/validated by the StructuredProfile Pydantic model (ADR 0015). Fields: summary, education[] (institution/credential/field/grade/dates), experience[] (title/org/dates/description), skills[], projects[] (title/description), languages[] (spoken/working). Overwritten by POST /profile/extract; PUT /profile accepts it only for a full replace ({} clears). build_profile_context() serializes it into the Candidate Profile block, falling back to cv_text when empty.
profile_supplement jsonb not null default '[]' (v5.1.0, migration 0007)
User-authored entries a one-page resume omits: an array of { kind: "experience" | "project", title, description }. Written only by PUT /profile — never by extraction — so re-uploading a PDF can't clobber them (ADR 0015). Appended to the Candidate Profile block as self-reported context at scan time.
updated_at timestamptz not null default now()
Touched on every upsert.

RLS: enabled with own-row select/modify policies; the backend uses service-role credentials and bypasses RLS for its own queries.
