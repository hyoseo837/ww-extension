Data Model

All persistent state. Updated whenever a storage key is added, removed, or its schema changes.

Client — chrome.storage.local

Trimmed to the live key set at v8.13 (dead-code sweep). The profile/settings cache keys of v3–v5 (apiKey, model, theme, tokenUsage, cvText, profileJson, profileSupplement, preferences, matchCriteria, hardFilterEnabled, droppedFile) are gone — profile data is server-authoritative and edited on the web app since v6.4, scoring is server-side since v4.4, and the pre-filter was retired by ADR 0043.

auth (v4.2.1)
Type: { access_token: string, refresh_token: string, email: string, user_id: string }. Supabase session captured by chrome.identity.launchWebAuthFlow; email and user_id are extracted from the decoded JWT for display. Absent when signed out; cleared by the Sign out button. The background worker refreshes the session reactively on a backend 401 (one shared in-flight refresh; Supabase rotates the refresh token per use).
creditBalance (v4.3.1)
Type: number | undefined. Last-known credit balance, updated by the background worker from GET /credits/balance and from each POST /scan response. Unit: 1 credit = $0.01 CAD; may be fractional. Cleared on sign-out. Live-synced to the sidebar credits chip and the options page via chrome.storage.onChanged.
ww_scores
Type: Record<postingId, { score: number | null, verdict: string, reason: string, breakdown: { point: string, effect: "plus" | "minus" }[], title: string, org: string, scanId?: string, board?: "full" | "direct", feedback?: "up" | "down" }>. Score map keyed by WW posting ID. score is 1–20 and verdict is one of Strong Apply · Apply · Consider · Unlikely · Skip · Excluded (ADR 0017); breakdown is the gain/loss points rendered in the sidebar card. scanId (v8.6.6) keys 👍/👎 feedback to the server scan row (ADR 0044); feedback records a sent vote (hides the buttons). board (v8.7.1) tags which WW board the entry was scanned on — absent means pre-v8.7, treated as "full". Drives badge rendering and the per-board sidebar list.
ww_posting_ids
Type: string[]. Ordered array from the last selectAll. Used for cross-page row navigation when the user clicks a sidebar entry on a different results page than where it was scored.
ww_scoring_schema
Type: number. The scoring-output schema version the cached ww_scores were written under (ADR 0017). On load, a mismatch with the client's current version clears ww_scores / ww_posting_ids wholesale so badges never mix scales (e.g. old 1–10 with new 1–20).
ww_save_collapsed (v8.6.10)
Type: boolean. Whether the sidebar's Save-to-Folder section is collapsed. Absent = collapsed (the default, so the results list gets the room).
welcomeShown
Type: boolean. Set after the first-install welcome tab opens. Prevents re-opening on dev reloads (which fire onInstalled with reason 'update').

Server — Supabase Postgres

User records are managed by Supabase Auth (table auth.users) — populated automatically on first Google sign-in. Application-owned tables live in public; their migrations are the column-level source of truth (server/migrations/, well-commented).

Live tables:

  • auth.users (Supabase-managed) — identity records keyed by UUID. The extension receives this UUID as sub in the session JWT.
  • public.credit_ledger_entry (v4.3) — append-only credit ledger. See below.
  • public.scan (v4.4) — per-call metering record.
  • public.user_profile (v4.4) — server-side profile. See below.
  • public.signup_bonus_block (v6.9) — deleted-account email hashes, bonus suppression. See below.
  • public.scan_feedback (v8.6.6) — 👍/👎 verdicts on scored postings. See below.
  • public.referral (v8.12) — friend-invitation attribution. See below.

public.credit_ledger_entry

Append-only log of credit movements per user. Balance is computed as SUM(delta) over a user's rows. Unit: 1 credit = $0.01 CAD.

id uuid primary key default gen_random_uuid()
Row identifier.
user_id uuid not null references auth.users(id) on delete cascade
Owner. If the auth row is deleted, the ledger rows go with it.
delta numeric(14, 6) not null
Positive for credits added (signup_bonus, admin_grant, purchase, scan_refund, referral_bonus); negative for credits spent (scan_debit). Fractional values are expected once token-priced debits land at v4.4. NUMERIC keeps Postgres SUM exact.
kind text not null check (kind in (…))
One of 'signup_bonus', 'admin_grant', 'purchase', 'scan_debit', 'scan_refund', 'referral_bonus' (v8.12, migration 0013).
ref text null
Free-form correlation (scan UUID for debit/refund pairs at v4.4; Stripe event ID for purchases at v4.5; invitee user id for referral bonuses at v8.12).
created_by uuid null references auth.users(id), note text null (v6.6, migration 0009)
Audit trail for admin gift grants (ADR 0025): created_by is the granting admin, note the free-text reason. NULL for system/self rows and all pre-v6.6 rows.
created_at timestamptz not null default now()
Insertion time.

Indexes: (user_id, created_at desc) for balance/history reads; partial unique index on (user_id) where kind = 'signup_bonus' as defense-in-depth against double-grant; partial unique index on (ref) where kind = 'purchase' (migration 0004, v4.5) so a replayed Stripe webhook can't double-grant — one purchase row per Stripe event id; partial unique index on (ref) where kind = 'referral_bonus' (migration 0013, v8.12) — at most one referral bonus per invitee, ever. The settlement hook does a plain insert-or-ignore on every successful scan, so "first scan only" is emergent with no first-scan bookkeeping (ADR 0050).

RLS: enabled. SELECT policy auth.uid() = user_id; no INSERT/UPDATE/DELETE policies. Backend uses service-role credentials and bypasses RLS for its own queries — RLS is a safety net for any future code path that ever holds a user-role connection.

Signup bonus trigger. public.grant_signup_bonus() fires AFTER INSERT on auth.users and inserts one signup_bonus row of delta = 100 (= $1 CAD). Hardcoded; bump via a follow-up migration.

Live (v4.4): public.scan — per-call request/response + metering record backing the estimate-debit-refund flow and scan_id idempotency on /scan and /profile/extract. Full column set in server/migrations/0002_scan.sql.

Credit purchases (v4.5). Stripe purchases add no new table. A paid checkout.session.completed webhook inserts one kind='purchase' row into credit_ledger_entry with ref = the Stripe event id; idempotency is the purchase-ref partial unique index above. ADR 0012 chose this over a dedicated stripe_event table (minimal-code; add one later if full payment-funnel auditing is ever needed).

public.signup_bonus_block (v6.9, migration 0010, ADR 0029). One-way SHA-256 hashes of lowercased emails, written on account deletion so a delete + re-register can't re-grab the signup bonus (the grant_signup_bonus trigger skips on a matching hash). Also consulted by the referral flow (v8.12, ADR 0050): a blocked identity is never referral_eligible. No plaintext email survives a deletion. RLS on with no policies — backend-only.

public.scan_feedback (v8.6.6, migration 0012, ADR 0044). User 👍/👎 verdicts on scored postings: one row per scan (scan_id PK), re-submits upsert so the latest verdict wins; rating, optional comment, and description_text (stored only on 👎, sent by the extension at feedback time). RLS on with no policies — backend-only. Full column set in server/migrations/0012_scan_feedback.sql.

public.referral (v8.12, migration 0013, ADR 0050). Friend-invitation attribution: one row per invitee (invitee_user_id PK, inviter_user_id, both FK to auth.users on delete cascade), written by POST /referral when the invitee answers the optional "Who invited you?" wizard step. The inviter's 20-credit referral_bonus ledger row is granted at the invitee's first successful scan settlement (idempotency via the partial unique index above). RLS on with no policies — backend-only.

public.user_profile

Server-authoritative profile, one row per user (migration 0003, v4.4). All writes go through the authenticated PUT /profile; POST /profile/extract sets cv_text.

user_id uuid primary key references auth.users(id) on delete cascade
Owner. Profile row is removed if the auth user is deleted.
cv_text text not null default ''
Legacy raw extracted profile text. As of v5.1.0 it's a fallback (ADR 0015): the scan serializes profile_json when non-empty, else this. Existing users keep scoring on it until they re-extract; a cleanup migration to drop it is deferred.
preferences text not null default ''
Free-form prose. As of v5.0.0 its meaning narrows to the "Additional Notes" field; the column name is kept (ADR 0013) so existing users' prose carries over with no data migration.
match_criteria jsonb not null default '{}' (v5.0.0, migration 0006)
Structured match criteria. Shape is owned/validated by the backend MatchCriteria Pydantic model — the DB enforces only valid JSON (ADR 0013). Fields:
  • work_authorization — enum citizen | pr | international | other | unset. An eligibility fact, not weighted.
  • preferred_locations, work_modes, target_term, target_length, languages (spoken/working, not programming) — each a WeightedCriterion: a weight (must | strong | nice-to-have) plus four string-array tiers preferred / acceptable / avoid / excluded.
build_job_part() serializes populated criteria into a short labelled block ahead of the notes; empty criteria emit nothing, so an empty-criteria scan is byte-identical to the pre-v5 prompt. As of v5.2 (ADR 0017) the scorer flags an excluded-tier match or work-auth ineligibility as the Excluded verdict during scoring. As of v5.3 (ADR 0018) the client also runs a credit-free pre-scan skip: postings whose results-table City matches an excluded-tier location are marked Excluded before any Gemini call. Coverage is conservative — structured City only (free-text work-auth/location-region gates still go through the scan-time verdict).
profile_json jsonb not null default '{}' (v5.1.0, migration 0007)
Machine-extracted structured profile, owned/validated by the StructuredProfile Pydantic model (ADR 0015). Fields: summary, education[] (institution/credential/field/grade/dates), experience[] (title/org/dates/description), skills[], projects[] (title/description), languages[] (spoken/working), plus raw-text dumps of the package's other documents (v5.1.6): grade_report, coop_history, cover_letter (the CV is structured; these aren't). Overwritten by POST /profile/extract; PUT /profile accepts it only for a full replace ({} clears). build_profile_context() serializes it into the Candidate Profile block, falling back to cv_text when empty.
profile_supplement jsonb not null default '[]' (v5.1.0, migration 0007)
User-authored entries a one-page resume omits: an array of { kind: "experience" | "project", title, description }. Written only by PUT /profile — never by extraction — so re-uploading a PDF can't clobber them (ADR 0015). Appended to the Candidate Profile block as self-reported context at scan time.
updated_at timestamptz not null default now()
Touched on every upsert.

RLS: enabled. Own-row SELECT policy only; the modify policy was dropped in migration 0011 (v8.3.2) so the backend — service-role credentials, bypasses RLS — is the sole writer and Pydantic validation can't be skipped via direct PostgREST writes.
