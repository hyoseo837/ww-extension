Code & infrastructure audit — 2026-06-11

Full read-through of the repo at v8.7.4, looking for weak points and upgrade candidates ahead of the September 2026 recruiting wave (ADR 0042's marketing window). Overall assessment: the credit flow is carefully idempotent, auth is verified via JWKS, prompts live server-side with injection guards — the weaknesses are mostly in what's around the code (tests, CI, failure recovery, observability), not in the code itself.

Each finding names its planned fix phase. The phase plan is decided in ADR 0046; per-phase scope is locked in each phase's spec when the phase opens. File references are as of commit e2ef15c.

High value

  1. Zero tests and zero CI, anywhere. No pytest suite, no ruff/mypy config, no .github/workflows. The code that most deserves tests handles money: the estimate→debit→call→refund flow (server/app/scoring/routes.py), idempotent replay (_replay), ledger math (server/app/billing/db.py), the Stripe grant, and the pure logic in pricing.py / gemini.verdict_for / gemini._valid_result. All of it is hand-verified today; every future v8.x fix re-risks it. Phase: v8.8.
  2. A crash mid-scan permanently eats the user's credits. If the server dies between transaction 1 (debit) and settlement — realistically, a DO deploy restart during the 1–10s Gemini call — the scan row stays pending forever, the debit is never refunded, and a retry on the same scan_id gets 409 forever (_replay, server/app/scoring/routes.py:388). There is no reconciliation path. Phase: v8.9.
  3. The balance check can be raced past. balance_after_estimate computes sum(delta) − estimate at read-committed isolation, and the extension runs SCAN_CONCURRENCY = 5 workers — several requests can pass the check before any debit commits, driving a balance negative by up to ~5 estimates. Self-inflicted only and bounded, but the "balance never goes negative" invariant is not actually enforced. A per-user pg_advisory_xact_lock in transaction 1 closes it. Phase: v8.9.
  4. server/pyproject.toml is stuck at 6.11.0. The server changed since (v8.6.6 shipped the feedback backend), so /health reports a wrong version — defeating the deploy-skew check that endpoint exists for (ADR 0010 discipline). Phase: v8.8 (catch-up bump + CI guard).

Server hardening

  1. Request bodies are unbounded before validation. /profile/extract checks the 5 MB PDF cap only after FastAPI parses the full JSON body; /scan's description_text has no server-side max_length (the 6000-char cap lives only in the extension). An authenticated user can post a 100 MB body and make the server parse it. Add Field(max_length=…) on inputs and confirm DO App Platform's body-size limit. Phase: v8.9.
  2. No rate limiting. /scan is credit-bounded, but /credits/checkout (Stripe session creation), /account/export (heavy multi-table query), and /scan/feedback are free to hammer. Phase: v8.10.
  3. No retry on transient Gemini failures. One 429/503/network blip = one user-visible failed scan in the batch (refunded, but reported as a failure in the summary). A single retry with short backoff in gemini.score() would cut failure noise on 200-job batches. Phase: v8.10.
  4. /health doesn't touch the DB. A dead connection pool still reports ok, so platform health checks won't catch the most likely real outage. A select 1 makes it honest. Phase: v8.10.
  5. No error monitoring. Failures exist only in DO's log stream; web-app errors vanish entirely. A free-tier error tracker (server + web) means hearing about breakage before users email. New external service — needs an owner decision at phase time. Phase: v8.10 (decision gated).
  6. Balance is a full-ledger sum on every call. get_balance is O(ledger size); fine at current scale, degrades as ledgers grow. A running-total or cached balance is the eventual upgrade. Not scheduled — revisit if scan latency logging shows db_pre_ms growth.

Extension

  1. ext/src/content.js is a 1037-line monolith mixing the scan engine, sidebar rendering, pagination navigation, and feedback UI. manifest.json can list multiple content-script files without a build step. Phase: v8.11.
  2. No per-job retry. Failed scans in a batch are reported only as an aggregate count; recovering means re-running (and re-confirming) the whole batch. A "retry N failed" affordance would help on flaky networks. Phase: v8.11.
  3. The model id gemini-2.5-flash is hardcoded client-side (ext/src/content.js:449). When Google retires it, the fix needs a Web Store release with review lag. Letting the server choose the default when model is omitted moves the risk server-side where a same-day deploy fixes it. Phase: v8.11.
  4. Dead code: VERDICT_ORDER in ext/src/page-bridge.js:3 is the obsolete 3-tier ladder, unused; _require_pool() in server/app/billing/db.py is also unused. Phase: v8.11 (ride-along).

Portfolio presentation (serves the ADR 0042 goal directly)

  1. The repo is public but has no GitHub description or topics — the first thing a visitor sees above the (already strong) README. One-minute fix. Strand: portfolio, any time.
  2. The docs don't render on GitHub. The ADR/spec system — the most impressive artifact for a recruiter — is HTML, shown as raw source on github.com. Serving docs/ via GitHub Pages (already styled, zero build) and linking it from the README turns 45+ ADRs from invisible into a showcase. Strand: portfolio (decision gated — outward-facing).
  3. Housekeeping: the whiteboard still lists the feedback loop and Direct board as future features (both shipped; editing needs explicit owner permission). And now that the repo is public, the captured WW Maps key in git history (ADR 0045) is publicly reachable — still a non-secret third-party key, but the "leave it" call predates knowing the repo was public; reaffirm or scrub. Strand: portfolio (owner decisions).
