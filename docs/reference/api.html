Backend API Contract

Authoritative contract for the FastAPI backend in server/ (monorepo since ADR 0010). Single source of truth; no mirror. The client (extension) reads this file directly.

Base URL: https://ww-extension-backend-x5h6h.ondigitalocean.app

Auth header convention

Authenticated endpoints expect the Supabase session JWT in Authorization: Bearer <jwt>. Backend verifies the JWT against Supabase JWKS (ES256/RS256, audience "authenticated", 10s leeway) before any business logic. Failures return 401 with WWW-Authenticate: Bearer.

CORS (v6.1). Browser clients (the web app) are served Access-Control-Allow-Origin for the origins in CORS_ORIGINS; methods GET/POST/PUT/OPTIONS, Authorization header allowed, credentials off (bearer-token auth, no cookies).

Live endpoints

GET /health

Liveness probe. No auth.

Response: 200 OK

{
  "service": "ww-extension-backend",
  "version": "4.2.0",
  "status": "ok"
}

version reflects the value in server/pyproject.toml at the deployed commit — read at startup via importlib.metadata.version. Useful for confirming a deploy went through.

GET /me

Authenticated. Returns the signed-in user's identity extracted from the verified Supabase JWT.

Response: 200 OK

{
  "user_id": "<supabase-user-uuid>",
  "email": "user@example.com"
}

Errors: 401 if the Authorization header is missing or the token fails verification (expired, wrong signature, wrong audience, malformed, etc.). v4.2.0 returns the underlying PyJWT error message in detail for debugging; v4.3+ may sanitize.

GET /credits/balance

Authenticated. Returns the signed-in user's current credit balance as a JSON number. Unit: 1 credit = $0.01 CAD. Computed as SUM(delta) over the user's credit_ledger_entry rows.

Response: 200 OK

{
  "balance": 100
}

May be fractional once debit/refund land (v4.4+) — e.g., {"balance": 99.925}.

Errors: 401 on missing or invalid Authorization header (same semantics as /me).

POST /scan

Authenticated. Scores one job posting. Backend pre-debits a worst-case estimate, calls Gemini, refunds the unused portion on success or the full estimate on failure, and returns the parsed result. Idempotent on scan_id.

Request:

{
  "scan_id": "<uuid v4 — client-generated, doubles as idempotency key>",
  "model": "gemini-2.5-flash" | "gemini-2.5-pro",
  "meta": { "title": "...", "org": "..." },
  "description_text": "...",
  "posting_id": "<WW posting ID>"
}

Breaking change in v4.4.2: cv_text and preferences are no longer accepted in the request body. The backend reads them from user_profile on every scan. Set them via PUT /profile first.

Response: 200 OK

{
  "result": {
    "score": 16,
    "verdict": "Apply",
    "reason": "...",
    "breakdown": [
      { "point": "Python + AWS match the stack", "effect": "plus" },
      { "point": "prefers Toronto, posting in Montréal", "effect": "minus" }
    ]
  },
  "cost": 0.074,
  "balance": 99.926
}

Scoring output (v5.2, ADR 0017). score is an integer 1–20 (model-produced). breakdown is the decisive gain/loss points, each { point, effect } with effect ∈ "plus" | "minus" (may be empty). verdict is server-derived — never sent by the model — from a model-emitted excluded flag, then the score band:

  • excluded == true (a hard work-auth/citizenship/clearance gate, or a criterion in the candidate's "excluded" tier) → Excluded; the model also scores it 1–5.
  • else by band: Strong Apply 17–20 · Apply 14–16 · Consider 10–13 · Unlikely 6–9 · Skip 1–5.

excluded stays server-side (it shapes the verdict and is kept on the stored scan.response for faithful replay); the client receives only the resulting verdict string. cost is the net debit (estimate minus the partial refund). balance is the user's balance after this scan, so the extension doesn't need a follow-up /credits/balance fetch.

Errors:

  • 400 — unsupported model, malformed request, or {"error": "profile_not_set"} when the user has no cv_text in their user_profile.
  • 401 — missing/invalid bearer token.
  • 402 Payment Required — insufficient credits. Body: 
    { "detail": { "error": "insufficient_credits", "balance": 0.4, "required": 0.74 } }
    No ledger row is written; the scan row is marked failed.
  • 409 — the same scan_id is currently pending or previously failed. Body: { "detail": { "error": "scan_in_progress_or_failed", "status": "..." } }. Successful scan_ids replay with their original result.
  • 502 Bad Gateway — Gemini call failed (network, non-2xx, parse, or schema). The pre-debit has been fully refunded; the scan row is marked failed with the error message stored. Body: { "detail": { "error": "gemini_failed", "message": "..." } }.

Idempotency. Replaying a POST /scan with a previously successful scan_id returns the original {result, cost, balance} without re-debiting or re-calling Gemini. The PK conflict on scan.id is the enforcement.

GET /profile

Authenticated. Returns the user's stored CV text, structured match criteria, and free-form notes. Empty values if the row hasn't been created yet.

Response: 200 OK

{
  "cv_text": "...",
  "preferences": "...",            // free-form "Additional Notes" (v5.0.0)
  "match_criteria": {              // structured criteria (v5.0.0); {} if unset
    "work_authorization": "international" | "citizen" | "pr" | "other" | null,
    "preferred_locations": { "weight": "strong",
      "preferred": [...], "acceptable": [...], "avoid": [...], "excluded": [...] },
    "work_modes":    { ...same WeightedCriterion shape... },
    "target_term":   { ... },
    "target_length": { ... },
    "languages":     { ... }       // spoken/working, not programming
  },
  "profile_json": {                // structured profile (v5.1.0); {} if not extracted
    "summary": "...",
    "education":  [{ "institution", "credential", "field", "grade", "dates" }],
    "experience": [{ "title", "org", "dates", "description" }],
    "skills":     ["..."],
    "projects":   [{ "title", "description" }],
    "languages":  ["..."],         // spoken/working
    "grade_report": "...",         // raw text from the transcript (v5.1.6)
    "coop_history": "...",         // raw text from the UW co-op work-history summary
    "cover_letter": "..."          // raw text, if the package included one
  },
  "profile_supplement": [          // user-authored entries (v5.1.0); [] if none
    { "kind": "experience" | "project", "title": "...", "description": "..." }
  ]
}

weight is one of must | strong | nice-to-have. Shapes are owned/validated by backend Pydantic models (ADR 0013, ADR 0015). The scan uses profile_json when non-empty, else falls back to cv_text (ADR 0015).

PUT /profile

Authenticated. Upserts the user's profile. Any field may be omitted to leave that column untouched. No credit cost.

Request:

{
  "cv_text": "...",            // optional
  "preferences": "...",        // optional — "Additional Notes"
  "match_criteria": { ... },   // optional — full object (see GET); replaces the column
  "profile_supplement": [ ... ], // optional — full array; replaces the column
  "profile_json": { ... }      // optional — normally set by /profile/extract;
                               //   accepted here only for a full replace ({} clears)
}

A bad work_authorization, weight, or supplement kind is rejected (422). match_criteria, profile_supplement, and profile_json are each replaced wholesale when present, so send the complete value.

Response: 200 OK with the updated {cv_text, preferences, match_criteria, profile_json, profile_supplement}.

POST /profile/extract

Authenticated. Sends a PDF to Gemini multimodal for structured extraction (a profile responseSchema, v5.1.0); on success, upserts the result into user_profile.profile_json (leaving cv_text and profile_supplement untouched, ADR 0015). The package is multi-document: the CV fills the structured fields, while the grade report, UW co-op work history, and cover letter are copied verbatim into the grade_report / coop_history / cover_letter raw fields (v5.1.6). Same estimate-debit-call-refund machinery as /scan (same scan_id idempotency, same 402 / 502 shapes).

Request:

{
  "scan_id": "<uuid v4>",
  "model": "gemini-2.5-flash" | "gemini-2.5-pro",
  "pdf_b64": "<base64-encoded PDF, no data: prefix>"
}

5 MB cap on the decoded PDF.

Response: 200 OK

{
  "profile": { ...structured profile, see GET /profile... },
  "text": "...readable serialization of `profile`, for display...",
  "cost": 1.85,
  "balance": 98.15
}

Errors: same set as /scan (400 unsupported model / invalid base64 / oversize / 401 / 402 / 409 / 502).

POST /credits/checkout (v4.5)

Authenticated. Creates a Stripe Checkout session (hosted payment page) for one credit package and returns its URL. No credit movement happens here — credits are granted later by the webhook. The granted amount is derived server-side from package_id; the client never sends a credit or dollar amount. Packages are fixed 1:1 bundles (1 credit = $0.01 CAD): credits_500 ($5), credits_1000 ($10), credits_2000 ($20).

Request:

{
  "package_id": "credits_500" | "credits_1000" | "credits_2000"
}

Response: 200 OK

{
  "url": "https://checkout.stripe.com/c/pay/<session>"
}

The extension opens url in a new tab (chrome.tabs.create).

Errors: 400 {"detail": "unknown package: …"} for an unrecognized package_id; 401 on missing/invalid bearer token.

POST /webhooks/stripe (v4.5)

Stripe-only; not JWT-authenticated. Gated by Stripe signature verification: the raw body is checked against the Stripe-Signature header using STRIPE_WEBHOOK_SECRET before any logic. On a checkout.session.completed event with payment_status = "paid", grants the package's credits as one kind='purchase' ledger row, keyed for idempotency on the Stripe event id (stored in ref). Replays and Stripe retries are no-ops.

Response: 200 OK {"received": true} — returned for handled and ignored event types so Stripe stops retrying. A DB error surfaces as 500 so Stripe retries (the grant is idempotent).

Errors: 400 {"detail": "invalid_signature"} on a missing/invalid signature or malformed payload — no ledger row is written.

GET /credits/checkout/result (v4.5)

No auth. Minimal HTML landing page Stripe redirects the browser to after Checkout (?status=success or ?status=cancel). Exists because Stripe requires an http(s) success_url and a chrome-extension:// URL is not allowed. Purely a UX page — it does not grant credits (the webhook does).
