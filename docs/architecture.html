Architecture

Living description of the system as currently shipped. Update this file when the architecture changes — not per phase. For phase-level detail see docs/specs/.

Baseline: v03.015 (last shipped client version before v4 opening). The backend lives at server/ in this repo (monorepo since ADR 0010 superseded 0004); its section below is a placeholder until v4.1 bootstrap creates that folder.

Components

Client — this repo (Chrome MV3 extension)

Files

manifest.json
MV3 manifest. options_ui.open_in_tab: true, action: {} (no popup — toolbar icon opens options). Content script matches jobs.htm* on WaterlooWorks.
options.html + src/options.js
Thin settings UI (slimmed at v6.4): a Model tab and a Settings tab (Google sign-in / email / live balance / sign-out, theme toggle, hard-filter toggle, About). Account, profile, preferences, and credit purchase moved to the web app — the page deep- links there (.open-web → chrome.tabs.create at ww-extension.hyoseo.dev/account · /profile). No profile/criteria editing or in-extension checkout remains.
welcome.html
First-run welcome page. Opens on install via chrome.runtime.onInstalled; welcomeShown storage flag prevents re-open on dev reloads.
src/content.js
Content script. Owns the sidebar UI, scan flow, badge injection via MutationObserver, theme listener, empty-state guide, and the out-of-credits "Buy credits" nudge (shown when a scan batch halts on NO_CREDITS; opens the web app's /buy via openWebApp, v6.4) — and a matching profile-not-set prompt (PROFILE_NOT_SET → web /profile). Also runs the client hard-exclusion pre-filter (ADR 0018): before /scan, a posting whose results-table City matches a excluded-tier location is marked Excluded with no Gemini call and no credit — so Excluded has two producers (this pre-filter and the scan-time verdict). Gated by the hardFilterEnabled setting.
src/background.js
Service worker. Gemini API client, token-usage counter, message router. Handles openWelcome, openOptions, openWebApp {path} (v6.4, deep-links to the web app), scan requests from content script.
src/page-bridge.js
Page-context bridge. Injected into the WW page (not isolated world) to access dataViewerApp and action tokens. Communicates with content script via postMessage with reqId namespacing.
src/sidebar.css
All extension CSS: sidebar variables (dark/light tokens), badge styles, controls. No JS-driven styling.

Storage

See reference/data-model.html for the full key list with schemas. Summary: settings (apiKey, model, cvText fallback + structured profileJson/profileSupplement, preferences/notes + structured matchCriteria), theme, cumulative token usage, score map per posting (with a scoring-schema version for clear-on-upgrade), hardFilterEnabled (hard-exclusion pre-filter toggle, v5.3), ordered posting-id list for cross-page navigation, auth (Supabase session, v4.2.1+) and creditBalance (last-known balance from GET /credits/balance, v4.3.1+). The credits chip in the sidebar header and the Account section in options both render creditBalance live via chrome.storage.onChanged. The options Account section also hosts the v4.5 Buy-credits buttons: a click routes through the background createCheckout handler to POST /credits/checkout and opens the returned Stripe URL in a new tab; the options page re-fetches the balance on visibilitychange when the user returns.

Key architectural decisions to preserve

  • page-bridge runs in page context. Required to reach dataViewerApp and action tokens that the isolated content-script world cannot see. Communication via postMessage with per-request IDs.
  • Direct fetch to /myAccount/co-op/full/jobs.htm with cached action tokens, bypassing getPostingOverview(). Kills overlay flicker during scans. Do not revert.
  • MutationObserver on <table> with rAF-debounced badge reinject. DataViewer reuses <tr> elements on pagination, so badges must re-attach after any DOM mutation.
  • API key sent as X-Goog-Api-Key header, never in query string. Keeps the key out of browser history / referer logs.
  • Token accumulation serialized through a per-context tokenWriteChain promise. Prevents lost-update races when multiple scans update the counter concurrently.
  • chrome.storage.onChanged drives live UI updates for theme switching and guide-step status. One listener, multiple consumers — do not add per-feature listeners.

Web app — web/ (Vite + React + TypeScript SPA)

Second client of the backend, added at v6.1 bootstrap. A static SPA (ADR 0019) that moves account, profile/CV, match-criteria, and payment management off the extension's options page onto a dedicated web surface; the extension stays focused on in-page scoring. Lives at web/ in the monorepo, excluded from the Web Store zip by the package.sh allowlist (ADR 0020). Deploys to ww-extension.hyoseo.dev on Vercel, independent of the backend's DigitalOcean deploy (ADR 0022).

Structure (v6.2). react-router SPA: src/supabase.ts (browser client, Google OAuth PKCE), src/api.ts (bearer-token fetch/POST), src/useSession.ts (session hook), and src/Layout.tsx (the app shell; shares balance via Outlet context). Routes: /account (dashboard home), /billing (paginated credit history; GET /credits/history), /buy (packages → POST /credits/checkout {client:"web"} → Stripe), and a logged-out Landing. A vercel.json rewrite serves index.html for all paths so deep links (the Stripe return to /billing) resolve client-side. The profile editor splits into /profile + /preferences at v6.3. v6.3 styled the app with Tailwind (ADR 0023); v6.5 reshaped the shell into a persistent left sidebar (w-64; content offsets md:ml-64, fixed bars md:left-64), made /account a dashboard home (welcome + balance + profile snapshot + recent activity), and built the full logged-out landing (ADR 0024).

Auth (independent sessions, ADR 0021). The web app signs in on its own via @supabase/supabase-js and holds its own Supabase session — no token sharing with the extension. Both surfaces resolve to the same user_id on the backend, so per-user data is identical from either. The extension links users here with a "Manage account →" deep link (wired at v6.4).

Config. Build-time VITE_ env vars, all public by design (they ship in the bundle): VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY (publishable key), VITE_API_BASE_URL. No secret ever reaches the SPA. Template in web/.env.example; setup checklist in web/README.md.

Backend — server/

FastAPI on Python 3.12+, deployed to DigitalOcean App Platform. Will host user accounts, credit ledger, and Gemini-calling logic (moving prompts and scoring tuning off the client). Stack rationale: ADR 0007 (DO), ADR 0008 (Supabase), ADR 0009 (FastAPI), ADR 0011 (uv). Monorepo rationale: ADR 0010.

Endpoints

Authoritative request/response contract: reference/api.html. Summary:

  • GET /health — liveness probe. No auth. Returns {service, version, status}.
  • GET /me (v4.2.0) — authenticated. Returns {user_id, email} from the verified Supabase JWT.
  • GET /credits/balance (v4.3.0) — authenticated. Returns {balance: number} (1 credit = $0.01 CAD).
  • GET /profile, PUT /profile (v4.4) — authenticated. Read/upsert the user's server-side profile: structured profile (profile_json JSONB + user-authored profile_supplement, v5.1.0) with cv_text kept as fallback, structured match criteria (match_criteria JSONB, v5.0.0), and free-form notes.
  • POST /scan, POST /profile/extract (v4.4) — authenticated. Billable Gemini calls; estimate-debit-call-refund against the ledger, idempotent on scan_id.
  • POST /credits/checkout (v4.5) — authenticated. Creates a Stripe Checkout session for a fixed credit package; returns its URL. No credit movement.
  • POST /webhooks/stripe (v4.5) — Stripe-only, signature-verified (not JWT-authed). Grants kind='purchase' credits on a paid checkout.session.completed, idempotent on the Stripe event id (ledger ref).
  • GET /credits/checkout/result (v4.5) — no auth. Minimal HTML landing page for Stripe's success/cancel redirect (a chrome-extension:// URL can't be a Stripe success_url).

Auth: Authorization: Bearer <jwt> on authenticated routes. Backend verifies JWTs against Supabase JWKS (ES256/RS256, audience "authenticated") via the app.auth.dependency.current_user FastAPI dependency. Full contract in reference/api.html.

CORS (v6.1). A CORSMiddleware allows the web app's browser origin(s) (CORS_ORIGINS) to call authenticated routes. Bearer-token auth (no cookies) → credentials off. The extension and direct API clients are unaffected (CORS is a browser-enforced policy).

Database access

app.billing.db owns an asyncpg connection pool, opened/closed via the FastAPI lifespan. Connects through the Supabase Session pooler (port 5432, IPv4, session-mode — preserves prepared-statement caching, unlike the transaction pooler). Backend bypasses RLS via the role's privileges; RLS policies on public.credit_ledger_entry remain enabled as defense-in-depth.

SQL migrations live in server/migrations/ as idempotent NNNN_*.sql files, applied manually via Supabase dashboard or psql. No migration runner yet — revisit if the file count grows past a handful.

Configuration

Env vars (SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, SUPABASE_SECRET_KEY, SUPABASE_JWKS_URL, DATABASE_URL, GEMINI_API_KEY, STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, PUBLIC_BASE_URL, CORS_ORIGINS, WEB_APP_URL) live in DO App Platform's env store. SUPABASE_SECRET_KEY, DATABASE_URL, GEMINI_API_KEY, STRIPE_SECRET_KEY, and STRIPE_WEBHOOK_SECRET are marked encrypted (they embed secrets); the others (including PUBLIC_BASE_URL) are public-by-design and stored as plain (CORS_ORIGINS, the comma-separated browser origins allowed by CORS, and WEB_APP_URL, the web app's base for Stripe return URLs, are also public and plain — v6.1/v6.2). Local dev uses server/.env (gitignored); server/.env.example is the committed template. server/app/core/config.py reads them via pydantic-settings.

Packaging boundary

server/ is excluded from the Web Store zip by package.sh's allowlist. This packaging discipline replaces the repo split (see ADR 0010) as the mechanism keeping backend code out of end-user installs. Verify the zip layout at every release that touches packaging — if server/ (or its env files) ever sneak into the allowlist, backend code or secrets could leak into the bundle.

Data flow (current — client only)

  1. User opens WW jobs page. Content script injects sidebar and attaches MutationObserver to the postings table.
  2. User clicks Scan. Content script asks page-bridge to enumerate posting IDs via dataViewerApp.
  3. For each posting: content script fetches the posting HTML directly (cached tokens), forwards to background.
  4. Background calls Gemini with the posting + cvText + preferences. Receives {score, verdict, reason}.
  5. Background writes the score to ww_scores storage. Content script's storage listener triggers badge reinject and sidebar list re-render.

v4–v5 reshaped this. Step 4's Gemini call now runs in the backend: the extension sends the posting payload to POST /scan (debiting credits) and receives the scored result. The extension no longer holds the Gemini API key. As of v5.2 the result is { score (1–20), verdict, reason, breakdown[] } — verdict server-derived from the score and a hidden excluded flag into one of Strong Apply · Apply · Consider · Unlikely · Skip · Excluded (ADR 0017; authoritative contract in reference/api.html).

v6.1 adds a second client. The web app authenticates against the same backend with its own Supabase session and reads per-user data (e.g. GET /me, GET /credits/balance); it does not scan. Profile editing migrates to it over v6.2–v6.3, after which the extension reads match_criteria via GET /profile for the ADR 0018 pre-filter but no longer edits it (v6.4).

Security boundaries

  • API key never enters the content-script context. It lives in chrome.storage.local and is read only by the background service worker, which makes the outbound Gemini request.
  • page-bridge has no access to extension storage or background. Communication is one-way request/response via postMessage; the page cannot poke storage or trigger scans on its own.
  • welcome.html is loaded as an extension page (chrome-extension://...) — no CSP relaxation, no remote scripts.
