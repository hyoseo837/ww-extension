This file records decisions made during v03 phases. Append a new section after each phase commit. Record only crucial decisions or non-obvious choices — not a step-by-step log. See docs/v02-archive/history.html for the same pattern applied to v02.001 through v02.022.

v03.006 — Options page: (?) help icons (2026-05-22)

A single #opts-help-popover element is shared across all three ? buttons rather than one popover per button. The active key is tracked in dataset.open so clicking the same ? a second time closes it (toggle behavior). Click-outside dismissal reuses the document-level click handler pattern already present in the sidebar for the badge and help tooltips.

The popover is position: fixed positioned from the button's getBoundingClientRect() so it works regardless of scroll depth in the options page. Left position is clamped to keep it on-screen on narrow viewports.

The token usage help text deliberately avoids quoting current Gemini pricing numbers because these change; it describes the cost model (cached = 25% of normal input, included in the Input total) without hard dollar figures. The model help text includes approximate figures only as a rough order-of-magnitude guide, not as a commitment.

v03.005 — Sidebar empty-state guide (2026-05-22)

The plain "No jobs scored yet" text was replaced with a three-step guide card rendered inside the same <li class="ww-ext-empty"> element, so no structural change to renderSidebarList() was needed beyond the innerHTML swap.

Steps 1 and 2 use live checkmarks driven by a single chrome.storage.local.get(['apiKey', 'cvText']) call at render time, plus the existing chrome.storage.onChanged listener (already present for theme syncing) — no new listener was added. updateGuideSteps() is a no-op when the empty-state card is not in the DOM, so the listener is safe to leave active at all times.

The step number circles use the same Apply-green color token (--s-apply-bg, --s-apply-c, --s-apply-bdr) for the "done" state — consistent with the rest of the extension's positive-outcome visual language.

v03.004 — Sidebar controls restructure + help tooltip (2026-05-22)

#ww-ext-controls was a single flex-wrap: wrap block with no visual hierarchy. Switching to flex-direction: column with .ww-ext-section children (each with its own padding and a top border divider) lets sections be independently styled without breaking the existing event-listener bindings, which all target stable IDs.

"Save to Folder" was chosen as the second section name rather than "Filter" because the Score ≥ input and verdict pills are purely save-scoping controls — they do not filter the displayed result list. Grouping them under the same label as the Save/Clear buttons makes their purpose self-explanatory.

A separate #ww-ext-help-tooltip element was added rather than reusing #ww-ext-badge-tooltip. The badge tooltip is pointer-events: none (display-only), while the help tooltip may eventually contain links. Keeping them separate avoids coupling their display states and CSS. The click handler toggle-logic checks dataset.open so clicking the same ? twice closes it (instead of re-opening).

The header ? button reuses the same CSS selector group as the existing #ww-ext-settings and #ww-ext-close buttons (shared size/padding/hover style), keeping the three-button cluster visually consistent. Its ID is ww-ext-help-open to distinguish it from the in-controls .ww-ext-help-btn elements.

v03.003 — First-run welcome page (2026-05-22)

welcome.html is a standalone extension page (no separate JS bundle) with three numbered step cards, two CTA buttons, and a footer with creator, GitHub, and privacy links. It reads theme from chrome.storage.local on load to match the user's existing dark/light preference, avoiding a jarring mismatch on first install.

The onInstalled listener uses a welcomeShown storage flag rather than relying solely on details.reason === 'install' because dev reloads ("Update") also fire onInstalled with reason 'update' — the flag ensures the welcome tab never appears during development without explicitly clearing it.

chrome.tabs.create (used for both the install hook and the openWelcome message handler) does not require the tabs manifest permission — that permission gates reading tab properties, not creating tabs.
