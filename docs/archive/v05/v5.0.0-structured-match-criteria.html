Spec v5.0.0 — Structured match criteria

Goal

First v5 phase — the start of the scoring-quality pass. Today a user's match preferences are a single free-form textarea (user_profile.preferences), prepended to the Gemini prompt as "Candidate Preferences". The most important signal — whether the candidate is even eligible for a posting (work authorization) — gets buried in prose and is unreliable, especially for international students. v5.0.0 replaces the single textarea with structured fields and demotes the prose to an "additional notes" field, so the scorer gets clean, consistent eligibility/logistics signal. Storage shape and the migration approach are fixed in ADR 0013.

Scope is deliberately the structured-criteria foundation: the fields, their storage, and a faithful pass into the existing prompt. The richer prompt rewrite (co-op framing, calibration anchors, few-shot) and hard filters are later v5 threads that build on this. The Account-section consolidation is out of scope (held pending the external-site direction — see roadmap).

The criteria object

Stored as user_profile.match_criteria (JSONB), owned/validated by a backend Pydantic model. ADR 0013's JSONB choice holds — this richer weighted/graded shape supersedes the flat scalars/arrays sketched there. Two kinds of field:

Eligibility fact (not weighted)

work_authorization
Categorical, single value: "citizen" · "pr" · "international" (study permit) · "other" · or unset. This is the user's status, not a preference — so it has no weight or tiers. Hard filters (#4) compare it to a posting's requirement (e.g. a clearance role requiring citizenship → an international user is ineligible → hard Skip).

Weighted, graded preferences

Each preference below is an object, not a flat value: a weight plus up to four value tiers.

weight
"must" · "strong" · "nice-to-have" — how heavily this criterion moves the score.
preferred / acceptable / avoid / excluded
String arrays. preferred = ideal (full marks); acceptable = fine (no penalty); avoid = allowed but penalized; excluded = never. Values are user-entered strings the LLM maps a posting against, so fuzzy entries like "West Canada" work without an enum.

Applies to preferred_locations, work_modes, target_term, target_length, and languages (spoken/working, e.g. English, French — not programming languages). Example (location):

"preferred_locations": {
  "weight": "strong",
  "preferred":  ["Toronto"],
  "acceptable": ["Ontario"],
  "avoid":      ["West Canada"],
  "excluded":   ["outside Canada"]
}

How tiers + weight resolve

  • excluded matched → hard Skip, no credit (thread #4), at any weight.
  • avoid / unlisted → score penalty scaled by weight: nice-to-have = small nudge, strong = significant, must = heaviest — can sink the score into the Skip band, but it is still scored and shown with its breakdown, not auto-skipped.
  • preferred → full marks; acceptable → no penalty; an empty criterion → no preference, no effect.

Scope boundary: the credit-free hard Skip on excluded values and work-auth ineligibility is implemented in thread #4. v5.0.0 stores the full tiered criteria and serializes them into the prompt; until #4 lands, an excluded match shows up only in the LLM's score (it'll read as Skip) and still spends a credit.

Plus the existing preferences text, re-purposed unchanged as additional notes (free-form, the model weighs it as before). Old prose carries over with no data migration (ADR 0013).

Verify

  1. Apply 0006 → user_profile has a match_criteria JSONB column defaulting to {}; existing rows' preferences are untouched.
  2. GET /profile returns match_criteria (and preferences as notes); PUT /profile with a full object — work-auth + a weighted/tiered preference (weight + preferred/acceptable/avoid/excluded) — round-trips and persists. A bad work_authorization or weight value is rejected by the model.
  3. Options page shows the structured form; saving writes the criteria server-side; reloading repopulates every field. An existing user's old prose appears in "Additional notes".
  4. Run a real scan: the Gemini job part includes the serialized criteria block (verify via a logged prompt or a scan whose verdict reflects, e.g., a work-authorization mismatch). Cost is unchanged in shape (criteria add a few input tokens).
  5. Regression: a user with empty criteria scores exactly as before (no criteria block emitted, notes-only behaves like the old preferences).

Notes

  • languages = spoken/working. English, French, etc. — for bilingual-required postings; not programming languages / tech stack. Confirmed 2026-05-29.
  • No prompt rewrite here. v5.0.0 passes criteria into the existing prompt via deterministic serialization. Co-op framing, calibration, and few-shot examples are a separate v5 thread (#3), now unblocked by structured inputs + live scoring data.
  • Hard filters deferred. Auto-Skip on work-authorization mismatch (#4) builds on this column but is its own phase; v5.0.0 only makes the model aware of criteria.
  • Account section / external site untouched. Held pending the external-site direction (roadmap). v5.0.0 changes the Profile & Context page only.
  • Weighted/graded model raises the cost. The tiered, weighted criteria make the options-page form the heaviest part of this phase; the client step may itself need more than one sub-version (e.g. work-auth + simple fields first, then the weight/tier UI). Confirmed with the user 2026-05-29 over the original flat-field sketch.
  • Sub-version slicing. Order: backend (migration + contract + serialization) → client (the weighted/tiered form, which may itself split into more than one sub-version) → close-out. v5.0.0 was the spec/ADR/roadmap; v5.0.1 was v4-archive housekeeping. Exact Z numbers are assigned at build time.
