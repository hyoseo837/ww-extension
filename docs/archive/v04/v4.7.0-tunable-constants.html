Spec v4.7 — Tunable constants consolidation

Goal

Follow-up to the v4.6 MARGIN dial. Several other adjustable knobs were either duplicated across files (so changing one silently desyncs the other) or buried as bare literals. v4.7 pulls the server-side ones into single named constants so they are safe to adjust. No behavior change — every value keeps its current number.

The duplications that mattered:

  • Output-token caps were defined twice: the scan cap (1024) in both pricing.py (DEFAULT_MAX_OUTPUT_TOKENS) and gemini.py; the extract cap (8192) likewise. pricing.py uses its copy for the pre-debit estimate, gemini.py uses its copy for the actual call — so a change to one without the other makes the cost estimate wrong (over- or under-debiting before the refund corrects it). This is the real footgun.
  • Default model ("gemini-2.5-flash") appeared as a bare literal in scoring/routes.py's ExtractRequest.
  • Scoring temperatures (0.2 for scan, 0 for extract) were inline literals in gemini.py.
  • Signup bonus (100 credits) was a bare literal inside the grant_signup_bonus() plpgsql trigger.

Scope decisions (confirmed with the user 2026-05-29):

  • Client left as-is. The client model fallback ('gemini-2.5-flash' in content.js, background.js, options.js) is a low-risk fallback — the real source is the options-page model selector — and the client has no shared-module system (plain scripts, no "type":"module"), so true single-sourcing would mean an ES-module restructure. Not worth it now.
  • Signup bonus stays in SQL as a named constant inside the trigger function (a declare … constant int := 100), not moved to the app layer. Changing it is still a migration, but the amount is no longer buried in the insert.

Files

server/app/billing/pricing.py (changed)
Add a DEFAULT_MODEL = "gemini-2.5-flash" constant (sits with supported_models() / _RATES; it is one of the _RATES keys). Update the comments on DEFAULT_MAX_OUTPUT_TOKENS / DEFAULT_EXTRACT_MAX_OUTPUT_TOKENS to say gemini.py now imports them (this module is the single source).
server/app/scoring/gemini.py (changed)
Import DEFAULT_MAX_OUTPUT_TOKENS and DEFAULT_EXTRACT_MAX_OUTPUT_TOKENS from app.billing.pricing and use them as the max_output_tokens defaults in score() (was 1024) and extract_pdf() (was 8192) — removing the duplicate literals. (pricing.py imports only decimal, so no import cycle.) Add module-level _SCORE_TEMPERATURE = 0.2 and _EXTRACT_TEMPERATURE = 0.0 and reference them in the two generationConfig/generation_config blocks.
server/app/scoring/routes.py (changed)
ExtractRequest.model default "gemini-2.5-flash" → pricing.DEFAULT_MODEL (pricing is already imported). ScanRequest.model is unchanged — it has no default (the client always sends one).
server/migrations/0005_signup_bonus_constant.sql (added)
create or replace function public.grant_signup_bonus() with the body unchanged except a declared bonus_amount constant int := 100 used in the insert. Same security definer / search_path; the trigger itself is untouched. Migrations are append-only — 0001 is not edited.
server/pyproject.toml, manifest.json (changed)
Bump to 4.7.0.
docs/roadmap.html (changed)
Add a v4.7 entry (shipped) under the v4 phase arc.

No API, response-schema, or balance/ledger behavior changes.

Verify

  1. python -c "from app.billing import pricing; from app.scoring import gemini" imports cleanly (no cycle); a scan and an extract still produce the same estimate and actual cost as before (the numbers are unchanged).
  2. GET /health → 4.7.0 after deploy.
  3. Apply 0005 on a fresh test user → still granted exactly 100 signup-bonus credits (the partial unique index from 0001 still enforces one-per-user).

Notes

  • Single source = pricing.py for billing-coupled numbers. The output-token caps live there because that module computes the pre-debit estimate; gemini.py (the actual call) imports them. Keep new billing-relevant tunables in pricing.py so estimate and actual can never desync.
  • Not an ADR. This is mechanical consolidation, no new architectural constraint beyond the line above — recorded here in Notes, consistent with how the pricing dials are handled.
  • Single commit. Small, cohesive, server-only phase (spec + code + migration + version bump + roadmap) ships as one v4.7.0 commit rather than the multi-sub-version slicing a larger phase uses.
  • Deferred. Client-side model single-sourcing (needs an ES-module restructure), and moving the signup bonus to the app layer.
