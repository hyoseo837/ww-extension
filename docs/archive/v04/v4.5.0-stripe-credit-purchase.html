Spec v4.5 — Stripe credit purchase

Goal

Let users buy credits. Until now the only way to gain credits is the 100-credit signup bonus; once spent, a user is stuck. v4.5 adds Stripe Checkout purchasing with credits granted by a signature-verified webhook, plus a Buy-credits UI in the options-page Account section. The credit ledger already reserves kind = 'purchase' (v4.3), so this phase is additive — no existing endpoint or schema changes.

Decision rationale (payments shape, webhook-driven idempotent grants, amount-from-package_id) is in ADR 0012.

Packages (1:1). Three fixed bundles — $5 / $10 / $20 CAD → 500 / 1000 / 2000 credits. Since 1 credit = $0.01 CAD = 1 cent, the Stripe unit_amount (cents) equals the credit count for every package. No markup at purchase time; margin is already baked into per-scan pricing (v4.4). Amounts live as in-code constants and are sent as dynamic price_data — no Stripe Dashboard Products to manage.

Security invariant. The credit amount granted is derived server-side from package_id and carried only in Stripe-held metadata. The client never sends a credit or dollar amount; the webhook trusts only metadata it set at session creation. Idempotency is a partial unique index on the ledger's ref (the Stripe event id), mirroring the v4.3 signup-bonus index.

Auth carries over from v4.2: POST /credits/checkout uses Authorization: Bearer <jwt> via the existing current_user dependency. POST /webhooks/stripe is the one unauthenticated write path — gated instead by Stripe signature verification.

Files

Backend

server/migrations/0004_purchase_idempotency.sql (added)
Idempotent. Adds a partial unique index credit_ledger_entry_purchase_ref_unique on (ref) WHERE kind = 'purchase' so a replayed Stripe event (same event id in ref) cannot double-grant. Stripe event ids are globally unique, so a purchase-scoped unique on ref is safe and never collides with scan_debit/scan_refund rows whose ref is a scan UUID. Same pattern as the 0001 signup-bonus index.
server/app/billing/payments.py (added)
Named payments.py, not stripe.py, so it doesn't shadow the stripe package.
  • CREDIT_PACKAGES — dict keyed by package_id → {cad_cents, credits}: credits_500 / credits_1000 / credits_2000. cad_cents == credits by the 1:1 rule.
  • create_checkout_session(user_id, package_id) -> str — validates package_id; builds a mode="payment" Checkout session with dynamic price_data (currency cad, unit_amount = cad_cents, product_data.name = "<N> credits", qty 1); sets client_reference_id = user_id and metadata = {user_id, credits, package_id}; success_url/cancel_url point at {public_base_url}/credits/checkout/result?status=…. Returns session.url. The blocking Stripe SDK call runs in fastapi.concurrency.run_in_threadpool.
  • verify_event(payload, sig_header) — wraps stripe.Webhook.construct_event(…, settings.stripe_webhook_secret) (local crypto, no threadpool); raises on bad signature.
  • Stripe api_key set from settings.stripe_secret_key.
server/app/billing/db.py (changed)
Add grant_purchase(user_id, credits, event_id): inserts kind='purchase', ref=event_id, with ON CONFLICT (ref) WHERE kind = 'purchase' DO NOTHING. Acquires its own pool connection (the webhook runs outside the scan transactions).
server/app/billing/routes.py (changed)
  • POST /credits/checkout — authenticated. Body {package_id}; 400 on unknown package. Returns {url}. No credit movement.
  • POST /webhooks/stripe — unauthenticated (Stripe-only). Takes Request; reads raw await request.body() + stripe-signature header → verify_event (400 on bad signature). On checkout.session.completed with payment_status == "paid": reads metadata.user_id + metadata.credits, calls db.grant_purchase(…, event_id=event["id"]). Returns {"received": true} (200) for handled and ignored event types so Stripe stops retrying; lets DB errors surface as 500 so Stripe does retry.
  • GET /credits/checkout/result — unauthenticated HTMLResponse. Minimal landing page Stripe redirects to ("Payment received — return to the extension; your balance updates in a few seconds", and a cancel variant via ?status=cancel). Needed because Stripe requires an http(s) success_url and a chrome-extension:// URL is not allowed.
server/app/core/config.py + server/.env.example (changed)
Add stripe_secret_key, stripe_webhook_secret, public_base_url to Pydantic Settings. .env.example documents all three (test-mode sk_test_… / whsec_… hints; DO app URL for PUBLIC_BASE_URL).

Setup (external — user, not blocking the code)

No Stripe account exists yet, so code is written and merged first; integration testing (Verify steps 3–7) waits on these:

  1. Create a Stripe account; stay in test mode.
  2. Copy the test Secret key (sk_test_…) → STRIPE_SECRET_KEY.
  3. Create a webhook for checkout.session.completed: local via stripe listen --forward-to localhost:8000/webhooks/stripe; deployed via Dashboard → Webhooks → {DO_URL}/webhooks/stripe. Copy the signing secret (whsec_…) → STRIPE_WEBHOOK_SECRET.
  4. Set PUBLIC_BASE_URL (DO app URL, or http://localhost:8000 locally).
  5. Add the two secrets to server/.env (local) and the DO App Platform env store (encrypted); PUBLIC_BASE_URL stored plain.

Notes

  • Why no stripe_event table. The data-model previously anticipated one for idempotency. ADR 0012 chose the cheaper partial unique index on the ledger ref instead — it reuses the existing append-only + signup-bonus-index pattern and adds no new query surface. The trade-off: we record only the granting event, not the full payment funnel. Add the table later if audit needs grow.
  • Why the SDK call is wrapped in a threadpool. The stripe Python SDK is synchronous; create_checkout_session makes a blocking HTTP call to Stripe. Running it in run_in_threadpool keeps the event loop free. Webhook signature verification is local crypto and does not need it.
  • StripeObject has no .get() (v4.5.3 fix). In stripe-python v15, event["data"]["object"] and its metadata are StripeObjects, which support subscript (session["payment_status"]) and attribute access but not dict.get(). Calling .get() raises AttributeError, which 500s the webhook (and makes Stripe retry forever). Caught in local testing before deploy; the handler uses subscript access throughout.
  • Why grant on webhook, not redirect. The user can close the success tab or never reach it; the checkout.session.completed webhook is the only reliable signal of payment. The browser success_url is purely a UX landing page.
  • Balance refresh on focus. The webhook grants asynchronously, so the redirect can land before the credit row exists. Refreshing on options-tab visibilitychange (plus one delayed retry) avoids trusting the redirect and avoids a polling loop. Usually the grant is present within seconds.
