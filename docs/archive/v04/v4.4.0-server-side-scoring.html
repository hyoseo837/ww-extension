Spec v4.4 — Server-side scoring

Goal

Move every Gemini call (scoring + PDF profile extraction) from the extension to the backend. The backend holds a single server-owned Gemini API key, debits credits against the signed-in user before each call, refunds on failure or for the unused portion of the worst-case estimate, and returns the result to the extension. The extension no longer needs (or accepts) a user-provided Gemini API key for any scoring path.

This phase closes the v4 loop: auth (v4.2) → ledger (v4.3) → metered API calls (v4.4). After v4.4, every billable action is gated by a real-time balance check, and v4.5 can plug Stripe in to top up that balance.

Scoring prompts and tuning logic also move server-side as part of this — they ride along with the Gemini calls and stop shipping to end users via the Web Store zip (see roadmap, "Rationale for moving the backend off the client").

Backend

server/migrations/0002_scan.sql (added — v4.4.0)
Create public.scan for audit and idempotency: id uuid primary key (client-generated UUID, doubles as idempotency key), user_id uuid not null references auth.users(id) on delete cascade, model text not null, posting_id text (WW posting ID, nullable for PDF-extract scans), kind text not null check in ('scan','profile_extract'), status text not null check in ('pending','success','failed'), estimated_cost numeric(14, 6) not null, actual_cost numeric(14, 6) (filled on success; equals the net debit after the partial refund), response jsonb, usage jsonb (raw usageMetadata for audit), error text, created_at timestamptz not null default now(), completed_at timestamptz. Index on (user_id, created_at desc). RLS enabled with the same defense-in-depth pattern as credit_ledger_entry.
server/app/billing/pricing.py (added — v4.4.0)
Per-model Gemini rate constants and the cost-computation functions. Rates stored as Python Decimal in credits per token (= USD per token × USD→CAD factor × margin, pre-computed). One entry per model + token kind (input, cached_input, output). Exposes: estimate_scan_cost(model, input_tokens, max_output_tokens, cached_input_tokens=0) -> Decimal and actual_cost(model, usage_metadata) -> Decimal. Constants commented with their source (Google pricing page snapshot date + USD rate + CAD FX + chosen margin) so future calibration is auditable.
server/app/scoring/gemini.py (added — v4.4.0)
Async Gemini REST client backed by a single httpx.AsyncClient held by the FastAPI lifespan (HTTP/2 enabled, persistent connection pool). One function per Gemini call shape we use: score(model, system_text, cv_text, job_part, cache_name=None) -> (response_json, usage_metadata) and (v4.4.2) extract_pdf(model, pdf_b64) -> (text, usage_metadata). Lifts the request bodies essentially verbatim from the current src/background.js + src/options.js Gemini fetches so behavior is preserved. Backoff/retry ported from RETRY_DELAYS.
server/app/scoring/routes.py (added — v4.4.0)
POST /scan — authenticated. Request body: {scan_id: uuid, model: string, meta: {title, org}, description_text: string, posting_id: string}. Profile (cvText) and preferences are read server-side from the user's stored profile (added in v4.4.2 alongside PDF extract). Until v4.4.2, the request also carries cv_text and preferences inline — explicitly deprecated by v4.4.2. Flow:
  1. Begin transaction.
  2. INSERT scan row with status='pending', estimated_cost from pricing.estimate_scan_cost(...). ON CONFLICT (id) DO NOTHING — return the existing row (idempotent retry).
  3. Check SUM(delta) - estimated_cost >= 0 for the user. If not, mark scan failed; return 402 Payment Required with {error: 'insufficient_credits', balance, required}.
  4. INSERT a scan_debit ledger row of -estimated_cost, ref = scan_id.
  5. Commit; release the transaction before Gemini call to avoid holding a row lock during a slow external API.
  6. Call Gemini. On HTTP/parse/validation failure: open a new transaction, INSERT a scan_refund ledger row of +estimated_cost with ref = scan_id, UPDATE scan SET status='failed', error=..., completed_at=now(); return 502 Bad Gateway (or appropriate code).
  7. On success: compute actual = pricing.actual_cost(model, usage). If estimated - actual > 0, INSERT a scan_refund for the difference, same ref. UPDATE scan SET status='success', response, usage, actual_cost=actual, completed_at=now(). Return 200 {result: {score, verdict, reason}, cost, balance} — including balance spares the extension an extra /credits/balance roundtrip after every scan.
POST /profile/extract (v4.4.2) — authenticated. Multipart upload (PDF), or base64-in-JSON for simplicity if the multipart middleware adds friction. Same estimate-debit-call-refund pattern, but with kind = 'profile_extract' and the multimodal Gemini call shape. On success: stores the extracted text in the user's profile (see new public.user_profile table below) and returns {text, cost, balance}.
server/migrations/0003_user_profile.sql (added — v4.4.2)

server/app/scoring/cache.py (added — v4.4.3)

New columns on user_profile: cache_name text, cache_expires_at timestamptz (added via 0004_user_profile_cache.sql). Reduces input cost on batch scans by ~75% per Gemini's cached-input rate.

Performance

Adding the backend hop adds ~200–500ms of overhead per scan (two DB round-trips around the Gemini call) on top of the ~1s Gemini call itself. Concurrent users don't multiply this unless they collide on a shared bottleneck.

Baked into v4.4.0 / v4.4.1

  • httpx with HTTP/2 + a persistent client for Gemini calls (v4.4.0). Reuses TCP/TLS across scans, saves ~50–100ms of handshake per request, and gives connection pooling under load. One httpx.AsyncClient instance held by the FastAPI lifespan, same pattern as the asyncpg pool.
  • asyncpg pool max_size = 25 (v4.4.0, up from v4.3.0's default of 10). Each scan uses ~3 queries across two transactions; 25 lets ~8 concurrent scans run without pool waits, comfortably above expected peak.
  • Bounded-parallel scan loop in content.js (v4.4.1). Up to 5 scans in flight at once instead of strictly sequential. Roughly 5× speedup on batch wall time for a 50-job scan (~60s → ~12s). Concurrency limit picked to stay well below per-key Gemini paid-tier limits and well inside the asyncpg pool. Sequential was the right default in v3 with a free-tier user key (15 req/min); with a server-owned paid-tier key, the constraint is gone.
  • p50 / p95 scan-latency logging (v4.4.0). Every POST /scan emits a single structured log line with scan_id, model, total duration, and a breakdown (db_pre_ms, gemini_ms, db_post_ms). DO captures stdout — gives a rolling latency picture without standing up a metrics backend. Revisit if/when load justifies one.

Deferred until measurements demand them

  • Streaming Gemini responses back to the client. Cuts perceived latency for long scans (especially Pro) but adds significant complexity in both backend (SSE/chunked) and extension (incremental render). Worth it if p95 stays above ~3s.
  • Autoscaling / Pro DO tier. The Basic instance handles the expected UWaterloo-scale load. Bump only when concurrent-user logs show CPU or memory ceiling.
  • Async / queue-based scan execution. Return a scan_id immediately, settle the result via polling or a webhook. Useful at very high concurrency or when scans get expensive (longer Pro calls); not worth the state machine yet.
  • Gemini per-key rate limit headroom. Request a paid-tier quota bump from Google ahead of public launch. Free tier (15 req/min for Flash) is enough for dev/test; not enough for batch scans across multiple concurrent users.

Notes

  • Estimate-first, refund the unused portion. Pre-debit a worst-case (input + maxOutputTokens) so the balance check at the start of /scan is definitive — no two concurrent scans can collectively overdraft. On success, refund the difference between estimate and actual; on failure, refund the full estimate. Two ledger rows per scan when the refund fires, both keyed by the same scan_id in ref for auditable correlation.
  • Idempotency via client-generated scan_id. Extension generates a UUID per scan attempt and includes it in the request body. Backend uses it as the scan table primary key with ON CONFLICT DO NOTHING; on conflict, the existing row's response is returned without re-debiting or re-calling Gemini. Network glitches and SW restarts therefore can't double-charge.
  • Pricing constants live in code, not env. server/app/billing/pricing.py holds per-model per-token-kind credit rates. Each constant carries a source-date comment (Google pricing snapshot + USD rate + CAD FX + chosen margin) so future changes are auditable in git history. Re-pricing is a code change + redeploy, not a dashboard tweak — appropriate for something that affects every user's bill.
  • Single server-owned Gemini key. The backend bills Google for all users' usage; users see only credits. Set up via a dedicated Google Cloud project so billing is isolated from any personal projects. Stored as GEMINI_API_KEY in DO encrypted env.
  • Transaction discipline around external calls. Hold a DB transaction only for the balance check + debit ledger insert + scan row insert; commit before calling Gemini. After Gemini returns, open a fresh transaction for the refund/update. Keeps Gemini's 1–10s latency out of the row-lock window.
