v7.5.1 — Scan confirm: estimated cost + low-balance warning

Goal

Make the pre-scan confirmation tell the user how much a scan will cost and warn when their balance won't cover it. The confirmation itself already exists — confirmScan (v6.13, ext/src/content.js) gates the only credit-spending action, the bulk Scan All Jobs. There is no per-job / rescore path to gate (score-selected and rescore were removed in v7.3, ADR 0031). So the whiteboard "confirmation button for any credit uses" item was already satisfied; this phase upgrades the existing dialog rather than adding one.

Why

Today the dialog says only "This uses credits — you have {balance}". After the v7.4 re-margin a scan costs ~1 credit each (ADR 0034), so N unscored jobs ≈ N credits — but the user can't see that, and nothing warns them when, say, scanning 50 jobs on an 8-credit balance. That scan currently dies partway with a NO_CREDITS halt (handled, but after burning time and part of the balance). Surfacing the estimate and a low-balance warning + Buy-credits nudge up front is the fix.

Behaviour

Estimated cost is ~count credits (1 credit/scan; the real per-scan cost is token-variable, hence "~"). Let bal be the cached creditBalance.

CaseMessageButtons
bal unknown (null) "This costs ~N credits." Cancel · Scan N
bal ≥ count (covers it) "This costs ~N credits — you have B." Cancel · Scan N
bal < count (short) "This costs ~N credits — you have B." + warning line "⚠ Not enough to scan them all." Cancel · Buy credits · Scan anyway
  • Buy credits opens the web app at /buy (the existing openWebApp message, same path setActionPrompt uses for the out-of-credits halt) and dismisses the dialog as a cancel (resolves false — the user is navigating away, not scanning).
  • Scan anyway proceeds (resolves true); the existing NO_CREDITS halt still stops the batch when the balance runs out, so over-scanning is already safe.
  • Singular wording when count === 1 ("~1 credit").

Code changes

  • ext/src/content.js — confirmScan(count, balance): compute the estimate + insufficient flag, render the cost in the message, add the conditional warning line and the third (Buy credits) button wired to { type: 'openWebApp', path: '/buy' }. The confirmDialog helper (clear-scores) is untouched.
  • ext/src/sidebar.css — a .ww-ext-confirm-warn line (var(--s-error), the existing red) and a neutral third-button style (reuse the -cancel look for Buy credits). The -actions flex row already handles three buttons.
  • ext/manifest.json — version → 7.5.1.

Verify

  1. Scan with balance ≥ count: message shows "~N credits — you have B", two buttons, scans as before.
  2. Scan with balance < count: warning line shows, three buttons; Buy credits opens the web app /buy tab and cancels the scan; Scan anyway runs and still halts cleanly on NO_CREDITS.
  3. count === 1 reads "~1 credit" (singular).
  4. No second credit-spending path exists (grep for scoreJob / /scan — only the bulk loop), so the gate stays complete.

Notes

  • No ADR — this is a copy/UX refinement of an existing dialog, no new decision. The "~1 credit/scan" basis is ADR 0034.
  • No server/ change — the estimate is client-side; the authoritative charge stays server-side per scan.
  • Strike the stale "confirmation button for any credit uses" entry on the whiteboard once this ships (with the user's go-ahead — whiteboard is owner-edited).
