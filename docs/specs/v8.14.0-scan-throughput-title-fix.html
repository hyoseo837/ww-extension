v8.14 — Scan throughput & title fix

Goal

Two findings from owner live use (2026-06-14): scans run too slowly, and some postings fail the /scan call with HTTP 422 string_too_long on meta.title (cap 300). The 422 value was job-description prose ("We're modernizing the internal applications…"), not a title — the extension's off-page title fallback grabs the wrong element. Fix both: raise concurrency and stop garbage landing in the title field.

  1. Concurrency 5 → 10, with a cache warm-up — SCAN_CONCURRENCY (core.js) goes from 5 to 10. But the backend leans on Gemini's implicit context cache (gemini.py sends a fixed systemInstruction + <candidate_profile> prefix on every /scan; pricing.py bills the cheap rate on cachedContentTokenCount). Implicit cache is populated by the first request with that prefix, so a flat 10-wide launch makes the first 10 scans all cache misses every batch — and a batch of ≤10 gets no cache benefit at all. So runScan primes the cache: run the first scan alone, then fan out to the 10-worker pool for the rest. One cold scan per batch instead of ten. See ADR 0051.
  2. Title-extraction fix (the 422 root cause) — the scan loop sources meta.title from, in order: the visible job-table row (rowInfo.title, authoritative), else extractedTitle from the fetched overview HTML, else #postingId. The row map only covers the currently visible page, but a scan runs over all posting ids across all pages (onSelectAll), so off-page postings rely on the fallback — and the fallback, doc.querySelector('h1, h2, h3'), grabs whatever the first heading is, which on some postings is description prose, not the title. Fix:
    • fetchPostingText collapses whitespace on the extracted heading and rejects it as a title if it is implausibly long (a real job title is short; a multi-sentence "heading" is prose) — returns '' so the meta builder falls through to #postingId rather than sending a paragraph.
    • The meta builder hard-truncates title and org to META_CHAR_CAP (200) before sending — a guarantee no source (row, heading, future change) can blow the server cap.
  3. Server cap as defense-in-depth — _MAX_META_CHARS (scoring/routes.py) goes 300 → 400 (comfortably above the client's 200 truncation). The validation stays; this is the backstop, not the fix. Test updated to assert against _MAX_META_CHARS rather than a literal.

Notes

  • The warm-up is best-effort: if the first scan is a non-halt failure (fetch/Gemini error), the cache may not be primed, but the batch still fans out. A halt on the first scan (no credits / not signed in / profile unset) short-circuits before any fan-out, as before.
  • The proper off-page title source would be a per-posting field from the overview DOM, but that DOM's title element isn't documented and varies by board; the length guard + #id fallback is the minimal-code fix that kills the 422 and keeps titles sane without depending on an unverified selector.
  • Concurrency 10 also raises parallel load on WaterlooWorks' overview fetch and on the backend → Gemini. Both are per-user and modest; no server-side change needed.
