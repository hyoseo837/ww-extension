Spec v4.3 — Credit ledger (balance read-only)

Goal

Stand up the credit ledger as the system of record for per-user credits. Ship an append-only credit_ledger_entry table in Supabase, an auto-grant of N free credits when a user first signs in, and GET /credits/balance on the backend. The extension fetches the balance after sign-in and renders it in the sidebar header and the options-page Account section.

Read-only in v4.3. Debit-on-scan and refund-on-failure are deferred — likely folded into v4.4 (server-side scoring) where the debit naturally happens server-side at the moment Gemini is called, removing the need for a client-driven debit/refund handshake. Scoring continues to use the user's own Gemini key in this phase.

Unit model. 1 credit = $0.01 CAD (customer-facing currency; target audience is UWaterloo co-op students). Gemini's per-token rates are USD, so v4.4's pricing constants apply a USD → CAD factor on top of the raw rates plus margin. The ledger stores delta as NUMERIC(14, 6) so per-scan and per-PDF costs can be priced from real token usage as exact fractions of a credit (e.g., a typical Gemini Flash scan lands around 0.07–0.14 credits at the current FX). One credit type only — every billable API call (scan, PDF extract, future features) draws from the same pool. Per-token pricing constants land with v4.4 when the backend starts seeing real token counts.

Auth stack from v4.2 carries over: every credits call uses Authorization: Bearer <jwt>, verified via the existing current_user dependency.

Files

Backend

server/migrations/0001_credit_ledger.sql (added)
Idempotent SQL: create public.credit_ledger_entry (UUID PK, user_id FK to auth.users(id) ON DELETE CASCADE, delta NUMERIC(14, 6) NOT NULL, kind text NOT NULL CHECK in ('signup_bonus', 'admin_grant', 'purchase', 'scan_debit', 'scan_refund'), ref text NULL, created_at timestamptz DEFAULT now()); index on (user_id, created_at DESC); partial unique index on (user_id) WHERE kind = 'signup_bonus' (defense-in-depth against double-grant); row-level security enabled, SELECT policy auth.uid() = user_id; no INSERT/UPDATE/DELETE policies — only the backend's service-role connection writes. Trigger on auth.users AFTER INSERT inserts a signup_bonus row with delta = 100 (hardcoded in the trigger function; changing it requires a follow-up migration).
server/app/billing/db.py (added)
Async Postgres pool initialized from a new DATABASE_URL env var. Use the Supabase direct connection (port 5432, not the transaction pooler on 6543) so asyncpg's prepared-statement cache works without extra configuration. Backend uses the Postgres service-role credentials and bypasses RLS. Helper get_balance(user_id) returning SELECT COALESCE(SUM(delta), 0) FROM credit_ledger_entry WHERE user_id = $1 as a Python Decimal; the handler serializes it to a JSON number (e.g., 100.000000 → 100).
server/app/billing/routes.py (added)
GET /credits/balance — authenticated; returns {balance: number} (JSON number, may be fractional once debit lands) from billing.db.get_balance(claims["sub"]).

Verify

  1. GET /health still returns 200 with the expected payload (regression check after billing router mounted).
  2. Applying 0001_credit_ledger.sql to a fresh Supabase project succeeds; rerunning it is a no-op (idempotent).
  3. Signing in with a brand-new Google account causes the trigger to insert one kind = 'signup_bonus' row of delta = 100. Verified by dashboard SQL.
  4. Manually re-running the bonus INSERT against the same user_id errors on the partial unique index (defense-in-depth).
  5. GET /credits/balance with no Authorization header returns 401.
  6. GET /credits/balance with a valid Supabase session JWT returns 200 with {balance: 100} for a freshly signed-up user.
  7. Inserting a fractional ledger entry (e.g., delta = -0.075000, kind = 'scan_debit') via dashboard SQL changes the balance returned by the endpoint to 99.925 — confirms NUMERIC precision survives the SUM and the JSON serialization.
  8. RLS holds: a service-role connection sees all rows; a user-role connection signed in as user A sees only A's rows; user A cannot SELECT user B's rows.
  9. Extension Account section (Settings tab) displays creditBalance; signing out clears the value; signing in re-fetches and re-renders (v4.3.1+).
  10. Sidebar credits chip on the WW jobs page renders the same value as the Account section and updates live when storage changes (v4.3.1+).

Notes

  • Why append-only ledger over a balance row. v4.4 will introduce debit/refund pairs that need to correlate via ref (scan UUID). A SUM-over-ledger reads fine for a single user up to many thousands of scans; if read latency ever matters we can add a materialized balance row later without touching the ledger schema.
  • asyncpg over supabase-py / SQLAlchemy. One backend service that owns its schema and bypasses RLS via service-role — no need for PostgREST or an ORM. asyncpg keeps the query surface visible (raw SQL in the few helpers we need) and the dependency set small. Promote to an ADR if a second backend feature also picks asyncpg.
  • Signup bonus via trigger, not API call. Triggering on auth.users INSERT means the row exists before the user's first authenticated request, eliminating a first-request race and keeping the /credits/balance handler trivial. The bonus amount (100, i.e. $1 CAD) is hardcoded in the trigger function — changing it is a new migration. The value moves rarely enough that coupling it to an env var or a GUC isn't worth the extra plumbing.
  • NUMERIC(14, 6) over INTEGER. Single credit pool, CAD-anchored, fractional-by-design: token-priced scans and PDF extracts produce cost values that don't fit whole credits. 6 decimal places (micro-cent precision) is more than enough for token-rate math; the 14-digit total gives ~14M displayed-credit headroom per row, far beyond any realistic single transaction. SUM-over-NUMERIC is exact in Postgres — no float drift, no rounding-to-money issues when v4.5 reconciles purchases against Stripe.
  • RLS configured but not relied on. The backend uses service-role credentials and bypasses RLS for its own queries. RLS is still enabled as a defense-in-depth measure: if a future feature accidentally exposes a user-role connection to a request handler, users still cannot read others' rows.
  • Sub-version slicing.
    • v4.3.0 — backend only: migration, asyncpg pool, /credits/balance, api.html + data-model.html docs updates. No extension changes; manifest bumps to 4.3.0 to keep the version in lockstep with pyproject.toml per ADR 0002.
    • v4.3.1 — extension wiring: background refreshBalance, Account section display, sidebar chip.
    • v4.3.2 — close-out: spec → done, architecture.html updated, manifest bump.
  • Out of scope (deferred). Debit-on-scan, refund-on-failure, admin-grant endpoint, Stripe purchase, balance display on the welcome page. The first two land with v4.4 server-side scoring; the rest are scheduled in later phases per roadmap.
