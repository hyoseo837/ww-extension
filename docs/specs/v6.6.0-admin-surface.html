v6.6.0 — Admin surface (operator console)

Goal

Add an operator-only admin console: list/inspect users (balance, credit ledger, scan activity) and issue manual gift-credit grants (goodwill, support make-goods, promos). Grants ride the existing append-only ledger as kind='admin_grant' (already in the ledger CHECK constraint, migration 0001) — balance derivation (SUM(delta)) is unchanged and every grant is auditable. Admin authZ is an env allowlist of admin user_ids enforced in a FastAPI dependency, so the credit-mutating endpoint is locked server-side, not merely hidden in the UI. Matches the admin_dashboard_sidebar Stitch screen. Decisions in ADR 0025.

Sliced into two commits: v6.6.0 (backend: authZ, admin endpoints, gift grant + audit migration) and v6.6.1 (web: the /admin page). This spec covers both.

Endpoints (new, all admin-gated → 403 for non-admins)

  • GET /admin/stats → { total_users, total_credits_issued, credits_used_24h } (aggregates over auth.users + credit_ledger_entry).
  • GET /admin/users?search=&limit=&offset= → { users: [{ user_id, email, created_at, balance }], ... }; search is an email ILIKE.
  • GET /admin/users/{user_id} → { user_id, email, created_at, balance, profile: {cv_ready, summary?}, history: [...], scans: [{id, kind, status, org, title, cost, created_at}] } (history reuses the scan-merged shape).
  • POST /admin/grant body { email, credits, reason } → resolve email→user_id (404 if unknown, 400 if credits ≤ 0), insert one admin_grant ledger row (created_by = admin, note = reason) → { user_id, balance }.

Verify

  1. Migration 0009 applies cleanly and is idempotent; existing rows have NULL created_by/note; balances unchanged.
  2. With ADMIN_USER_IDS set to a test admin uid: that user's bearer token reaches all /admin/* endpoints; a non-admin token gets 403 on every one (including POST /admin/grant — server-side lock, not UI-only).
  3. POST /admin/grant adds credits to the target user's balance, writes one admin_grant row with the granting admin in created_by and the reason in note, and the grant shows in that user's /credits/history.
  4. Web /admin matches the Stitch screen for an admin (stat cards, searchable user table, gift form that grants and refreshes); a non-admin sees an access-denied state.
  5. cd web && npm run build clean; /health reports the bumped server version.

Notes

No new ledger kind. admin_grant was reserved in migration 0001 and already passes through get_history / HistoryList (its card_giftcard icon and "Admin grant" label exist). Only the audit columns are new.

Design copy is illustrative. The screen's +12% since last week and the Activity Logs / System Settings nav items are not built — the console is one dashboard page (stats + users + gift). Stat cards show real aggregates.

Service-role DB access. The backend pool already bypasses RLS, so admin queries can read auth.users and any user's ledger/scan rows directly; authZ is the env allowlist, not RLS.
