v6.2.0 — Account + credits on web

Goal

Turn the v6.1 bootstrap shell into a real, routed account surface: view balance, browse full credit history, and buy credits via Stripe Checkout that returns to the web app (not the chrome-extension result shim). The extension's existing checkout path is left untouched — it keeps using the shim until the v6.4 slim-down. Backend gains one read endpoint (GET /credits/history) and a web-aware success_url on checkout; the rest is the React app.

Notes

Why no ADR. The web success_url is an additive, back-compatible extension of the Stripe flow (ADR 0012) — the client field defaults to the existing extension behavior. Recorded here, not as a new decision.

History detail is intentionally shallow. Each row shows date, a humanized kind (Purchase / Signup bonus / Scan / Scan refund / Admin grant), and the signed credit amount. Joining scan for per-posting labels (e.g. the job title) is deferred — posting_id is available but the title isn't stored, and it isn't worth a join for v6.2.

Routing anticipates v6.3. Per the user's call, the profile editor splits into separate pages: /profile (CV upload + experiences/projects) and /preferences (match criteria), rather than one screen. v6.2 builds only /account, /billing, /buy; the nav gains /profile + /preferences when v6.3 builds them.

Packages unchanged. The live three (500/$5, 1000/$10, 2000/$20, strictly 1:1) are surfaced as-is; any repricing or bulk-discount tier is a separate pricing decision (would touch payments.py and the 1¢=1-credit invariant).

Styling is a baseline, not the final design. The Stitch design pass (warm, cozy, Claude-like light theme) lands later and will be reconciled into index.css tokens, then propagated to the extension sidebar and options page.

Refinements (v6.2.3+) — credit-history readability

The first history cut (raw ledger rows) was too noisy and too thin. Three changes, decided 2026-05-31:

  • One net row per scan. get_history sums each scan's scan_debit + scan_refund into a single net item (−14.16 + 11.85 → −2.31); fully-refunded (net-0, failed) scans are dropped.
  • Richer descriptions. Migration 0008_scan_meta_batch.sql adds title/ org to scan (stored from the /scan meta); history shows "Scan · Org" for postings and "Extract application package" for profile_extract. Old rows (no org) fall back to "Scan · job posting".
  • Batch grouping. The same migration adds batch_id; the extension generates one id per Scan run and sends it on every /scan in that run. The web client collapses consecutive same-batch scan items into an expandable "Scanned N jobs · net" group. Decision: a stored batch id (not a time-window heuristic) — exact grouping; applies to scans done after the change.

Slices: v6.2.3 backend (migration, /scan stores meta + batch_id, get_history rewrite, api.html) · v6.2.4 extension (per-run batch_id) · v6.2.5 web (merged descriptions + collapsible batch groups). Additive and back-compatible — no ADR.
