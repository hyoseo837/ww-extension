v6.1.0 — Web app bootstrap

Goal

Stand up the web app skeleton and prove the end-to-end auth round-trip before any account/profile features are built on it. Scaffold web/ as a Vite + React + TypeScript SPA (ADR 0019), wire Supabase Google sign-in (ADR 0021), and ship a deliberately minimal signed-in shell that makes one authenticated backend call. Deploy it to ww-extension.hyoseo.dev on Vercel (ADR 0022) and open the backend's CORS to the new origin.

The success condition is narrow and structural: from the deployed web origin, a user can sign in with Google, and the SPA can call an authenticated FastAPI route with the resulting Supabase JWT and render the response. That validates the SPA → Supabase → FastAPI chain (build, auth redirect, CORS, bearer token) that every later v6 web phase rides on. No account management, profile editing, payments, routing, or landing page in this phase — those are v6.2–v6.5.

Verify

  1. Build. cd web && npm install && npm run build produces web/dist/ with no TypeScript errors. npm run dev serves at http://localhost:5173.
  2. CORS. A preflight OPTIONS to an authenticated route from the web origin returns the Access-Control-Allow-Origin header; an authed GET /me from the browser succeeds with no CORS error in the console.
  3. Local round-trip. With web/.env set and localhost:5173 in Supabase redirect URLs + backend CORS: clicking "Sign in with Google" runs the OAuth redirect, returns signed-in, and the shell renders the user's email (GET /me) and balance (GET /credits/balance).
  4. Deployed round-trip. https://ww-extension.hyoseo.dev loads over TLS; the same sign-in → email + balance flow works against the live backend.
  5. No secrets in the bundle. Grep web/dist/ for any sk_ / secret key —none present; only the publishable Supabase key and the API base URL.
  6. Packaging untouched. ./package.sh still produces a zip with no web/ (or server/) contents.
  7. Extension unchanged. The unpacked extension still loads and scans; manifest.json reads "version": "6.1.0".

Notes

External setup checklist (operator steps, prerequisites — not code; track in web/README.md):

  • Create a Vercel project pointed at this repo's web/ dir (build npm run build, output dist).
  • Cloudflare DNS: CNAME ww-extension → Vercel, set DNS-only (grey cloud) so Cloudflare doesn't double-proxy Vercel's TLS.
  • Supabase Auth → Redirect URLs: add https://ww-extension.hyoseo.dev and http://localhost:5173. If Supabase uses the project's own Google OAuth creds, mirror the authorized origins/redirects in the Google Cloud console.
  • Vercel env vars: VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, VITE_API_BASE_URL (= the DO backend URL).
  • DO App Platform env: set CORS_ORIGINS to include the prod web origin.

Scope boundary. The shell is a smoke test, not a feature. Account/credits UI is v6.2, profile editor v6.3, landing page v6.5. No router this phase — a single auth-gated view needs none; add react-router when v6.2 introduces a second route. Keep the React code minimal (ADR 0003 still governs within the app): no state library, no component kit until a real need appears.

Independent sessions (ADR 0021). This phase touches only web/ and server/ — the extension is untouched and keeps its own session. The "Manage account →" deep link from the extension lands in v6.4, once the web app has something to manage.

Deploy coupling. The server/ CORS change triggers a DigitalOcean redeploy (expected). Web deploys are independent (Vercel, on web/ changes). Confirm the backend stays healthy (GET /health) after the CORS deploy.

Preview deployments. Vercel previews get rotating URLs not in the CORS/redirect allowlists, so auth/API won't work there by default. For this phase, treat previews as build-only and exercise auth on production; a deliberate preview-wildcard allowance can come later if wanted.
