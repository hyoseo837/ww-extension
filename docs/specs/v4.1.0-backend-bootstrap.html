Spec v4.1.0 — Backend bootstrap

Goal

Stand up the backend repo and ship a minimal deployed FastAPI service: /health endpoint returning 200, a Supabase project configured with Google OAuth, and the feature-grouped folder skeleton in place. No client-side code changes in this repo — extension wiring follows in v4.2. This phase is the foundation for every later v4 phase.

Stack and platform are fixed by ADRs: 0007 (DO App Platform), 0008 (Supabase auth + DB), 0009 (FastAPI).

Verify

  1. The deployed backend URL responds 200 OK on GET /health with a JSON body containing the service name and a build/commit identifier.
  2. The Supabase project's Google OAuth provider is configured; a manual sign-in via the Supabase dashboard's test flow returns a valid session JWT.
  3. The backend repo's folder layout matches the feature-grouped convention from ADR 0009.
  4. docs/reference/api.html in this repo documents GET /health with the actual response shape (no longer a placeholder).
  5. docs/architecture.html's backend section names the stack, deploy target, and backend repo URL — no remaining "TBD" markers in that section.

Notes

  • This repo's specs only cover the client-visible surface. Detailed backend work (routes, schemas, env config) is tracked in the backend repo's own specs/ADRs.
  • Backend repo name is WW-extension-backend (locked at v4 planning). Create at phase start; record the URL in architecture.html and api.html once the repo exists.
  • Region selection (DO + Supabase) is a load-bearing call for cross-vendor latency — match regions deliberately and document the choice in the backend repo.
  • No extension code changes in this phase. The version bump (v4.1.0) is a doc-only commit in this repo.
