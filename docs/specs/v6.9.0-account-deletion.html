v6.9.0 — Self-serve account deletion

Goal

Let a signed-in user delete their own account and all associated data (the data-subject right to erasure) — the companion to the v6.14 export (access/portability). Unblocked 2026-06-01: ADR 0027 is accepted (hard delete, Stripe as financial record), and the coupled signup-bonus farming concern is resolved by ADR 0029 (a retained one-way email hash). Implemented under the v6.9 phase (commits v6.9.1 server / v6.9.2 web).

Mechanism

Every app table is ON DELETE CASCADE on auth.users(id) — user_profile (mig 0003), credit_ledger_entry (mig 0001), scan (mig 0002). So deleting the Supabase auth user atomically removes all app data; no per-table delete is needed. Deletion happens via the Supabase Auth admin API, which requires the service-role key the backend already holds (supabase_secret_key) — the browser can't do this itself.

Signup-bonus suppression (ADR 0029)

The 100-credit bonus is granted by a trigger on auth.users insert, keyed per auth-row — so a hard delete + re-register would re-grant it. To make the bonus once-per-person:

  • New table signup_bonus_block (email_hash text primary key, created_at) — migration 0010.
  • Before deleting the auth user, the backend inserts encode(digest(lower(email), 'sha256'), 'hex') (email from the verified JWT) into signup_bonus_block (on conflict do nothing). Only the hash is stored — no plaintext email.
  • Migration 0010 amends grant_signup_bonus() to return new (skip the grant) when sha256(lower(new.email)) is already in the block table. The 100-credit constant (mig 0005) is preserved.
  • pgcrypto provides digest; create extension if not exists pgcrypto in the migration.

Ordering matters: insert the block row first, then delete the auth user (afterward the email is gone). If the Supabase delete then fails, the user isn't deleted but a block row exists — harmless (they keep their existing bonus; a future re-register, which can't happen without deleting, would be suppressed). Acceptable for a rare, retryable action.

Files

Server

  • migrations/0010_signup_bonus_block.sql — the block table + amended trigger function + pgcrypto.
  • app/account/routes.py — authenticated DELETE /account: read sub + email from the JWT, insert the block hash, then call the Supabase admin delete (DELETE {supabase_url}/auth/v1/admin/users/{sub} with the service-role key via a one-off httpx request — httpx is already a dependency). Returns 204.
  • app/account/db.py — block_signup_bonus(email) (insert the hash). Keeps the route free of raw SQL; reuses billing.db.pool.
  • pyproject.toml — version bump (server touched, ADR 0010).

Web

  • src/pages/Account.tsx — a "Danger zone" section with a Delete account action → a confirm modal that states what is removed and is irreversible, and requires typing DELETE to enable the button → calls the endpoint → signOut() (the session re-render drops the user to the landing).
  • src/api.ts — add an apiDelete helper (no JSON body, tolerates a 204/empty response).
  • src/pages/legal/Privacy.tsx — disclose the retained email hash (ADR 0029): on deletion we erase everything except a one-way hash of the email kept solely to prevent repeat signup bonuses.

Docs

  • docs/reference/api.html — document DELETE /account (auth, cascade scope, block-hash, 204, errors).
  • docs/architecture.html — note the deletion path + block table.

Verify

  1. A test user deletes their account → the auth.users row is gone and (by cascade) their user_profile, credit_ledger_entry, and scan rows are gone; a signup_bonus_block row (hash only) remains.
  2. The user is signed out and lands on the logged-out page; the deleted session can no longer call authenticated endpoints (401).
  3. Signing in again with the same Google account creates a fresh user with an empty profile and NO signup bonus (the block hash matched) — farming closed.
  4. A brand-new, never-deleted account still receives its 100-credit bonus exactly once.
  5. Only the authenticated user can delete their own account (the endpoint keys on sub; no cross-user deletion). npm run build and a server import check pass.

Notes

Stripe customer. Deleting our user does not touch Stripe; financial history persists there (ADR 0027). Leaving / PII-minimizing the Stripe customer object is an implementation detail, not done in this phase.
