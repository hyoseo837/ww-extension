v6.9.0 — Self-serve account deletion

Goal

Let a signed-in user delete their own account and all associated data (the data-subject right to erasure). The deletion policy — hard delete, relying on Stripe as the financial system-of-record — is in ADR 0027 (proposed: confirm the retain-financials question before implementing). This phase is specced, not yet built.

Mechanism

Every app table is ON DELETE CASCADE on auth.users(id) — user_profile (mig 0003), credit_ledger_entry (mig 0001), scan (mig 0002). So deleting the Supabase auth user atomically removes all app data; no per-table delete is needed. Deletion happens via the Supabase Auth admin API, which requires the service-role key the backend already holds (SUPABASE_SECRET_KEY) — the browser can't do this itself.

Files (planned)

Server

  • app/auth/routes.py (or a new app/account/) — authenticated DELETE /me (or POST /account/delete): verify the JWT, then call the Supabase admin delete for user["sub"] via httpx (DELETE {SUPABASE_URL}/auth/v1/admin/users/{id} with the service-role key — no new dependency; matches the existing httpx use). Cascade clears app rows. Returns 204.
  • pyproject.toml — version bump (server touched, ADR 0010).

Web

  • An account/"Danger zone" section (on /account or a new /settings) with a Delete account action → a confirm modal that states what is removed and is irreversible, and requires a deliberate confirmation (type the email or the word DELETE) → calls the endpoint → signOut() + redirect to the landing.
  • src/api.ts — add a DELETE helper if needed.

Docs

  • docs/reference/api.html — document the delete endpoint (auth, cascade scope, 204, errors).
  • docs/architecture.html — note the deletion path.

Verify

  1. A test user deletes their account → the auth.users row is gone and (by cascade) their user_profile, credit_ledger_entry, and scan rows are gone.
  2. The user is signed out and lands on the logged-out page; the deleted session can no longer call authenticated endpoints (401).
  3. Signing in again with the same Google account creates a fresh user (new signup bonus, empty profile) — no resurrected data.
  4. Only the authenticated user can delete their own account (no cross-user deletion); admins may also delete via the admin surface if wired.

Notes / open questions

Blocked on ADR 0027 sign-off. If the user decides any financial records must persist in our DB (not just in Stripe), the mechanism changes from hard-delete to anonymize-in-place (scrub PII: email/CV/profile; keep de-identified ledger rows) — a larger build. The current spec assumes hard delete.

Stripe customer. Deleting our user does not touch Stripe; whether to also delete/anonymize the Stripe customer is an implementation detail decided alongside ADR 0027.

Companion: data export. The "download my data" right (v6.10) pairs naturally with deletion; out of scope here.
