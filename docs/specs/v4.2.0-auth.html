Spec v4.2 — Auth in the extension

Goal

Wire end-to-end authentication: extension signs in with Google via Supabase OAuth, stores the session JWT, sends it as Authorization: Bearer to the FastAPI backend. Backend verifies the JWT against Supabase JWKS and exposes GET /me returning user identity.

Sign-in is optional in v4.2 — the extension still scores via the user's own Gemini key. The hard sign-in-or-no-scoring gate ships at v4.4 (server-side scoring).

Stack already locked. New ADR may follow if token refresh strategy turns out to be load-bearing.

Verify

  1. GET /health still returns 200 with the expected payload (regression check after auth router mounted).
  2. GET /me with no Authorization header returns 401 with WWW-Authenticate: Bearer.
  3. GET /me with a malformed/expired/unsigned JWT returns 401.
  4. GET /me with a valid Supabase session JWT returns 200 with {user_id, email}.
  5. Extension manifest loaded by Chrome resolves to the fixed ID ceobdeelponblelbcbbnojfjijheffpi.
  6. Options page Settings tab shows the Account section (v4.2.1+).
  7. "Sign in with Google" opens the Supabase OAuth flow, lands on Google's account picker, and returns to the extension via chrome.identity.launchWebAuthFlow (v4.2.1+).
  8. After sign-in, the Account section displays the user's email; Sign out clears the session and the UI reverts to the Sign in button (v4.2.1+).
  9. Access token expiry triggers a refresh-token roundtrip and the original request succeeds (v4.2.2+).

Notes

  • Extension ID is locked. The manifest "key" deterministically produces ceobdeelponblelbcbbnojfjijheffpi. OAuth redirect URL is therefore https://ceobdeelponblelbcbbnojfjijheffpi.chromiumapp.org/.
  • Supabase dashboard prep (before v4.2.1). Authentication → URL Configuration → Redirect URLs must include the chromiumapp.org URL above. Without it, Supabase refuses to redirect back after OAuth completes.
  • Token refresh strategy (v4.2.2). Supabase access tokens expire ~1 hour. Refresh tokens are long-lived. Store both in chrome.storage.local; on 401 from backend, call Supabase token endpoint with the refresh token, replace stored tokens, retry once. Background service worker owns this logic so the UI doesn't see expiries.
  • Why JWKS, not the JWT secret. Supabase moved to asymmetric signing (ES256/RS256). FastAPI fetches public keys via the well-known JWKS URL; no shared secret stored on the backend. See ADR 0008.
  • Sign-in stays optional in v4.2. Existing users without an account keep scoring via their own Gemini key. v4.4 will gate scoring on a valid session.
