v7.3.0 — Redesign + integration polish

Goal

Post-approval only. With the extension published (v7.2) and Stripe live, bring the extension UI up to the sidebar design sheet and tighten how it hands users off to the web app. This is the riskier rewrite the v7 sequencing deliberately put after the Web Store gate — don't start it while v7.2 is in review, because it changes the very artifact under review.

Five strands, all on the extension client (no server/ change expected):

  1. Sidebar redesign to match ext/design/extension_sidebar_job_scan/ (warm editorial, card-per-posting with score chip + verdict + reason snippet + save-to-folder).
  2. Light-mode only — drop the dark/light theme toggle and the dark tokens; one set of tokens in sidebar.css.
  3. Minimal options page — reduce to a sign-in/account state + the auto-skip (hard-filter) toggle. The Model tab is removed (scoring is Flash-only, ADR 0031).
  4. Toolbar entry → web app — the action icon opens (or a small popup redirects to) the web app rather than the options page.
  5. welcome.html → thin launcher — a big Set up your profile → deep link to the web app; the detailed how-to moves into the sidebar empty-state guide.

Plus removals: drop score-selected and rescore (per roadmap), and tighten the extension↔web flows — sign-in deep links, buy / out-of-credits nudges, and profile_not_set routing all pointing cleanly at the web app.

Decisions to record (ADRs)

Significant calls here that a future agent would otherwise re-debate — write each as an ADR before/with the code (numbering continues from 0031):

  • Light-mode only — dropping the theme toggle and dark tokens (removes a stored theme key + its storage.onChanged consumer). Why: design sheet is light; one token set is simpler; matches the "minimal" direction.
  • Toolbar action behavior — popup vs. direct chrome.tabs.create to the web app, and what happens to options_ui / action: {} in the manifest.
  • (Possibly) removing rescore / score-selected if it changes a stored contract or user-visible guarantee; otherwise a spec Note is enough.

Notes

  • Scale mismatch in the mockup: the design screen.png shows single-digit scores (9, 4, 7, 8) on what reads as a 1–10 scale. The live product scores 1–20 with a six-verdict ladder (ADR 0017). Port the visual style, but keep the real 1–20 score + Strong Apply / Apply / Consider / Unlikely / Skip / Excluded verdicts — do not regress the scale to match the mockup.
  • Gated behind v7.2 approval. Per the locked sequencing, do not begin implementation until the current design is published and Stripe is live — this rewrite must not jeopardize the approval the product needs to monetize.
  • Likely worth slicing into sub-versions (e.g. options/Model removal, sidebar restyle, welcome launcher, toolbar behavior) as separate commits per the per-phase commit discipline, rather than one large commit.
  • The v8 JS→TS migration follows this; keep the restyle in plain JS — do not start TS here.
