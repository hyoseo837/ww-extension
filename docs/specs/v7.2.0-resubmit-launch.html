Store listing — what review needs

The 0.1.0 rejection was "remote code in MV3" against the old v03 artifact, not today's code (ADR 0030). Beyond the code being clean, the listing itself must satisfy review:

Per-permission justification
Each permission needs a one-line "why" in the listing. Current manifest:
  • storage — persist settings, last-known credit balance, per-posting scores, and the Supabase session locally.
  • identity — Google sign-in via launchWebAuthFlow (Supabase OAuth) so scores attach to the user's account/credits.
  • host waterlooworks.uwaterloo.ca — the content script runs only on the co-op jobs page; this is the product.
  • host *.supabase.co — auth (session/JWT).
  • host …ondigitalocean.app — the backend that scores postings and holds the credit ledger.
No <all_urls>, no broad host match — keep it that way; narrow host permissions are the easiest review path.
Privacy-practices form
Declare a single purpose (score WaterlooWorks postings for the signed-in user). Data handled: account email + uploaded CV/profile + posting text sent to the backend for scoring. Must link a privacy policy — the in-app Privacy page shipped at v6.12 (/privacy on the web app); point the listing and README at it (the old hyoseo.dev/privacy-policy/… was removed in v6.10). Confirm a "data is not sold / used only to provide the feature" attestation matches reality.
Description + screenshots
Plain description of what it does and that it needs a (free-bonus or paid) account; screenshots of the current sidebar (not the v7.3 redesign mockup). Add the "not affiliated with the University of Waterloo / WaterlooWorks" disclaimer (already in README + extension + web footer).

Stripe live-mode checklist (run on approval)

Test mode is verified end-to-end (v4.5). Going live is an env swap + reconfiguration — no code change (ADR 0012). Run in order:

  1. Activate the Stripe account for live payments (business details, bank payout) if not already done.
  2. Create a live webhook endpoint in the Stripe Dashboard (live mode) pointing at POST /webhooks/stripe on the DO backend, subscribed to checkout.session.completed. Copy its live signing secret.
  3. Swap the DO env vars (App Platform → Settings → env):
    • STRIPE_SECRET_KEY: sk_test_… → sk_live_… (encrypted).
    • STRIPE_WEBHOOK_SECRET: test → the live signing secret from step 2 (encrypted).
    Confirm WEB_APP_URL / PUBLIC_BASE_URL point at the production web app + backend (for the Stripe return URL). Redeploy.
  4. Real-card smoke test: from the web app /buy, purchase the smallest package with a real card; confirm Stripe shows a live payment, the webhook returns 200, and the balance increases by exactly the package's credits (idempotent — no double grant on Stripe retry; ADR 0012's partial-unique-index).
  5. Refund path: confirm the v6.12 refund policy (ADR 0028) text is live, and that a Dashboard refund of the smoke-test charge works. (Credit clawback on refund is out of scope unless the policy requires it — note it, don't build it here.)
  6. Receipts/emails: verify Stripe emails a receipt (hosted by Stripe per ADR 0012).

Verify

  1. ./package.sh produces a zip whose manifest.json version is 7.2.0 and which contains welcome.html + fonts/*.woff2 (the v7.1 fixes) and no server/ or web/ files.
  2. Web Store Developer Dashboard accepts the upload (version is higher than any prior) and all listing fields validate (permissions justified, privacy policy URL resolves, screenshots sized correctly).
  3. Item reaches published (or, if rejected, the rejection reason is captured here and addressed — re-run this phase).
  4. Live Stripe smoke test: one real-card purchase credits the exact package amount once; a manually replayed webhook does not double-grant.
  5. A freshly installed published build: sign in, see balance, scan a posting, buy credits with a real card end-to-end.
