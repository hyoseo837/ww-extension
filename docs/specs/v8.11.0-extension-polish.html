v8.11 — Extension polish

Goal

Close the four extension findings from the 2026-06-11 audit (findings #11–#14; ordering per ADR 0046): content.js is a 1050-line monolith, a failed scan in a batch can only be recovered by re-running the whole batch, the Gemini model id is pinned client-side where a fix needs a Web Store review cycle, and two dead symbols linger.

  1. Split content.js into modules — MV3 content_scripts.js accepts multiple files sharing one isolated-world scope, so the split needs no build step (ADR 0026 posture unchanged). ext/src/content.js becomes ext/src/content/, five classic scripts in manifest load order:
    1. core.js — constants, shared mutable state (scores, allPostingIds, aborted, detectedPageSize), small utils (esc, verdictSlug, SVGs, BOARD), the page bridge (injectBridge/sendBridge), and persistence (loadScores/saveScores/ scheduleFlush/clearScores/ removeScore).
    2. table.js — job-table integration: badge injection, table observer, pagination navigation, scrollToRow.
    3. scan.js — the scan engine: progress line, confirm dialogs, batch loop, fetchPostingText.
    4. sidebar.js — sidebar shell + results list + feedback UI.
    5. main.js — injection guard, init sequence, storage.onChanged listener.
    Pure reorganization: no behavior change, no renames beyond file placement. Top-level declarations in classic scripts share the realm's global lexical scope, so cross-file references work as before; only top-level execution order matters, and only main.js executes at top level.
  2. "Retry failed" affordance — the batch loop records the posting ids of non-halt failures (fetch errors, Gemini failures; refunded server-side). When a run ends with failures, the progress area gains a Retry N failed button that re-runs only those ids through the same loop — same cost confirmation (it spends new credits, the failed scans were refunded), same Stop button, fresh batch_id. Halt codes (NO_CREDITS, NOT_SIGNED_IN, PROFILE_NOT_SET) keep their action prompts and do not populate the retry list — the jobs a halt skipped are not failures, and "Scan All Jobs" already picks up anything unscored. Mechanically: the worker loop is extracted from scanAllJobs() into runScan(ids), and "Scan All Jobs" becomes selectAll → filter unscored → confirm → runScan.
  3. Server-side default model — ScanRequest.model gains the default pricing.DEFAULT_MODEL (/profile/extract already has it), and the extension stops sending model entirely (drop the literal in the scan loop and the fallback in background.js). When Google retires gemini-2.5-flash, the fix becomes a one-line server deploy instead of a Web Store review cycle. Validation is unchanged: an explicitly sent unsupported model still gets 400.
  4. Dead-code removal — VERDICT_ORDER in page-bridge.js (the obsolete 3-tier ladder, unused) and _require_pool() in server/app/billing/db.py (unused).

Notes

  • The five-file split is deliberately coarse — the audit's concern is the monolith, not maximal modularity; minimal-code rule applies. ES modules in content scripts would need import-capable injection or a bundler; multiple classic scripts get the same outcome with zero toolchain.
  • Retry intentionally re-runs the cost confirmation: failed scans are refunded, so a retry spends new credits, and v6.13's "confirm before spending" rule applies to every spend path.
  • Once v8.11 ships, the client is model-agnostic; choosing a new default (or per-user models someday) is purely a server decision. The Web Store zip is unaffected structurally — package.sh zips all of ext/.
  • Deploy order: the production server (master) still requires model until the next release — a v8.11.3+ extension scanning against prod gets 422 until dev is merged into master. Release the server before loading this extension build against prod (the Web Store version naturally trails the server deploy anyway).
