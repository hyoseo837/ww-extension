v8.0.0 — Open v8: maintenance & polish

Goal

Open major version 8 as a maintenance & polish major: cleanup, small fixes, and minor bugs. v7 delivered its mission — the extension is approved, published, and working against the web app, with monetization live — so the product is essentially in production. v8 is the upkeep track that follows: tidy what shipped fast, and fix the small things that surface in real use.

This is a rough plan, opened deliberately before the work is fully known. The backlog is still being collected, so v8 runs as a rolling major rather than a fixed scope — items are added as they're found, not enumerated up front.

The v8 slot

v8 previously held the extension JS→TS migration, scheduled 2026-06-01 and dropped 2026-06-05 (ADR 0037 — the extension ships fine in JS; the migration had no Web-Store benefit and would have added a build step superseding ADR 0026). That idea now lives in the roadmap's "Further out". The v8 number is reused here for the maintenance major; it is unrelated to the dropped migration.

Strands (ordered)

  1. Cleanup first. Low-risk hygiene on what already ships: dead/duplicated code, stale doc references, inconsistent naming or copy, and small inconsistencies left by the fast v6→v7 build-out. No behaviour change — each cleanup is verifiable as "same behaviour, less cruft". This strand starts immediately.
  2. Small fixes / minor bugs. Filled in as the owner collects "fix needed" points (and as real-use bugs appear). Each is its own v8.x. Tracked on the whiteboard's Existing Bugs list until scheduled.

Process (lighter than a full phase)

The standard rule is per-phase spec + ADR (rules.html). For v8 that is scaled to the change, since most items are one- or two-file fixes where a full spec would outweigh the work:

  • Trivial fix / cleanup — ship as a v8.x commit with a clear message; no spec. The commit is the record.
  • Grouped cleanup — a themed batch (e.g. "doc-link sweep") may get a short spec if it spans many files, but doesn't have to.
  • Non-trivial change or any real decision — still gets a spec and/or an ADR, per the normal rule.

Versioning, commit-per-change, and minimal-code rules are unchanged.
