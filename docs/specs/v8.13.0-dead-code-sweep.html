v8.13.0 — Dead-code sweep & consolidation

Goal

Remove verified-dead code and consolidate verbatim duplication found by a full-repo quality review (2026-06-12, all of ext/src, server/app, web/src read end-to-end, every suspect symbol traced through git history). No feature changes; behavior is preserved except where the "behavior" was already broken (the sidebar guide's step-2 checkmark, which keyed off a storage key nothing writes). Serves the v8 maintenance charter and ADR 0003 (minimal code).

Findings being fixed

  1. Extension checkout path, dead since v6.4.1. background.js still carries the createCheckout message handler + function, but the only sender was the options page's buy UI, removed in v6.4.1 — before the first Web Store publication (7.1.1), so no installed extension has ever called it. This also strands the server's client == "extension" checkout branch, the GET /credits/checkout/result HTML shim it returned to, and the client request field (the web app always sends "web"; with the extension branch gone the field selects nothing). PUBLIC_BASE_URL existed only to build the shim URL and goes with it.
  2. Sidebar guide step 2 keys off cvText, which nothing writes (profile moved server-side at v6.4). The ✓ for "Set up your profile" can never light up; the changes.cvText storage listener never fires. Decision: drop the step-2 checkmark derivation rather than invent a backend round-trip for a cosmetic ✓ — the step stays a numbered link (ADR 0003).
  3. Legacy storage cleanups for keys no published user ever had. The every-SW-start remove(["apiKey", "tokenUsage"]) (pre-v4.4.2 keys) and the sign-out removal of cvText / profileJson / profileSupplement / preferences / matchCriteria (pre-v6.4 keys). Also expires_at, computed and stored on the auth object in two places but never read (refresh is 401-reactive).
  4. Server scaffolding with no caller. gemini.score()'s cache_name / cachedContent branch (explicit context caching, never wired up); the required-but-unread SUPABASE_PUBLISHABLE_KEY setting; ExtractResponse.text (back-compat for the pre-v6.4 options page — the web app, the only extract client, reads only cost).
  5. Web duplication. ChipToggle / TagInput / ChipSelect + chip classes duplicated verbatim between Preferences.tsx and PreferencesSetup.tsx (~120 lines); the pricing-card markup duplicated between Landing.tsx and Buy.tsx (~40 lines each); fmtDate defined twice. Plus two redundant API calls: landing on /account fetches GET /profile twice (SetupGate, then Account), and the extract flow refetches GET /profile when the POST response already carries the fresh profile_json.
  6. Extension duplication. confirmScan and confirmDialog duplicate the overlay scaffolding (backdrop / card / Esc / settle, ~35 lines each).
  7. Server duplication. The insufficient-credits reserve block (lock → balance check → 402 → debit) is copy-pasted between /scan and /profile/extract; the must-match-the-trigger email hash is implemented in both billing/db.py and account/db.py.

Notes — deliberate non-removals

  • cv_text legacy fallback stays (ADR 0015 — kept until re-extraction).
  • The v1→v2 criteria converters stay in both server and web (deploy-skew shim, ADR 0041). The durable fix is a one-time SQL migration rewriting remaining v1 rows, then deleting both converters — deferred to its own phase since it's a production data change.
  • gemini-2.5-pro pricing rates stay: inert data, rides along whenever pricing.py is next touched (ADR 0031 context).
  • ext/design/ and web/design/ mockups stay in place — unreferenced by any build (package.sh is an allowlist) and documented repo furniture; archiving is an owner call.
  • ratelimit._windows unbounded growth noted but not fixed here — behavior addition, not dead code; harmless at current scale with deploy restarts.
