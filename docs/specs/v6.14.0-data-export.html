v6.14.0 — Download my data

Goal

Give a signed-in user a one-click JSON export of everything we hold about them — the data-subject access / portability right, the companion to v6.9 account deletion (the erasure right). The server already stores it all; this phase just assembles it and hands it back as a download. No new data, no credit cost.

Scope & policy

  • Everything we store, nothing we don't. The export mirrors what's actually in the DB: account identity, credit balance, the full credit ledger, every scan row, and the full profile (structured profile_json, user-authored profile_supplement, legacy cv_text, free-form notes, and match_criteria). We do not store the uploaded application-package PDF — only its extracted text — so the PDF is not in the export (it never existed server-side after extraction).
  • Self-serve, free, no confirmation. Unlike deletion or a scan, reading your own data is harmless and reversible, so it's a plain button — no dialog, no credit debit.
  • JSON, not a per-table CSV. One machine-readable file a developer-savvy user (the audience) can diff or re-import. Wrapped with an export_version so the shape can evolve.

Module placement

Introduces server/app/account/ — the home for data-subject rights endpoints, exactly as the v6.9 deletion spec anticipated ("app/auth/routes.py or a new app/account/"). Export lands here now; deletion slots in beside it when v6.9 is built. The route reuses existing data access rather than duplicating queries: billing.db for the ledger/scans/balance and account row, profile.db for the profile.

Payload shape

{
  "export_format": "ww-scorer-account-export",
  "export_version": 1,
  "exported_at": "<ISO-8601>",
  "account": { "user_id", "email", "created_at" },
  "balance": <number>,
  "profile": { "cv_text", "preferences", "match_criteria",
               "profile_json", "profile_supplement" },
  "credit_history": [ { "id","kind","delta","created_at",
                        "org","title","posting_id","batch_id" }, … ],
  "scans": [ { "id","kind","status","org","title","cost","created_at" }, … ]
}

credit_history and scans are the full sets (not the 25/50-row paginated views the dashboard uses). The reused get_history helper is called once with a high limit; a new export_user query reads all scan rows.

Files

Server

  • app/account/__init__.py, app/account/routes.py — authenticated GET /account/export: assemble the payload from billing.db.export_user(sub) + profile.db.get_profile(sub). Returns the JSON object.
  • app/billing/db.py — export_user(user_id): account row (auth.users), balance, all ledger entries (reuse get_history with a high limit), all scan rows.
  • app/main.py — register account_router.
  • pyproject.toml — version bump (server touched, ADR 0010).

Web

  • src/pages/Account.tsx — a "Your data" card with a Download my data button: apiGet("/account/export"), serialize to a Blob, trigger a ww-scorer-data-<date>.json download. Loading + error states inline (no new API helper — reuse apiGet, build the Blob client-side).

Docs

  • docs/reference/api.html — document GET /account/export (auth, payload, no cost).
  • docs/architecture.html — note the account/ module + export path.

Verify

  1. GET /account/export with a valid token returns the full payload; balance, ledger, scans, and profile match the dashboard.
  2. No token → 401; a token only ever returns its own data (the query keys on sub, no cross-user read).
  3. Web: click Download my data → a ww-scorer-data-<date>.json file downloads and parses; a fresh account (empty ledger/scans) still exports valid JSON.
  4. Fetch failure shows an inline error, not a silent no-op. npm run build and server ruff/import check pass.
