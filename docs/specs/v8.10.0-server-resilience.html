v8.10 — Server resilience

Goal

Close the four resilience gaps from the 2026-06-11 audit (findings #6–#9; ordering per ADR 0046): the free endpoints can be hammered, one transient Gemini blip means one user-visible failed scan, /health reports ok with a dead connection pool, and failures live only in DO's log stream while web-app errors vanish entirely.

  1. Rate limiting — in-memory per-user fixed-window counters (no new dependency; correct for the single DO instance) on the three free-to-hammer authenticated endpoints: /credits/checkout 5/min, /account/export 3/min, /scan/feedback 30/min. Over-limit requests get 429 {"detail": "rate_limited"}.
  2. Gemini retry — the raw POST in score() / extract_profile() moves to a shared helper that retries once after a short backoff (0.8 s) on transient failures only: network errors and HTTP 429 / 5xx. Parse and shape errors never retry.
  3. Honest /health — the endpoint runs select 1 on the pool (5 s timeout) and returns 503 {"status": "db_unavailable"} when it fails, so platform health checks catch the most likely real outage.
  4. Error monitoring — Sentry free tier (ADR 0049, owner-chosen 2026-06-11): sentry-sdk[fastapi] on the server and @sentry/react on the web app, both errors-only and env-gated (SENTRY_DSN / VITE_SENTRY_DSN; absent = SDK never initializes, so dev and CI run exactly as before).

Verify

  • pytest green: limiter allows up to the limit in a window, rejects past it, resets on window roll, keys per user; retry decision retries network/429/5xx once and never retries 4xx-other or parse failures.
  • CI green on push.
  • With no DSN set, server starts and web builds with Sentry fully inert (local + CI behave as before).
  • Owner runbook (live): create a Sentry org with two projects (FastAPI server, React web); set SENTRY_DSN on the DO app and VITE_SENTRY_DSN on Vercel; after the next release, confirm a thrown test error reaches both projects, and that /health still reports ok with the new version.

Notes

  • The limiter is in-memory and per-process — exactly right for the single-instance DO deployment, and it resets on deploy. If the app ever scales out, move the counters to Postgres or a shared store (and revisit ADR 0047's startup reconciliation in the same pass).
  • /scan itself stays unlimited: it is credit-bounded, and v8.9's per-user debit lock already serializes its spend.
  • Stripe's webhook is not rate-limited — it is signature-verified and replay-idempotent (migration 0004's partial unique index).
