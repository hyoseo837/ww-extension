Spec v5.3.0 — Hard filters (credit-free pre-scan exclusion)

Goal

Fourth and final v5 thread (#4). Skip postings that match the candidate's own excluded-tier match criteria before calling POST /scan — so no credit is spent and no Gemini call is made. The skipped posting is surfaced with the existing Excluded verdict (v5.2, ADR 0017): no score number, a reason naming the gate. The check is deterministic and conservative — it skips only on a confident structured match and never on missing/ambiguous data, so it can never wrongly hide a viable job. Work-auth/citizenship gates are not pre-filtered (free-text, unreliable); they remain caught by the scan-time Excluded verdict. Architecture in ADR 0018.

Scope: client-only. The extension fetches the user's match_criteria via the existing GET /profile at scan-batch start, extracts the excluded tiers, and matches them against each posting's structured fields in the scan loop. Backend unchanged. The sidebar/badge/save-filter already render and filter Excluded (v5.2.4), so UI work is minimal. The pre-filter is user-toggleable via an options-page setting (hardFilterEnabled, default on) — when off, every posting scans normally (ADR 0018).

Matching rule

The excluded-tier values are free strings the user typed; posting fields are also strings. To guarantee no false-positive skips:

  • Source. Use structured fields only — the results table's City column (available with no fetch) is the reliable starting field. Term length / work mode / language are included only where a clean structured field exists (confirm against a live posting / getPostingData during build); otherwise they are left to the scan-time Excluded verdict.
  • Match. Normalize (lowercase, trim); skip only when the posting's structured value equals or clearly contains an excluded token. Substring containment is intentionally conservative — it catches exact city-name exclusions ("Calgary" → "Calgary, AB") and misses region/province/country exclusions ("Quebec" vs "Montréal, QC"), which is acceptable: those fall through to a normal scan and the Excluded verdict still catches them.
  • Never skip on missing data. If the relevant field is absent/empty, do not pre-filter — scan normally.

Verify

  1. A posting whose City matches an excluded location is shown Excluded with no score and no credit charged — balance unchanged, no /scan call (no scan_ok log line for it).
  2. A posting with no excluded match scans normally and is scored as before.
  3. A posting with a missing/ambiguous City is never pre-filtered.
  4. Pre-filtered Excluded entries render, sort (last), and filter via the save-to-folder Excluded toggle alongside server-produced Excluded ones; the no-score badge shows just "Excluded".
  5. With no excluded criteria set, every posting scans as before (the filter is a no-op).
  6. Turning off the hardFilterEnabled toggle in Settings makes the pre-filter a no-op — a posting that would have been pre-filtered instead scans normally (and may still land in Excluded via the scan-time verdict).

Notes

  • Client needs the criteria. One GET /profile per scan batch (cheap, no credit) supplies the excluded tiers; cache for the batch.
  • Null score. A pre-filtered Excluded has no fit score — the genuinely new client wrinkle (v5.2 assumed an integer score). Load-validation, sort, and badge must accept score === null when verdict === "Excluded".
  • Field confirmation. City is confirmed (results-table column, ADR-referenced WW DOM cheatsheet). Confirm term length / work mode availability empirically before extending the match beyond location; ship location first if others aren't cleanly structured.
  • Toggle. hardFilterEnabled (chrome.storage.local, boolean, default true when unset) gates the pre-filter; surfaced as a Settings-tab toggle so users can opt out (ADR 0018).
  • Out of scope. Work-auth/citizenship pre-filtering (free-text / pre-screening) — future work per ADR 0018.
