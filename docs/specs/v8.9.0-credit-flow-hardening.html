v8.9 — Credit-flow hardening

Goal

Close the three credit-flow holes from the 2026-06-11 audit (findings #2, #3, #5; ordering per ADR 0046), now that v8.8's test suite makes money code safe to touch:

  1. Stranded-scan reconciliation — a server death between the debit transaction and settlement leaves the scan row pending forever and the user's debit unrefunded. At app startup, refund the unrefunded scan_debit of every pending scan older than 10 minutes and mark the row failed (error='stranded'). Mechanism decision in ADR 0047.
  2. Per-user debit lock — the balance check is read-committed, so the extension's 5 concurrent workers can all pass it before any debit commits, driving the balance negative. Take pg_advisory_xact_lock keyed on the user id inside transaction 1, immediately before the balance check, in both /scan and /profile/extract. The lock releases at commit and never spans the Gemini call.
  3. Server-side input caps — request fields were unbounded (the 6000-char description cap lived only in the extension). Add pydantic max_length caps on /scan, /profile/extract, and /scan/feedback inputs, plus a Content-Length middleware rejecting bodies over 8 MiB with 413.

Files

  • server/app/billing/db.py — reconcile_stranded_scans(), lock_user_for_debit().
  • server/app/main.py — call reconciliation in lifespan after init_pool(); body-size middleware.
  • server/app/scoring/routes.py — lock before the balance check in both endpoints; max_length on ScanRequest / ExtractRequest / FeedbackRequest fields.
  • server/tests/test_ledger.py — reconciliation tests; test_concurrent_debits_can_overdraw flips to …cannot_overdraw (its docstring already demands this).
  • server/tests/test_input_caps.py — added: field-cap validation + body-size-limit unit tests (no DB).
  • server/pyproject.toml, ext/manifest.json — version bumps per commit.

Verify

  • pytest green on the disposable Postgres (TEST_DATABASE_URL), including: a pending scan older than the cutoff is refunded exactly once and marked failed; a second reconciliation run is a no-op; a fresh pending scan is untouched; two concurrent debit transactions on one user serialize — the second sees the first's debit and gets rejected, balance never negative.
  • ScanRequest with a 6001-char description_text fails validation (422 at the API boundary); same for an oversized pdf_b64 / comment.
  • CI (v8.8.2 workflow) green on push.
  • Live after deploy: a normal scan batch still works end-to-end (lock is invisible at human timescales); /health version reports 8.9.x.

Notes

  • Caps chosen: description_text 6000 (mirrors the extension's DESC_CHAR_CAP), title/org 300, posting_id 32, pdf_b64 7,000,000 chars (≈ the 5 MB PDF cap in base64), feedback comment 2000 parse-cap (the existing truncate-to-500 behaviour is kept), feedback description_text 8000. Body middleware 8 MiB > the largest legal body (pdf_b64 + JSON overhead).
  • The advisory lock key is hashtextextended(user_id::text, 0); a hash collision between two users merely serializes their transaction-1s — harmless.
  • A stranded scan's 409-on-replay remains until reconciliation flips the row to failed; the extension never reuses a scan_id (fresh UUID per attempt), so no client change is needed — after the refund, the next batch simply re-scans the posting.
