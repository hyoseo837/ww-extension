v8.3.0 — Small fixes: quieter data buttons + user_profile RLS hardening

Goal

Two small items promoted from docs/whiteboard.md by the owner (2026-06-10). First v8 phase developed under the new branch model (ADR 0039): commits land on dev, merge to master deploys.

  1. Quieter data-rights buttons (web). On /account, "Download my data" and "Delete account" render as full-size outlined buttons with icons — the same visual weight as primary actions. Both are rare, once-ever actions; shrink them to compact buttons (smaller padding and label, smaller icon). The type-DELETE confirm dialog (v6.9) remains the real safety gate for deletion and is unchanged.
  2. user_profile RLS hardening (server). Drop the user_profile_modify_own policy (for all) so authenticated users can no longer write their own profile row directly via PostgREST with the anon key, bypassing FastAPI's Pydantic validation. Verified 2026-06-10: no client touches user_profile via PostgREST — the web app goes through PUT /profile and the extension never references the table — and the backend writes via service-role / direct Postgres, which bypasses RLS. Read access (user_profile_select_own) is kept as forward-compat.

Files

  • web/src/pages/Account.tsx — compact classes on the two buttons; no logic change.
  • server/migrations/0011_user_profile_rls_backend_writes.sql — new migration, idempotent; drops user_profile_modify_own. Migration files are immutable history — 0003 is not edited.
  • server/pyproject.toml — patch bump (server-touching commit, ADR 0010).

Slices

  • v8.3.0 — docs: this spec.
  • v8.3.1 — web: compact Download-my-data / Delete-account buttons.
  • v8.3.2 — server: migration 0011 + pyproject bump.

Verify

  • Web: on /account, both buttons render visibly smaller than the page's primary actions; download and delete flows still work (delete still gated by the type-DELETE dialog).
  • Server: after applying 0011 in the Supabase SQL editor, a PostgREST PATCH /rest/v1/user_profile with a user JWT + anon key affects 0 rows, while GET of the own row still works and PUT /profile through the API still saves.

Notes

  • Applying the migration is a production database change regardless of git branch (ADR 0039 consequence) — it only removes an unused write path, so it is safe to apply when merged.
  • The third whiteboard fix ("better Match preferences page UX") is deliberately excluded: it is a redesign with open product questions, scheduled as its own phase (v8.4) once scoped with the owner.
