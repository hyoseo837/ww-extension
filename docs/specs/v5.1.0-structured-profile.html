Spec v5.1.0 — Structured profile extraction

Goal

Second v5 phase (thread #2 of the scoring-quality pass). Today the candidate profile is a raw-text blob (user_profile.cv_text) that POST /profile/extract fills from the uploaded PDF and the scorer receives verbatim as "Candidate Profile". This phase switches the profile to a structured JSON object (summary / education / experience / skills / projects / languages), extracted via a Gemini responseSchema, and adds user-authored supplementary experience/project entries for things a one-page resume omits. The structured profile is serialized into the scan's Candidate Profile context, giving the model clean signal and (expected) fewer input tokens than re-sending resume prose. Storage shape and the cutover are fixed in ADR 0015.

Scope is the structured-profile foundation: extraction to JSON, storage, the supplementary-entries form, and a faithful pass into the existing prompt. This is not the prompt rewrite (thread #3) — the serialized profile slots into the current prompt structure unchanged; #3 later reworks framing, calibration, and per-aspect output (and depends on this phase's fields). Hard filters (#4) remain separate.

The profile_json object

Stored as user_profile.profile_json (JSONB), owned and validated by a backend Pydantic model. All fields optional/defaulted so a partial object is valid; {} = not yet extracted.

{
  "summary":      "string",
  "education":    [{ "institution", "credential", "field", "grade", "dates" }],
  "experience":   [{ "title", "org", "dates", "description" }],
  "skills":       ["string"],
  "projects":     [{ "title", "description" }],
  "languages":    ["string"],  // spoken/working, not programming
  // raw-text dumps of the package's other documents (v5.1.6 follow-up):
  "grade_report": "string",    // transcript, verbatim
  "coop_history": "string",    // UW co-op work-history summary, verbatim
  "cover_letter": "string"     // verbatim, if present
}

The profile_supplement array

Stored as user_profile.profile_supplement (JSONB, default []), written only by the user via PUT /profile — never by extraction (ADR 0015), so re-uploading a PDF can't wipe hand-entered entries.

[
  { "kind": "experience" | "project", "title": "string", "description": "string" }
]

Cutover (ADR 0015)

The scan uses profile_json when non-empty, else falls back to cv_text. No data migration; legacy users keep scoring on their existing blob and upgrade to JSON the next time they extract. profile_supplement is always serialized alongside whichever profile source is used.

Follow-up — full application-package extraction (v5.1.6)

The initial extraction (v5.1.1) only pulled CV-shaped fields, but a WaterlooWorks application package PDF bundles several documents: a résumé/CV, a grade report (transcript), a UW co-op work-history summary, and sometimes a cover letter. The CV stays structured; the other three are captured as raw text (they don't need structure) in three new profile_json string fields — grade_report, coop_history, cover_letter — and appended to the scan's Candidate Profile block. No DB migration (the JSONB column grows under the same Pydantic ownership, ADR 0015); only the model, the extraction prompt/schema, and the serializer change, plus a minimal read-only render of the three raw sections. UI: the options-page form's poor field-visibility is a known issue but is deliberately left as-is — the whole profile/criteria UI is slated for a redesign in v6, so this follow-up keeps the existing pattern and adds no UX polish.

Verify

  1. Apply 0007 → user_profile has profile_json (default {}) and profile_supplement (default []); cv_text untouched.
  2. POST /profile/extract on a real PDF returns a structured profile; profile_json persists; a pre-existing profile_supplement survives the extract; cv_text is left as-is.
  3. GET /profile returns profile_json + profile_supplement; PUT /profile with supplement entries round-trips; a bad kind is rejected (422).
  4. Options page: after extract, the structured sections render; add a supplementary entry, save, reload — it repopulates; re-extract keeps the supplementary entry.
  5. Scan with profile_json set uses the serialized structured profile (verify via a logged prompt). Regression: a user with only cv_text (no JSON) still scores via the fallback, unchanged from v5.0.
  6. Measure per-scan input tokens for a JSON profile vs the equivalent raw cv_text — expect ≤.
  7. (v5.1.6) Extract a full application package (CV + grade report + co-op history + cover letter) → profile_json gains populated grade_report, coop_history, and cover_letter raw text; they render read-only and feed the scan context. A CV-only package leaves them empty.

Notes

  • cv_text fallback, no migration (ADR 0015). Legacy users keep working until they re-extract; a cleanup migration to drop cv_text is deferred to a later phase once adoption is complete.
  • Supplement in its own column so extraction can't clobber user-entered entries — a structural guarantee, not merge code (ADR 0015).
  • No prompt rewrite here. The profile is serialized faithfully into the existing prompt; framing/calibration/per-aspect output is thread #3, which depends on these structured fields.
  • Extraction stays one multimodal call — now with a responseSchema. A malformed/empty extraction must fail without destroying the existing profile_json.
  • Languages here = spoken/working (English, French), matching the v5.0.0 criteria field — not programming languages, which live under skills.
  • Slicing. backend (migration + extract + contract + scan serialization) → client (structured display + extract, then the supplement form, possibly two sub-versions) → close-out. Z numbers assigned at build time.
