v4 — Monetization (shipped)

Shipped and frozen. All v4 phase specs are archived under docs/archive/v04/ (kept in spec format — see ADR 0014); the cross-cutting decisions remain in docs/decisions/. This section is retained for the vision/rationale; per-phase detail lives in the archived specs.

Goal: turn the extension into a monetizable service. A FastAPI backend in server/ (monorepo since ADR 0010 superseded 0004) holds user accounts, a credit ledger, and the Gemini-calling logic + prompts. The extension becomes a thin client: authenticates the user, spends credits per scan, displays results.

Rationale for moving the backend off the client:

  • Hide proprietary scoring prompts and tuning logic from end users (kept out of the Web Store zip by package.sh).
  • Centralize Gemini key management — user no longer needs their own paid API key.
  • Enable per-user billing (credits) without trusting the client.

Stack and platform locked in v4 planning (2026-05-27):

  • Backend: FastAPI on Python 3.12+ (ADR 0009).
  • Deploy: DigitalOcean App Platform (ADR 0007).
  • Auth + DB: Supabase (Google OAuth provider; managed Postgres for the credit ledger) (ADR 0008).
  • Payments: Stripe Checkout (hosted page) + webhook-driven credit grants (ADR 0012).

v5 — Profile structure + scoring quality (shipped)

Shipped and frozen. All v5 phase specs are archived under docs/archive/v05/ (kept in spec format — see ADR 0014); the cross-cutting decisions remain in docs/decisions/. This section is retained for the vision/rationale; per-phase detail lives in the archived specs.

Direction set 2026-05-28. v4 ships a functional monetized product but treats user preferences as one free-form prose field and the candidate profile as a raw text dump of the resume PDF. That's enough for the product to work; it isn't enough for the scoring to be trustworthy. v5 is the quality pass.

Phase-started 2026-05-29. Sequence chosen by dependency: structured match criteria leads (the v5.0.0 phase — biggest accuracy gap, and it unblocks hard filters), then structured profile, then the prompt rewrite (now that live v4.4–v4.6 scoring data exists to calibrate against), then hard filters. (Account-management and external-web-surface work moved to v6 — see below.) Threads:

  • Structured Custom Match Criteria. (Shipped — v5.0.0 phase: backend v5.0.3, client v5.0.4–v5.0.5, docs v5.0.6–v5.0.7.) Replaced the single textarea with structured fields (work authorization, plus weighted/tiered preferred locations, target term + length, work mode, languages) and demoted the existing free-form prose to an "additional notes" field. Biggest gap closed: work-authorization signal for international students. Storage in ADR 0013.
  • Structured PDF extraction. (Shipped — v5.1.x.) Switch the profile from a raw-text blob to a JSON profile (summary / education / experience / skills / projects / languages), extracted via a Gemini responseSchema. Cheaper signal per scan than re-sending resume prose, and sharper matching. Also lets the user add supplementary experience/projects as structured entries (title + description) for things a one-page resume omits, merged into the profile for scoring. Existing cv_text kept as a fallback (no forced re-upload); storage + cutover in ADR 0015. The application package is multi-document: the CV is structured, while the grade report, UW co-op work history, and cover letter are captured as raw-text fields on profile_json (v5.1.6 follow-up). The options-page field visibility is poor and is addressed by the v6 UI transition (web app). See docs/archive/v05/v5.1.0-structured-profile.html.
  • Scan-prompt rewrite + richer scoring output. (Shipped — v5.2.x.) Co-op framing and calibration anchors in the prompt. Moves scoring to a 1–20 scale with a verdict ladder of five score bands (Strong Apply 17–20 / Apply 14–16 / Consider 10–13 / Unlikely 6–9 / Skip 1–5) plus an Excluded verdict for hard-criteria/eligibility gates (work-auth/citizenship, or a criterion in the candidate's "excluded" tier) — all derived server-side — and returns a structured per-aspect breakdown — the specific criteria/profile points that gained or lost points (e.g. "prefers Toronto, job in Québec"; "AWS preferred, not in profile"), surfaced in the sidebar. The Excluded verdict is a down-payment on thread #4 (its cheaper pre-scan filter stays separate). Contract in ADR 0016, scale + Excluded verdict revised in ADR 0017. Calibration is anchored only this phase; few-shot from real disagreements is a later tuning pass once enough live v5 scans accumulate. See docs/archive/v05/v5.2.0-scan-prompt-rewrite.html.
  • Hard filters. (Shipped — v5.3.x; v5.4–v5.5 followed: extract line-break fidelity and the prompts.py module extraction.) Credit-free pre-scan skip: client-side, before /scan, auto-Skip postings that match the candidate's own excluded-tier criteria on a structured field (e.g. a City in their "never" list), shown via the existing Excluded verdict with no credit spent. Conservative — confident structured matches only, never on missing data, so it can't wrongly hide a job. Free-text work-auth/citizenship gates stay with the scan-time Excluded verdict (not pre-filtered). Architecture in ADR 0018; see docs/archive/v05/v5.3.0-hard-filters.html.

v6 — UI transition to a web app + admin surface (shipped)

Shipped and frozen. All v6 phase specs (v6.0–v6.15) are archived under docs/archive/v06/ (kept in spec format — see ADR 0014). v6 delivered the web app (account, profile/CV, match criteria, Stripe credit purchase), the admin surface, the legal/trust + support pages, and the data-subject rights (export + account deletion). Closed 2026-06-01 as v7 opened.

Direction locked 2026-05-30 (v6.0). v5 made scoring trustworthy; the remaining weak spot is the UI. The extension's three-tab options page is cramped, and the structured-profile fields it gained in v5.1 are barely usable there. v6's theme is the UI transition: move account, profile/CV, match-criteria, and payment management off the options page and onto a dedicated web app, leaving the extension focused on in-page scoring. This absorbs the older "consolidate the options-page Account section" idea — that consolidation now happens on the web, not in the options page.

The move is clean because the state already lives server-side: profile and credits sit behind authenticated FastAPI endpoints, and POST /scan reads the stored profile (no client-sent profile since v4.4.2). So the web app is a new client of the existing API, and the extension becomes a profile reader (it still fetches match_criteria for the ADR 0018 pre-filter) rather than an editor.

Decisions locked at v6.0:

  • Stack: Vite + React + TypeScript SPA (ADR 0019); TypeScript scope is the web app only — the extension stays JS.
  • Repo: web app at web/ in the monorepo, excluded from the Web Store zip by the allowlist (ADR 0020).
  • Auth: extension and web app keep independent sessions, connected by a Manage account → deep link, no handoff (ADR 0021).
  • Hosting: Vercel at ww-extension.hyoseo.dev, Cloudflare DNS-only CNAME (ADR 0022).

v7 — Extension fix: website integration + Web Store approval (active)

Opened 2026-06-01 (v7.0). Sequencing locked 2026-06-01: ship the essential compliance fix first, then resubmit and get approved, and only then do the redesign and feature upgrades — the Web Store approval gate (and going live on Stripe) stays ahead of the riskier rewrite. The JavaScript→ TypeScript migration was pulled out of v7 and scheduled as its own major, v8 — since dropped (ADR 0037; see v8 below). Phases are listed at the end of this section; per-phase specs/ADRs land as each opens.

v6 rebuilt the account/profile/payment surface as the web app; v7 turns back to the Chrome extension so it (a) works cleanly against that web app and (b) passes Chrome Web Store review. Submission history:

  • Version 0.1.0 — Rejection — 2026-05-26 — Content Policies. Violation: "Including remotely hosted code in a Manifest V3 item."
  • Version 7.1.1 — Approved & published — 2026-06-04. Live at chromewebstore.google.com/…/bichfckekdcnmkenflpmmehegggcfgdd (publisher hyoseo.dev). The published build is 7.1.1; the later 7.1.2–7.1.6 commits were docs/assets only and were never uploaded, so the spec's planned 7.2.0 re-upload version was not used for this submission.

Diagnosis of current ext/: the hard blocker (remote JS/Wasm) is not present now — no remote <script src>, no eval / new Function / importScripts / dynamic import; the one script injection in content.js uses chrome.runtime.getURL('src/page-bridge.js'), a locally packaged web-accessible resource (the correct MV3 pattern). The only remote dependency left is Google Fonts (<link href="https://fonts.googleapis.com/…"> in welcome.html + options.html) — self-hosted in v7.1 (ADR 0030), so no remote resource remains in a shipped page.

Resolved: the rejected 0.1.0 artifact was the old v03 public build (its manifest predated strict versioning), not the current code — so the rejection was not against today's ext/ (see ADR 0030).

v8 — JavaScript → TypeScript migration (dropped)

Scheduled 2026-06-01 as its own major, then dropped 2026-06-05 (ADR 0037). The extension ships and works in production as plain JS; the migration's only motivation was parity with the web app (ADR 0019), with zero Web-Store-review benefit, while it would add a build step and supersede the no-build packaging of ADR 0026. Not worth a whole major — the extension stays JS; ADR 0026 stands. De-committed to "Further out" below, reopenable only by a future ADR.
