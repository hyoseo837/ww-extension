v4 — Monetization (active)

Goal: turn the extension into a monetizable service. A FastAPI backend in server/ (monorepo since ADR 0010 superseded 0004) holds user accounts, a credit ledger, and the Gemini-calling logic + prompts. The extension becomes a thin client: authenticates the user, spends credits per scan, displays results.

Rationale for moving the backend off the client:

  • Hide proprietary scoring prompts and tuning logic from end users (kept out of the Web Store zip by package.sh).
  • Centralize Gemini key management — user no longer needs their own paid API key.
  • Enable per-user billing (credits) without trusting the client.

Stack and platform locked in v4 planning (2026-05-27):

  • Backend: FastAPI on Python 3.12+ (ADR 0009).
  • Deploy: DigitalOcean App Platform (ADR 0007).
  • Auth + DB: Supabase (Google OAuth provider; managed Postgres for the credit ledger) (ADR 0008).
  • Payments: Stripe Checkout (hosted page) + webhook-driven credit grants (ADR 0012).

Phase arcs:

  1. v4.0 — Doc restructure + v4 opening (shipped as v4.0.0 and v4.0.1). See docs/specs/v4.0.0-restructure.html.

  5. v4.4 — Server-side scoring (shipped) — Gemini calls (scoring + PDF extract) and the scoring prompt itself moved to the backend; estimate-debit-refund flow on POST /scan; profile lives server-side. Extension no longer holds a Gemini key.
  6. v4.5 — Stripe credit purchase (shipped; verified end-to-end in Stripe test mode, including the live extension Buy flow) — Stripe Checkout integration, webhook-driven credit grants, purchase UI in options page. Remaining for real payments: complete Stripe account activation and swap the DigitalOcean env vars to live values (sk_live_… + a live-mode webhook secret); no code change.   7. v4.6 — Free tier + paid tier UX (shipped) — rebalanced the per-token margin 2× → 5× so the 100-credit signup bonus is a ~200-scan trial rather than a whole co-op term (margin is now a single MARGIN dial in pricing.py; existing balances untouched); fixed the wrong welcome/options copy to show approximate scan counts and a pricing explainer; added a sidebar "Buy credits" nudge when a scan batch halts out of credits. No behavior change. Client left as-is. See docs/specs/v4.7.0-tunable-constants.html.

Phase numbering above is the plan of record; sub-commits within a phase use the Z digit per ADR 0002. Slicing may still shift if a phase grows too large — promote to a new Y bump rather than overloading one phase.

Out of scope for v4 (deferred): auto-apply, cover-letter generation, non-Gemini providers, native mobile.

v5 — Profile structure + scoring quality (planned)

Direction set 2026-05-28. v4 ships a functional monetized product but treats user preferences as one free-form prose field and the candidate profile as a raw text dump of the resume PDF. That's enough for the product to work; it isn't enough for the scoring to be trustworthy. v5 is the quality pass.

Threads (vague plan — concrete slicing decided at phase-start):

  • Structured Custom Match Criteria. Replace the single textarea with essential structured fields (work authorization, preferred locations, target term + length, work mode, languages) and demote the existing free-form prose to an "additional notes" field. Biggest gap today is work-authorization signal for international students.
  • Structured PDF extraction. Switch the profile from a raw-text blob to a JSON profile (summary / education / experience / skills / projects / languages). Cheaper signal per scan than re-sending resume prose, and sharper matching.
  • Scan-prompt rewrite. Co-op framing, calibration anchors, few-shot examples — using real disagreements from v4.4 scans as the examples. Wait until v4.4 has produced enough live scoring data to iterate against, not before.
  • Hard filters. Once preferences are structured, auto-Skip postings that explicitly exclude the user (e.g. US-citizen-only) without spending a credit. Catches the worst false-Apply class cheaply.
  • Account section in options page. Consolidate sign-in / balance / credit history into a dedicated Account area. Promoted from the whiteboard; fits here because the Profile & Context page is being restructured anyway.

Other v5+ candidates still on the table: non-Gemini provider support, cover-letter generation, team / recruiter views, re-score on demand. No commitment yet — revisit when v5 phase planning starts.
