v4 — Monetization (shipped)

Shipped and frozen. All v4 phase specs are archived under docs/archive/v04/ (kept in spec format — see ADR 0014); the cross-cutting decisions remain in docs/decisions/. This section is retained for the vision/rationale; per-phase detail lives in the archived specs.

Goal: turn the extension into a monetizable service. A FastAPI backend in server/ (monorepo since ADR 0010 superseded 0004) holds user accounts, a credit ledger, and the Gemini-calling logic + prompts. The extension becomes a thin client: authenticates the user, spends credits per scan, displays results.

Rationale for moving the backend off the client:

  • Hide proprietary scoring prompts and tuning logic from end users (kept out of the Web Store zip by package.sh).
  • Centralize Gemini key management — user no longer needs their own paid API key.
  • Enable per-user billing (credits) without trusting the client.

Stack and platform locked in v4 planning (2026-05-27):

  • Backend: FastAPI on Python 3.12+ (ADR 0009).
  • Deploy: DigitalOcean App Platform (ADR 0007).
  • Auth + DB: Supabase (Google OAuth provider; managed Postgres for the credit ledger) (ADR 0008).
  • Payments: Stripe Checkout (hosted page) + webhook-driven credit grants (ADR 0012).

Phase arcs:

  1. v4.0 — Doc restructure + v4 opening (shipped as v4.0.0 and v4.0.1). See docs/archive/v04/v4.0.0-restructure.html.
  2. v4.1 — Backend bootstrap (shipped) — server/ folder created with FastAPI skeleton (auth/, scoring/, billing/, core/) + Dockerfile + pyproject.toml; /health live on DO App Platform; Supabase project configured with Google OAuth; api.html + architecture.html updated; package.sh excludes server/ from the Web Store zip. No extension code changes. See docs/archive/v04/v4.1.0-backend-bootstrap.html.
  3. v4.2 — Auth in the extension (shipped) — sign-in via chrome.identity.launchWebAuthFlow, Supabase session JWT stored, sign-out. Extension can authenticate against the backend.
  4. v4.3 — Credit ledger (shipped) — server-side balance, append-only ledger, signup-bonus trigger, extension shows balance.
  5. v4.4 — Server-side scoring (shipped) — Gemini calls (scoring + PDF extract) and the scoring prompt itself moved to the backend; estimate-debit-refund flow on POST /scan; profile lives server-side. Extension no longer holds a Gemini key.
  6. v4.5 — Stripe credit purchase (shipped; verified end-to-end in Stripe test mode, including the live extension Buy flow) — Stripe Checkout integration, webhook-driven credit grants, purchase UI in options page. Remaining for real payments: complete Stripe account activation and swap the DigitalOcean env vars to live values (sk_live_… + a live-mode webhook secret); no code change. See docs/archive/v04/v4.5.0-stripe-credit-purchase.html and ADR 0012.
  7. v4.6 — Free tier + paid tier UX (shipped) — rebalanced the per-token margin 2× → 5× so the 100-credit signup bonus is a ~200-scan trial rather than a whole co-op term (margin is now a single MARGIN dial in pricing.py; existing balances untouched); fixed the wrong welcome/options copy to show approximate scan counts and a pricing explainer; added a sidebar "Buy credits" nudge when a scan batch halts out of credits. See docs/archive/v04/v4.6.0-free-paid-tier-ux.html.
  8. v4.7 — Tunable constants consolidation (shipped) — follow-up to the v4.6 MARGIN dial: pull the duplicated server-side knobs into single named constants so they're safe to adjust. Output-token caps now have one source in pricing.py (imported by gemini.py, so the cost estimate can't desync from the call); default model and scoring temperatures are named constants; the signup bonus is a named constant in the trigger. No behavior change. Client left as-is. See docs/archive/v04/v4.7.0-tunable-constants.html.

Phase numbering above is the plan of record; sub-commits within a phase use the Z digit per ADR 0002. Slicing may still shift if a phase grows too large — promote to a new Y bump rather than overloading one phase.

Out of scope for v4 (deferred): auto-apply, cover-letter generation, non-Gemini providers, native mobile.

v5 — Profile structure + scoring quality (active)

Direction set 2026-05-28. v4 ships a functional monetized product but treats user preferences as one free-form prose field and the candidate profile as a raw text dump of the resume PDF. That's enough for the product to work; it isn't enough for the scoring to be trustworthy. v5 is the quality pass.

Phase-started 2026-05-29. Sequence chosen by dependency: structured match criteria leads (the v5.0.0 phase — biggest accuracy gap, and it unblocks hard filters), then structured profile, then the prompt rewrite (now that live v4.4–v4.6 scoring data exists to calibrate against), then hard filters. (Account-management and external-web-surface work moved to v6 — see below.) Threads:

  • Structured Custom Match Criteria. (v5.0.0 — first v5 phase.) Replace the single textarea with essential structured fields (work authorization, preferred locations, target term + length, work mode, languages) and demote the existing free-form prose to an "additional notes" field. Biggest gap today is work-authorization signal for international students.
  • Structured PDF extraction. Switch the profile from a raw-text blob to a JSON profile (summary / education / experience / skills / projects / languages). Cheaper signal per scan than re-sending resume prose, and sharper matching. Also lets the user add supplementary experience/projects as structured entries (title + description) for things a one-page resume omits, merged into the JSON profile.
  • Scan-prompt rewrite + richer scoring output. Co-op framing, calibration anchors, few-shot examples from real v4.4 disagreements. Moves scoring to a 1–100 scale with a 5-tier verdict ladder (Strong Apply 85–100 / Apply 70–84 / Consider 50–69 / Unlikely 30–49 / Skip 1–29), and returns a structured per-aspect breakdown — the specific criteria/profile points that gained or lost points (e.g. "prefers Toronto, job in Québec"; "AWS preferred, not in profile"), surfaced in the sidebar. Aspect attribution depends on structured criteria (#1) and profile (#2); calibration waits on enough live scoring data, which v4.4+ now provides.
  • Hard filters. Once preferences are structured, auto-Skip postings that explicitly exclude the user (e.g. US-citizen-only) without spending a credit. Catches the worst false-Apply class cheaply.

v6 — Web surface + account management (planned)

Exploratory (2026-05-29) — deferred out of v5. A separate web app (a second frontend on the existing FastAPI backend) for managing the account, CV / profile text, and payment — moving that surface off the extension, which stays focused on in-page scoring. This absorbs the older "consolidate the options-page Account section" idea: rather than build a dedicated Account area into the options page, account / balance / credit-history / profile / payment management would live on the web app. Not committed; if the web direction doesn't proceed, the fallback is an options-page Account consolidation. Revisit once the v5 quality pass ships.

Further-out candidates still on the table (v6+): non-Gemini provider support, cover-letter generation, team / recruiter views, re-score on demand. No commitment yet — revisit at phase-planning time.
