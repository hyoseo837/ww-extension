Session History — ww-extension v02

This file records decisions made during v02 phases. Append a new section after each phase commit. Record only crucial decisions or non-obvious choices — not a step-by-step log. See v01's history.html for the same pattern applied to v01.001 through v01.020.

v02.018 — remaining audit fixes + doc drift (2026-05-21)

scoreJob now retries network errors on the same backoff schedule as HTTP 429 (was: immediate NETWORK failure). A transient connection blip during a scan no longer marks the job failed when one of the next three retries would have succeeded. The behaviour is now consistent with the rate-limit path — both transient classes get up to three retries with 2/4/8s delays.

Cache-create logs in content.js removed (matches the v02.016 intent to move observability from console to UI). Cache health is already visible via the cached-tokens column in the API tab — if it stays at 0 during a scan, the cache silently fell back to inline. Kept the catch blocks themselves (with brief comments) so failures still don't propagate, just no longer pollute the page console.

loadScores now shape-checks each stored entry (integer score, known verdict, string reason) before re-inserting. Corrupted storage from an earlier schema or external tampering no longer crashes injectRowScores downstream. clearScores also now resets detectedPageSize to the default 50, so the pagination estimate doesn't carry stale values across a clear.

Doc fixes applied to the historical record itself: the v02.002 entry now mentions that v02.007 dropped the PDF cap 20 → 5 MB (it previously claimed 20 MB as final), and v02.016 was corrected to say "the two billing-significant call sites" rather than "both call sites covered" — the Test API Key handler also hits Gemini, but is intentionally not counted (one-shot ~5-token validation ping; counting it would conflate "did the user check their key" with actual scoring cost).

v02.017 — atomic token counter + header auth (2026-05-21)

Token accumulation in v02.016 used chrome.storage.local.get followed by set with no serialization — concurrent calls (extraction during a scan, or back-to-back scoreJob handlers) could read the same starting value and the later write would clobber earlier increments. Fix: a module-level tokenWriteChain = Promise.resolve() in each context, with incrementTokenUsage appending the next get→set to the chain. Within a context, increments are now serial. Cross-context races (background ↔ options) remain theoretically possible but require simultaneous activity in both contexts — rare for this UX.

All Gemini calls now send the API key as X-Goog-Api-Key rather than the ?key= query string. Query-string keys land in browser history (for options-page calls) and any fetch instrumentation; header auth keeps the key contained to the request body itself.

Removed currentTheme in content.js — set on every theme change, never read. Vestigial from an earlier design that gated per-badge class toggling on the current theme; the :root.ww-light CSS-var approach made that unnecessary.

v02.016 — light/dark theme + cumulative token usage (2026-05-21)

Options page uses body.light for theme overrides (dark vars stay on :root as baseline, so no FOUC on the default dark mode before the storage read resolves). Two previously hardcoded values were promoted to vars — --primary-glow and --on-primary — because they differ between palettes and would have been invisible to a class override if left inline.

Sidebar theming uses a two-tier variable scheme: --s-* vars defined on #ww-ext-sidebar cascade to all sidebar descendants; --ww-* vars defined on :root cover elements that live outside the sidebar in the WW DOM (table badges, row highlight). The toggle button and badge tooltip are overridden via :root.ww-light #ww-ext-toggle descendant selectors rather than adding extra classes per element — single .ww-light class on document.documentElement drives everything outside the sidebar. chrome.storage.onChanged in the content script keeps the WW page in sync if the user changes the theme in the options tab without reloading.

Token usage is accumulated in chrome.storage.local (key tokenUsage) rather than sent to a UI event because the scoring runs in the background service worker, which has no direct DOM access. Tracked at the two billing-significant call sites: background.js (per-job scoring) and options.js (PDF extraction). The Test API Key handler in options.js also hits Gemini but is intentionally not tracked — it's a one-shot validation ping (~5 input tokens) and counting it would conflate "did the user check their key" with actual scoring cost. The display updates live via chrome.storage.onChanged, so the counter ticks up in real time during a scan without any polling.

v02.005 — Context caching + responseSchema (2026-05-21)

SYSTEM_TEXT is duplicated in both background.js and content.js — they are separate MV3 execution contexts and cannot share modules, so duplication is intentional. The cache body in content.js uses the same text so the cached system instruction is identical to what the inline fallback sends.

scanApiKey is hoisted outside the try block so the finally cache-delete can reference it without capturing settings (which is declared inside the try). The delete is fire-and-forget (.catch(() => {})) — the 30-minute TTL covers the case where it fails.

Markdown-fence stripping removed from the parse step — responseSchema guarantees the model returns bare JSON. validate() kept for semantic checks (score bounds, verdict membership) that the schema alone cannot enforce. Token log now includes cachedContentTokenCount to make cache hits visible in DevTools.

v02.004 — Preferences field + prompt wiring (2026-05-21)

Preferences live in a dedicated third tab ("Preferences") rather than appended to the Context tab — keeps each tab focused and makes the upcoming v02.005 caching phase easier to reason about (preferences are a per-call inline field, not part of the cached content). The conditional ternary in the prompt template ensures the Candidate Preferences: block, including its surrounding blank lines, is entirely absent when the field is empty — no token cost for users who don't fill it in.

v02.002 — PDF upload and Gemini multimodal extraction (2026-05-21)

Extraction uses inline_data with the full base64 PDF — no Files API upload step. This keeps the implementation self-contained in the options page and avoids a separate upload round-trip. The initial cap was 20 MB (Gemini's inline-data ceiling); v02.007 reduced it to 5 MB because a real CV/coop package never approaches the ceiling and the smaller limit gives faster, more obvious feedback on accidental uploads. FileReader.readAsDataURL is used (instead of readAsArrayBuffer + manual btoa) because it handles the base64 encoding in one step; the data:…;base64, prefix is stripped with a regex before sending. Extraction status is a separate #extractStatus element so the main Save/Test #status is unaffected. The textarea remains editable after extraction — the user must still click Save to persist.

v02.001 — Options page replaces popup (2026-05-21)

Pure UI migration. popup.html + src/popup.js deleted; options.html + src/options.js created with identical storage logic. Manifest swaps action.default_popup for options_ui.open_in_tab: true. Background gains action.onClicked → openOptionsPage() and an 'openOptions' message case for the sidebar button. Sidebar header gets a ⚙ button that posts {type:'openOptions'} through the background. No behavior changes to scan flow or storage.

Sidebar CSS merged #ww-ext-settings and #ww-ext-close into a shared rule — identical style, keeps the selector list short. Header buttons wrapped in .ww-ext-header-btns to avoid justify-content: space-between pushing them apart when there were three flex children.
