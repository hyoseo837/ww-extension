Docs Index

This file is the map. Open it first when you don't know which doc you need. It explains where things live and the conventions used across docs/.

Doc tree

docs/README.html
This file. Map of everything below.
docs/roadmap.html
Living vision. Active major version's goals; sketched future majors. Updated in place across version bumps — not archived.
docs/architecture.html
Living system architecture. Current shipped state: files, storage keys, components, contracts. Updated whenever the architecture changes (not per phase).
docs/specs/
One file per phase: vX.Y.Z-slug.html. Self-contained spec for that phase: vision, files to touch, verify criteria, status. Replaces the old plan.html + impl.html.
docs/decisions/
ADRs (Architecture Decision Records). One file per significant decision: NNNN-slug.html. Immutable once accepted — supersede with a new ADR rather than editing. Replaces the old chronological history.html.
docs/reference/
Stable lookup material. WW DOM cheatsheet, storage/data schemas, backend API contract. Read on demand, not by default.
docs/archive/
Frozen old major versions. v01/v02/v03 used the older plan/impl/history shape. Do not extend; reference only.
docs/whiteboard.md
User's personal scratchpad for raw ideas, possible changes, future updates. Markdown by exception (see ADR 0006) for low-friction editing. Agents: read for context; do not edit without explicit permission. Entries promoted out of here go to roadmap.html first.

Lifecycle of an idea

whiteboard.md
   ↓ (matures into a real direction)
roadmap.html
   ↓ (scheduled into a phase)
docs/specs/vX.Y.Z-*.html
   ↓ (significant call made along the way)
docs/decisions/NNNN-*.html

Not every idea travels the full path. Most whiteboard entries are dropped or stay loose for a long time. Promotion happens only when an entry earns it.

  2. docs/specs/vX.Y.Z-slug.html (the specific phase)
  3. docs/architecture.html (only the relevant section)

  1. docs/architecture.html
  2. docs/reference/data-model.html
  3. docs/decisions/ (browse titles)

  1. docs/roadmap.html (where does it fit?)
  2. docs/decisions/ (what constraints apply?)
  3. Write a new docs/specs/vX.Y.Z-slug.html following the convention below

Conventions

How to write a spec (docs/specs/vX.Y.Z-slug.html)

Required <meta>: project, type="spec", version, status (planned | in-progress | done), last-updated. Body sections:

  • Goal — one paragraph: what this phase does and why.
  • Files — files to touch (changed / added / moved).
  • Verify — concrete checks a human or agent can run to confirm the phase shipped correctly.
  • Notes (optional) — non-obvious observations from implementation. If a decision in here turns out to constrain future work, promote it to an ADR.

A trivial phase (e.g. a one-line copy fix) gets a 15-line spec. A complex phase can grow to a folder vX.Y.Z-slug/ with spec.html plus supporting assets.

How to write an ADR (docs/decisions/NNNN-slug.html)

Required <meta>: project, type="adr", status (proposed | accepted | deprecated | superseded), date, optional supersedes / superseded-by. Body sections (Michael Nygard template):

  • Context — the forces at play. Why this decision is on the table.
  • Decision — what we chose, in one or two sentences.
  • Consequences — what becomes easier, what becomes harder, what's now constrained.

ADRs are immutable once accepted. To change a decision, write a new ADR that supersedes the old one (link via supersedes / superseded-by meta and an explicit prose pointer).

File naming

  • Specs: vX.Y.Z-kebab-slug.html (e.g. v4.1.0-auth.html). The vX.Y.Z string is identical to the manifest.json version field — no zero-padding, no concatenating Y and Z. Legacy specs under docs/archive/ used a different naming scheme; see ADR 0002.
  • ADRs: NNNN-kebab-slug.html, zero-padded to four digits (e.g. 0001-html-over-markdown.html). Numbering is monotonic and never reused.
