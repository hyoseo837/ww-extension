plan.html Corrections (v01.002)

  1. Posting ID column is a <th>, not <td>. plan.html said "the posting ID is the text content of the first td". The rendered DOM has <th scope="row"> for the first column. Corrected to: use input[name="dataViewerSelection"].value (numeric string). Fallback: checkbox id matches /^resultRow_(\d+)$/.
  2. Vue template attributes stripped from rendered DOM. plan.html said to use col-key="Id" and :is-id="true" as selectors. These are Vue template props consumed by DataViewer and are absent in the rendered HTML. Removed from spec.
  3. Table selector added. plan.html did not specify how to uniquely identify the jobs table. Added: #dataViewerPlaceholder table.data-viewer-table (the data-viewer-table class is unique to this table on the page).
  4. Action tokens are object-literal values, not var declarations. plan.html said "embedded as string literals... by searching for the function or variable name". The actual pattern is always an object property value (e.g. action: '_-_-...' inside a $.post call). Updated extraction language and provided concrete regexes in both plan.html and exampleWW-compact.html §4.
  5. getPostingOverview returns an HTML string, not JSON. plan.html implied JSON. The function has no explicit dataType on its $.post call, so jQuery returns the raw server response — an HTML string. Must use DOMParser + .textContent to extract plain text before sending to Gemini.
  6. Folder trigger: bare form, not .$data form. plan.html said dataViewerApp.$data.jobFolderEditSidebar = true. The page itself uses dataViewerApp.jobFolderEditSidebar = true (bare, no .$data) for single-row actions. Both work in Vue 3; corrected to bare form.
  7. Vue 3.5.13 IS loaded by the page. plan.html said "NOT a plain Vue 3 SPA" — true, but implied Vue was not present. Vue 3.5.13 is loaded globally as the underlying framework for DataViewer. The extension must not ship its own copy of Vue.

Score persistence + cross-page navigation (2026-05-20)

Persistence overrides the original out-of-scope decision — explicit user request
plan.html listed "Saving scores across sessions or page reloads" as out of scope. User explicitly requested persistence to save API tokens across partial scans. Scores and allPostingIds are stored in chrome.storage.local (ww_scores, ww_posting_ids). New scores overwrite old ones for the same posting ID; others are preserved (merge semantics).
allPostingIds drives cross-page navigation — assumes default DataViewer sort order
scrollToRow calculates target page as floor(resultIds.indexOf(postingId) / pageSize) + 1. This is only correct when DataViewer is in the same sort order as the selectAll response. If the user sorts by a different column, the navigation may land on the wrong page.

v01.020 — scrollToRow: tighter selector + restore-on-failure (2026-05-20)

Drop CSS.escape, lock the selector to name="dataViewerSelection"
Posting IDs are numeric strings — no escaping is needed for an attribute-value selector. CSS.escape's \34 form is technically valid inside a quoted attribute value but is needless churn and was the prime suspect for "walk goes through all pages, finds nothing." Selector now reads input[name="dataViewerSelection"][value="${idStr}"].
String-normalize allPostingIds on scan
data.resultIds from selectAll could be strings or numbers depending on WW's JSON serialization. card.dataset.postingId is always a string, so a number-typed allPostingIds means allPostingIds.indexOf(idStr) silently returns -1, skipping the direct jump. postingIds.map(String) forces consistency.
Save start page, restore on failure, surface error
Previously: if the walk failed to find the row, the user was stranded on the last page reached with no feedback. Now: stash activePageText() at entry; if the row isn't found after the walk, surface "Posting X not in current view — filter or sort may have changed" via setProgress, then navigate back to the start page.

v01.019 — scrollToRow: read active/disabled from the <a>, not the <li> (2026-05-20)

WW pagination puts state on the <a class="pagination__link">, not the wrapping <li>
v01.018's helpers all read active / disabled / aria-label from the <li>, which never has any of those. Effects:
  • activePageItem() always returned undefined → waitActive predicate never matched → every navigation burned the full 800ms timeout.
  • nextPageItem()'s findIndex(li => li.classList.contains('active')) returned -1 → nextPageItem returned null → the walk broke on its first hop. This is the real reason page 1 → anywhere failed: we never advanced past page 1.
  • Page 4 → page 1 "worked" by accident — after ~1.6s of failed waits a rAF check happened to find the row that the click had in fact moved into place.
Fix: helpers now operate on .pagination__link elements directly (paginationLinks / activeLink / pageNumberLink / nextPageLink).
Dispatch synthetic clicks to avoid CSP errors from javascript: hrefs
Pagination anchors are <a href="javascript:void(0);">. Calling the native .click() makes the browser try to navigate to the javascript: URL, which CSP blocks (cosmetic, but noisy). Switched to dispatchEvent(new MouseEvent('click', { bubbles: true, cancelable: true, view: window })) — Vue's @click handler still fires (it listens via addEventListener), but untrusted events don't trigger the anchor's default navigation.

v01.018 — scrollToRow: watch active page, not the row (2026-05-20)

Wrong wait target — we watched for the row, not the navigation
waitForRowOrIdle observed the table for the target input[value="..."] to appear. If the destination page didn't contain the row (sort mismatch, stale order, or direct click landed on the wrong page), the observer never fired and we burned the full 2000ms timeout before falling through. Then the fallback waited another 1500ms per hop. 5-page walk = ~9.5 seconds.
Watch pagination's active-page text instead
DataViewer page changes flip the active class on the new page item in the same render cycle. Watching that with attributeFilter:['class'] resolves in ~1 frame regardless of where the row actually ended up. We then check separately whether the row is on the new page; if not, walk forward. New per-hop budget: ~50ms instead of 1500ms.
Next-button detection beyond just "next numeric li"
Previous nextPageItem() fell back to items[items.length - 1] which is "Last", not "Next". Now also matches by aria-label / text against next|›|»|→ and skips disabled items. Important when the active page is the last visible numeric item in a windowed pagination ("…1 2 3 4 5 next»").
aria-disabled honoured in addition to .disabled
Some WW pagination items may use the ARIA attribute instead of the class. isItemDisabled() checks both.

v01.017 — Verdict filter + TDZ hotfix (2026-05-20)

Module constants must precede the init block — TDZ regression from v01.016
v01.016 added const TABLE_SEL AFTER the if (!__wwExtensionInjected) { waitForTable() } block. waitForTable is a function declaration so it's hoisted — but its body references TABLE_SEL, which is in the temporal dead zone when the synchronous init call runs. Result: ReferenceError, content script dead on arrival. Fix: hoist all const/let declarations above the init block.

Verdict filter

Three pill toggles (Apply / Consider / Skip) compose with the Score ≥ threshold
Filter is the intersection: score >= min && verdicts.has(verdict). Defaults to Apply ✓ Consider ✓ Skip ✗ — Skip is rarely something the user wants to save into a folder, but leaving it as a toggle keeps the workflow flexible.
Pure-CSS toggle state via :has(input:checked)
No JS event listeners on the checkboxes — the label-with-hidden-checkbox pattern plus :has() drives the visual state. Chrome 105+ (Aug 2022), which is below the floor for any user on current WaterlooWorks anyway. Verdict colors match the badge palette so the toggles visually identify what they filter.

scrollToRow — robust page navigation (2026-05-20)

Page size was wrong on the last page
Previous impl used querySelectorAll(ROW_SEL).length || 50 as the page size. On the last page that returns the partial count (e.g. 7) — the targetPage math then sends you to the wrong page. Fix: detectedPageSize is a module-level max-watermark updated from the table observer; never shrinks.
Target page button often isn't in visible pagination
WW pagination renders a windowed view: 1 2 3 4 5 … 19 20. The button for page 8 isn't in the DOM, so querying for it returns null and navigation silently fails. Fix: if direct click misses, reset to page 1 and walk forward via Next (max 40 hops; bails if the active page stops changing).
Sort-order mismatch handled by the same fallback
allPostingIds is in selectAll's default order. If the user has re-sorted the DataViewer, the index → page mapping is wrong. The forward walk from page 1 finds the row regardless of sort order — at most O(pages) clicks.

Quality pass — Opus 4.7 review (2026-05-20)

Bypass getPostingOverview to kill the loading-overlay flicker
WW's getPostingOverview() calls orbisApp.showLoadingOverlay() per request. During a 200-job scan that's 200 overlay flashes. Bridge's fetchOverview now hits /myAccount/co-op/full/jobs.htm directly with $.post + the cached action token, skipping the overlay. Page-side cached the extracted tokens too so re-scans don't re-walk every inline script tag.
Scan loop throttles sidebar re-render + storage writes
Previously, every successfully scored job triggered saveScores() + renderSidebarList() synchronously — O(n) work per call, O(n²) over a full scan. New scheduleFlush() coalesces both into a 300ms-debounced setTimeout. Also keeps writes under chrome.storage.local's quota when scoring fast. Final unconditional flush runs at scan end so the persisted state matches what's on screen.
Structured error codes between background and content
background.js now returns {ok:false, code, error} where code ∈ {NETWORK, RATE_LIMIT, HTTP, PARSE, SHAPE}. Replaces the brittle reply.error?.includes('Rate limited') string match. Adding new error types from the worker no longer requires touching content.js's branching logic.
Gemini response shape validated server-side
background.js now validates score ∈ 1..10, verdict ∈ {Apply, Consider, Skip}, reason non-empty. Bad-shape responses return code:'SHAPE' instead of getting stored as scores Map entries with garbage data that would later crash the badge CSS (.ww-ext-badge--<unknown> has no styling).
CSS.escape() for posting IDs in selectors
scrollToRow() template-strung the posting ID into input[value="${id}"]. Numeric IDs are safe but it was an injection liability. Now uses CSS.escape() and reuses the escaped selector for both the initial lookup and the post-navigation lookup.
esc() handles null/undefined defensively
Sidebar render previously called .replace() on whatever string came through. A missing reason or org (e.g. interrupted scan partial entry) would throw. esc() now coerces with String(value ?? '') first.
Stable sort for the sidebar list
Equal-score jobs used to reorder arbitrarily on every render. Now: score desc → verdict (Apply > Consider > Skip) → title asc. Predictable position across re-renders so the user doesn't lose their place mid-scan.
20s timeout on the selectAll fetch
Previously no timeout — if WW hung, scan hung forever with no Stop possible (the for-loop hadn't started yet). AbortSignal.timeout(20000) bounds the wait.
Magic numbers extracted to module constants
TABLE_SEL, ROW_SEL, DESC_CHAR_CAP, SCAN_DELAY_MS, FETCH_TIMEOUT. The two table selectors were duplicated in 6+ places; one source of truth now.

Mid-flight fixes (2026-05-20)

DataViewer reuses tr elements across page changes — badges leak unless wiped
Page change does NOT replace the entire tbody. DataViewer mutates row contents in place: the same tr now shows a different posting ID, but the old .ww-ext-badge span from the previous occupant is still there. The idempotency check found the old badge and skipped re-injection. Fix: in the table MutationObserver callback, disconnect, strip all .ww-ext-badge from the table, re-inject, reconnect. rafPending flag debounces multiple mutations into one rAF pass.
Title self-heals on page visit instead of being looked up via separate API call
indexVisibleRows() only captures titles for jobs on the current page at scan start. Jobs on other pages get title="#postingId". Fix: injectRowScores() now also updates stored title/org from the live row whenever the row becomes visible. After the user browses through pages, all titles are eventually corrected without any extra network calls.
Cross-page navigation waits for the row to appear, not a fixed 700ms
scrollToRow used setTimeout(700) after clicking a pagination button. Replaced with a MutationObserver that resolves the moment input[value=""] appears in the tbody, with a 2s ceiling. Reliable on slow re-renders.

v01.012 — Ranked sidebar list + row navigation (2026-05-20)

Delegated click handler set up once in injectSidebar, not per render
renderSidebarList() rewrites innerHTML on every score, which would lose per-element event listeners. A single delegated listener on the ul persists across re-renders and routes clicks via closest('.ww-ext-card').
scrollToRow is a no-op when the row is not on the current page
If the posting ID is on a different page, the input selector returns null and the function exits silently. No navigation to other pages — per spec.

v01.011 — AI Score column + badge re-injection (2026-05-20)

Observer fires twice per DataViewer re-render but second call is a no-op
When DataViewer replaces the tbody, the observer fires and injectRowBadges() adds td[data-ww-score] elements, which triggers the observer again. The second call finds all rows already have td[data-ww-score] and exits early. No infinite loop, no flag needed.
Empty badge cells are not added for unscored jobs
injectRowBadges() only appends a td if the row doesn't already have one. For unscored jobs the td is still appended (blank), which keeps column alignment. Only jobs in the scores Map get visible badge content.

v01.010 — Scan All Jobs flow (2026-05-20)

Title/org only available for visible rows; fallback is #postingId
indexVisibleRows() maps only the currently rendered table rows to title/org. Jobs on other pages get title="#postingId", org="" as a fallback. This is acceptable because the sidebar list (v01.012) will display whatever is stored, and titles for visible-page jobs will be correct.
fetchOverview failures are skipped silently
If the bridge times out or getPostingOverview errors for a specific posting, the scan increments the counter and continues rather than aborting the whole scan. A broken single posting should not kill 200 others.

Bugfixes found during v01.009 testing (2026-05-20)

script.remove() must be in onload, not synchronous
Removing a <script src> element from the DOM synchronously after appendChild causes Chrome to skip execution when the fetch completes. Moved remove() to script.onload so the element stays in the document until the script has run.
gemini-2.5-flash thinking tokens consume maxOutputTokens budget
gemini-2.5-flash is a thinking model. Internal reasoning tokens count against maxOutputTokens, leaving almost none for the actual JSON response. Fixed by setting thinkingConfig: { thinkingBudget: 0 } to disable thinking (unnecessary for simple scoring) and raising maxOutputTokens from 300 to 1024.

v01.009 — Page bridge (2026-05-20)

e.source === window check prevents cross-origin message spoofing
WaterlooWorks and any embedded iframes could otherwise postMessage into the bridge. Checking e.source === window ensures only same-window messages are processed, and the __ww_ext_cs / __ww_ext_page source field namespaces extension messages away from anything WW posts internally.
script.remove() after bridge injection is safe
Removing the <script> element from the DOM after appending it does not stop or interrupt script execution. The script continues running. Removing it keeps the DOM clean.

v01.008 — Content script: sidebar shell (2026-05-20)

All CSS selectors are ID-based with ww-ext- prefix
WaterlooWorks injects its own CSS globally. Using IDs (high specificity) with a unique prefix avoids any class-name collisions without needing Shadow DOM.
Toggle button uses writing-mode: vertical-rl instead of transform: rotate
Vertical text via writing-mode keeps the button's clickable area correctly sized along the right edge. A rotated element would misalign its hit box.

v01.007 — Background worker / Gemini client (2026-05-20)

Network errors abort immediately; only 429s are retried
A network-level fetch failure (DNS, timeout, offline) returns immediately with an error rather than retrying. Retries are reserved for 429 rate-limit responses, which are transient by nature. Non-429 HTTP errors (4xx/5xx) also abort immediately since retrying them is unlikely to help.
JSON parse failure returns the first 100 chars of raw output in the error
Gemini sometimes returns unexpected formats. Including the raw prefix in the error message makes it diagnosable without having to instrument the service worker.

v01.006 — Settings popup (2026-05-20)

Popup makes Gemini test calls directly, not via background.js
The Test API Key button fetches the Gemini endpoint from popup.js rather than routing through background.js. Both contexts have host_permissions for generativelanguage.googleapis.com, so this works and avoids unnecessary message passing for a one-off UI action.
