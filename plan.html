ww-extension — Project Plan

This is the authoritative plan. All decisions here have been confirmed with the user. Read this fully before writing any code.

Vision and Goal

WaterlooWorks lists hundreds of co-op job postings per term. Evaluating each one manually — reading descriptions, judging fit, deciding whether to apply — takes hours. The goal of this extension is to eliminate that manual triage entirely: let AI read every posting, score it against the user's background, and surface only the jobs worth spending time on.

The approach is a Chrome extension rather than a scraper or external tool for one key reason: WaterlooWorks requires authenticated sessions, and the extension runs directly in the user's browser where that session already exists. No auth tokens to manage, no reverse-engineering login flows, no external server. The extension piggybacks on the browser's existing session transparently.

This is a personal tool built by Hyoseo Lee (CS co-op student, University of Waterloo, 2026 Spring term) for his own job search. The measure of success is simple: open WaterlooWorks, click Scan, and immediately know which jobs are worth applying to — without reading a single description manually.

Project Overview

A Chrome extension (Manifest V3) for personal use on the WaterlooWorks co-op job search page. It reads all job IDs across all pages, fetches each job description, scores each job against the user's CV using the Gemini API, and injects score badges directly into the WaterlooWorks job table. A sidebar provides controls and a ranked list of all scored jobs.

Target site

https://waterlooworks.uwaterloo.ca — specifically the co-op full-cycle jobs page (/myAccount/co-op/full/jobs.htm). The job table is managed by a proprietary DataViewer Vue component (DataViewer.umd.min.js v0.10.2) on top of jQuery 3.1.1 and Vue 3.5.13. It is NOT a plain Vue 3 SPA — DataViewer is a plugin registered on top of Vue 3. The page loads Vue 3.5.13 globally; do not ship a second copy of Vue with the extension.

Architecture

content.js

  • Injects the sidebar toggle button and sidebar panel into the page. Uses a module-level boolean flag to prevent duplicate injection on re-runs.
  • Waits for the DataViewer table to appear using MutationObserver before doing anything.
  • On "Scan All Jobs": POSTs to /myAccount/co-op/full/jobs.htm with the selectAll action token (extracted from the page's inline scripts) to retrieve all matching posting IDs across all pages. This mirrors what WaterlooWorks does internally for its "select all" feature.
  • For each posting ID, fetches the full job description by calling getPostingOverview via a page-context script injection and postMessage. This is done from the page context (not the content script isolated world) so it can use the session cookies and the action token already embedded in the page's JS.
  • Sends each job's text to background.js for Gemini scoring. Adds a 600ms delay between jobs to avoid rate limits.
  • Stores all scores in memory (Map: postingId to score result).
  • Injects an AI Score column into the visible table rows. Uses a MutationObserver on the tbody to re-inject badges whenever the DataViewer re-renders rows (on sort, filter, page change).
  • Sidebar shows a ranked list of all scored jobs (sorted by score descending) regardless of which page is currently visible.
  • For "Save to Folder": triggers WaterlooWorks' native folder UI by setting dataViewerApp.sidebarPostingIds and dataViewerApp.$data.jobFolderEditSidebar = true. No custom storage needed.

background.js (service worker)

  • Receives a message from content.js: job metadata, description text, CV summary, API key, and model name.
  • Calls the Gemini API and returns a score (1–10), verdict (Apply / Consider / Skip), and a 2–3 sentence reason.
  • Retries on 429 responses with exponential backoff: 2s, 4s, 8s (max 3 retries).
  • Strips markdown code fences from the response before JSON parsing.

popup.html + popup.js

  • Stores settings in chrome.storage.local: Gemini API key, model name, CV summary (plain text).
  • Fields: API key (password input), model selector, CV textarea.
  • "Test API Key" button: sends a minimal prompt to verify the key works.
  • Does not store scores or job data. That lives only in content.js memory for the lifetime of the page.

WaterlooWorks DOM and API

Job table structure (from exampleWW-compact.html §1)

The table is rendered by the DataViewer component inside #dataViewerPlaceholder. Unique CSS selector: #dataViewerPlaceholder table.data-viewer-table. Each visible job row is a tr.table__row--body inside a tbody. Columns in order: Id (posting ID), Job Title, Organization, Division, Openings, City, Level, Apps (ApplicationCount), App Deadline.

The first column is a <th scope="row">, not a <td>. The Vue template attributes col-key="Id" and :is-id="true" are stripped from the rendered DOM and must not be used as selectors. Read the posting ID from: tr.table__row--body input[name="dataViewerSelection"].value (numeric string, e.g. "471670"). Fallback: the checkbox id matches /^resultRow_(\d+)$/.

To inject the AI Score column: append a th (class "table__heading overflow--hidden", data-v-612a1958="") to thead tr.table__row--header, and a matching td (class "table__value overflow--hidden", data-v-612a1958="") to each tr.table__row--body. Re-run injection inside the MutationObserver callback.

Getting all posting IDs (across all pages)

WaterlooWorks' "select all" feature internally POSTs to /myAccount/co-op/full/jobs.htm with the selectAll action token and returns data.resultIds — an array of all posting IDs matching the current filter. Extract the selectAll action token from the inline script that defines the onSelectAll callback (search for "onSelectAll" in all script tags). Use this same request from content.js to get all IDs.

Fetching job descriptions (from exampleWW-compact.html §3)

The page defines getPostingOverview(postingId, callback) which POSTs to /myAccount/co-op/full/jobs.htm with the posting's action token and session cookies. It does NOT specify a jQuery dataType, so the callback receives an HTML string (not a JSON object). Strip it to plain text using DOMParser + .textContent before sending to Gemini.

Because content scripts run in an isolated world and cannot call page-defined functions directly, inject a small script element into the page to call getPostingOverview and relay the result back via window.postMessage. The content script listens for that message.

Action tokens (from exampleWW-compact.html §4)

Each WaterlooWorks action has its own session-specific token starting with _-_- followed by a base64url payload ([A-Za-z0-9_-], ~195–215+ chars). Tokens are always object-literal values (e.g. action: '_-_-...' inside a $.post call or dataViewerProps property) — never bare variable declarations (var x = '_-_-...'). Tokens must be extracted fresh on each page load — they change per session. Scan inline script elements (script:not([src])) and search for the owning function or property name, then capture the adjacent token with a regex such as: /onSelectAll[\s\S]{0,400}?action:\s*['"](_-_-[A-Za-z0-9_-]+)['"]/

Native folder feature (from exampleWW-compact.html §5)

WaterlooWorks has a built-in "Save to My Jobs Folder" feature. Trigger it from content.js by injecting a page-context script that sets: dataViewerApp.sidebarPostingIds = Number(postingId) and dataViewerApp.jobFolderEditSidebar = true. The bare form (no .$data) is what the page itself uses for single-row actions (exampleWW-compact.html §5). Both the bare form and the .$data form work in Vue 3; use the bare form. The WW folder sidebar then handles all storage.

CV Input

Plain text only. The user pastes their CV summary into a textarea in the popup. Stored in chrome.storage.local. No PDF parsing. Plain text minimizes token cost and avoids formatting noise.

Features

  1. Sidebar toggle button fixed to the right edge of the WaterlooWorks page.
  2. Sidebar panel with: Scan All Jobs button, progress indicator (x of y jobs scored), stop button, and a ranked list of all scored jobs sorted by score descending.
  3. Each sidebar job card shows: score, verdict, job title, org, reason. Clicking a card scrolls the table to that row if visible, or navigates to that page.
  4. AI Score column injected into the WaterlooWorks job table. Each badge shows the score and verdict color (green = Apply, yellow = Consider, red = Skip). Badges persist across pagination via the score Map.
  5. Per-row action in the table: "Save to Folder" button that triggers WaterlooWorks' native folder sidebar.
  6. Settings popup: API key, model selector, CV textarea, Save button, Test API Key button.

Out of Scope

  • Auto-apply (clicking Apply buttons automatically).
  • Cover letter generation.
  • Saving scores across sessions or page reloads.
  • Any backend server or remote storage.
  • Non-Gemini AI providers (extensible by design, not built now).
  • PDF CV upload.

Key Constraints and Gotchas

  • Content scripts run in an isolated world — they cannot access page-defined JS variables or functions (dataViewerApp, getPostingOverview, etc.) directly. Use script-tag injection into the page context and window.postMessage to bridge the gap.
  • The DataViewer re-renders tbody rows on every sort, filter, page change, and refresh. Always re-inject score badges inside the MutationObserver callback, not just on page load.
  • Action tokens are session-specific. Extract them from the current page's script tags on each scan — never hardcode or cache across sessions.
  • Gemini sometimes wraps JSON in markdown fences. Always strip fences before parsing.
  • Add 600ms delay between Gemini calls. Retry on 429 with exponential backoff (2s, 4s, 8s, max 3 retries).
  • The page size is 25 or 50 (user-selectable). Scanning all jobs requires the selectAll POST to get IDs beyond the visible page.
  • manifest.json must declare host_permissions for waterlooworks.uwaterloo.ca and generativelanguage.googleapis.com.
